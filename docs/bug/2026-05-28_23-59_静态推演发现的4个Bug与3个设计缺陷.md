## Bug 1 🔴 `_run_mastering` 文件名冲突——最优版本被静默覆盖

**文件**: `orchestration/workflow_engine.py:615`

**现象**: Phase 4-6 循环中，每个版本调用 `_run_mastering` 生成输出文件。但三个版本生成的文件名完全相同。

```python
# workflow_engine.py:613-616
base_name = Path(input_path).stem          # "test"
emotion_short = emotion_target[:2]         # "GA"
output_filename = f"{base_name}_{emotion_short}_{platform}.wav"
# → "test_GA_spotify.wav"  ← 版本 1/2/3 同名
```

**伤害链**:

```
i=0: _run_mastering → 写入 "test_GA_spotify.wav" (Version 1 的音频)
     _diagnose_audio → 读取 Version 1 ✓ → eds=68.2
     → best_eds=68.2, best_output="test_GA_spotify.wav"

i=1: _run_mastering → 覆写 "test_GA_spotify.wav" (Version 2 的音频)
     _diagnose_audio → 读取 Version 2 ✓ → eds=61.1 (不更新 best)

i=2: _run_mastering → 覆写 "test_GA_spotify.wav" (Version 3 的音频)
     _diagnose_audio → 读取 Version 3 ✓ → eds=59.5 (不更新 best)

循环结束:
  best_eds = 68.2                    ← 来自 Version 1
  best_output = "test_GA_spotify.wav" ← 磁盘上是 Version 3
```

然后第 275 行:
```python
ws_after_obj = self._diagnose_audio(best_output)
# 读到的是 Version 3 的频谱, 不是 EDS=68.2 的 Version 1
```

**结论**: `WorkflowResult.wave_state_after` 和 `WorkflowResult.eds` 来自两个不同的音频版本。用户拿到的是最后一个版本（EDS 最差的那个），而不是 EDS 最优的版本。

**根因**: `_run_mastering` 的签名没有版本参数，多版本循环中无法区分输出文件。

**修复方向**: 文件名加版本后缀，如 `test_GA_spotify_v1.wav`。

## Bug 2 🟡 `vector_bias` 全程未使用——Phase 0 的 LLM 产出被丢弃

**文件**: `orchestration/workflow_engine.py:119` → `optimizer/search.py:122` → `diagnosis/health_scorer.py:119`

**现象**: Phase 0 通过 `resolve_emotion_from_nl()` 获取了 DeepSeek 解析的 `vector_bias`，但后续两个关键计算点都没有接收和使用它。

**证据链**:

Phase 0 产出:
```python
# workflow_engine.py:114-121
emotion_parsed = {
    "vector_bias": {"E": 0.03, "D": 0.0, "S": -0.02, "T": 0.0, "H": 0.02},
    ...                                                   # ↑ DeepSeek 说 "比 GA 偏亮 +0.03"
}
```

proxy 评估（搜索阶段）:
```python
# optimizer/search.py:107,122
def proxy_evaluate(strength_vector, diagnosis, emotion_code: str, craft_card=None):
    #                                         ↑ 只接收 emotion_code 字符串
    target = get_ideal_process_vector(emotion_code)
    #        ↑ 返回 stock 理想向量, bias 无法传入
```

EDS 测量（后处理阶段）:
```python
# health_scorer.py:119-120
def compute_eds(self, ws_raw, ws_processed, emotion_target: str):
    target_vec = self._get_ideal_vector(emotion_target)
    #            ↑ 同样查表返回 stock 向量, bias 不可达
```

**结论**: 用户输入 `"像清晨阳光穿过窗帘，温暖但不刺眼"`，DeepSeek 正确解析出 `E+0.03 (偏明亮)`。但整个处理流水线用的是标准 "温柔觉醒" 的理想向量。NL 描述和预设代码 "GA" 产生完全相同的结果。Phase 0 的核心价值被完整丢弃。

**根因**: `proxy_evaluate` 和 `compute_eds` 的接口设计只接受 `emotion_code: str`，无法传递偏置信息。bias 数据从 `emotion_parsed` dict 中取出后没有进入任何计算路径。

**修复方向**: 创建 `EmotionContext` 值对象，包含 code + intensity + vector_bias，提供 `get_ideal_vector()` 方法统一应用 bias。所有接受 `emotion_code: str` 的函数改为接受 `EmotionContext`。

## Bug 3 🟡 RAG 推荐参数无边界校验

**文件**: `orchestration/workflow_engine.py:164-167`

**现象**: LLM 返回的参数直接传给 DSP 链，没有经过 `craft_chains` 的 min/max 边界校验。

```python
# workflow_engine.py:164-168
result = llm.recommend_params(prompt)
if result and "parameters" in result and "strength_vector" in result:
    rag_params = {p["param_name"]: p["value"] for p in result["parameters"]}
    rag_strength = result["strength_vector"]
    rag_confidence = result.get("confidence", 0.7)
    # ← 直接使用。没有任何 clamp/validate。
```

对比搜索路径的 `strength_to_params()`（`optimizer/search.py:181`）:
```python
value = max(mn, min(mx, value))  # ← 始终 clamp 到 min/max
```

**可能的伤害场景**:
- LLM 幻觉出 `P06_compression_ratio: 20.0`（GA 安全上限是 2.5）
- LLM 输出负数 `P10_reverb_t60: -0.5`
- LLM 遗漏某个参数键（只有 14 个而非 15 个）

这些情况在搜索路径中会被 `strength_to_params` 的 clamp + `get_recommended_params` 的 fallback 拦截。但 RAG 路径直接裸用 LLM 输出。

**根因**: RAG 路径和搜索路径走了两条不同的参数生成逻辑。搜索路径有完整的参数→强度→参数往返校验，RAG 路径没有。

**修复方向**: RAG 参数在返回前通过 `strength_to_params` 反推验证，或至少 clamp 到 craft_chains min/max。LLM prompt 中的安全范围声明不足以防止幻觉。

## Bug 4 🟢 DefectClassifier 重复调用三次

**文件**: `orchestration/workflow_engine.py:287,150` + `optimizer/search.py:212`

**现象**: 同一个 `WaveStateDiagnosis` 被 `DefectClassifier.classify()` 分析了三次，输入相同，输出相同。

```
调用 1: _run_diagnosis()           (workflow_engine.py:287)
         → defects 存入 phase1.output["defects"]
         → 但后续代码没有从这里读取

调用 2: Phase 1.3 RAG 路径         (workflow_engine.py:149-150)
         → classifier = DefectClassifier()
         → defects = classifier.classify(ws, emotion)
         → 用于构建 RAG prompt

调用 3: search_optimal_strengths()  (optimizer/search.py:212)
         → classifier = DefectClassifier()
         → defects = classifier.classify(diagnosis, emotion_code)
         → 传给 define_strength_space()
```

**结论**: 不影响正确性，但浪费了诊断计算资源。`DefectClassifier.classify()` 依赖 `HealthScorer._diagnosis_to_process_vector()` 和其他内部逻辑，虽然不是最重的操作，但三次重复调用暴露了数据流设计的缺陷——Phase 1 已经产出了 `defects`，却没有被下游复用。

**根因**: `search_optimal_strengths()` 的接口设计为自包含（自己分类缺陷），导致调用方 Phase 1.3 也必须自己做一次。正确的依赖方向是：调用方提供已分类的 defects，搜索函数只消费。

**修复方向**: `search_optimal_strengths()` 接受可选的 `defects` 参数。Phase 1 的 defects 存入上下文，Phase 1.3 和 1.5 复用。

## 缺陷 5 🟢 `process()` 方法 260 行，无法单元测试

**文件**: `orchestration/workflow_engine.py:79-338`

当前 `process()` 包含的情绪解析、RAG 检索、参数搜索、音频处理、结果选择、LLM 解读、历史记录全部耦合在一个方法内。任何一个环节的改动都需要修改 `process()`。无法对"参数选择"或"版本比较"做独立的单元测试。

**修复方向**: 提取 `ParameterSelector` 协议（策略模式）+ `AudioPipeline` 类（封装 Phase 3-6），让 `process()` 退化为 ~30 行的薄壳编排器。

---

## 缺陷 6 🟡 RAG 和 Search 是同一抽象但实现为 if/else

**文件**: `orchestration/workflow_engine.py:172-207`

RAG 路径和搜索路径本质上都是 `(diagnosis, emotion) → list[Candidate]`。但因为没有统一接口：
- 增加第三种策略（如基于 `offline_fallback.py` 的加权聚合）需要再加一个分支
- RAG 路径只产 1 个候选，跳过了多版本比较机制
- 两路径的 PhaseResult 结构不同（`source: "rag_llm"` vs 无此字段）

**修复方向**: `ParameterSelector` 协议 + `SelectorChain` 责任链。RAGSelector 返回 None 时自动 fallback 到 SearchSelector。

## 缺陷 7 🟢 Phase 4-6 循环产生 9 个 PhaseResult，6 个指向已覆盖的文件

**文件**: `orchestration/workflow_engine.py:234-250`

每个版本 append 3 个 PhaseResult（Phase 4/5/6），3 版本 = 9 个。输掉的那 6 个版本的 PhaseResult：
- 状态是 `COMPLETED`
- 但对应的输出文件已被下一个版本覆盖
- 在最终报告中它们看起来都是成功的，但数据已不存在

**修复方向**: `AudioPipeline.process()` 返回 `ProcessedResult` 而非追加 PhaseResult。`process()` 只保留最优版本的 PhaseResult。
