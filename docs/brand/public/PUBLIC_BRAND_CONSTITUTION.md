# Moodify Public Brand Constitution v0.1

**状态：** Public Form 阶段工作权威

**日期：** 2026-08-19

**适用范围：** Moodify 所有公开网站、App 公共文案、下载页、Demo、媒体资料、路演首页、社交媒体简介、SEO/OG 文案
**不适用范围：** 内部研究文档、模型实验记录、工程协议、学术讨论

---

# 0. 宪法目的

Moodify 已经形成多条技术、产品与研究路径，但公共世界只能同时记住极少数信息。

本宪法的目的不是缩小 Moodify 的能力，而是压缩它的公共认知：

> **内部可以复杂，外部必须简单。**

Moodify 的公开表面不再承担“展示我们做了多少”的任务，而承担“让人立即知道我们为什么存在、用户得到什么”的任务。

---

# 1. 创始价值原点

## 1.1 原始表达

> **弱者的声音也值得被世界听见。**

这句话定义的是 Moodify 站在哪一边。

它指向一个长期存在的问题：声音被听见的机会并不平等。时代、录音条件、设备、资金、技术、分发能力与社会资源，会影响一个声音最终以怎样的质量抵达人。

Moodify 不接受“资源不足，所以声音只能更差地被听见”作为理所当然的结果。

## 1.2 对外转换

公共产品不应把用户直接定义为“弱者”。

因此，对外统一转换为：

> **每一种声音，都值得被世界听见。**
>
> **Every voice deserves to be heard.**

这是 Moodify 的最高级公共品牌语义。

它不是一次营销 campaign 的临时 slogan，而是长期判断标准。

任何未来功能、页面、商业模式和合作，只要与这句话严重冲突，就应重新审视。

---

# 2. Moodify 是什么

## 2.1 公共定义

Moodify 首先是一个**聆听产品**。

它的公共任务不是向用户展示复杂的音频工程，而是让声音以更值得被听见的方式被播放。

用户看到的应该是：

`Sound -> Moodify -> Play`

而不是：

`Upload -> Separation -> Representation -> Judgment -> Intervention -> Verification -> Model -> Evidence -> Pipeline`

后一条链路可以真实存在，但属于内部。

## 2.2 不再用什么定义 Moodify

以下概念可以作为技术、历史或研究描述存在，但**不得继续成为 Moodify 的首要公共定义**：

- AI 音乐后处理平台
- Auditory Intelligence Infrastructure
- The Ear of AI
- 音频 API 平台
- ACU 计算平台
- Creator Platform
- 又一个音乐流媒体平台
- 老歌修复工具
- 分轨工具
- 母带工具

这些都可能是 Moodify 的能力、阶段、模块或未来商业支线，但不是品牌原点。

---

# 3. 品牌五层结构

Moodify 的公开与内部信息必须按层级组织。

## Layer 1 - WHY / 信念

> **Every voice deserves to be heard.**
>
> 每一种声音，都值得被世界听见。

回答：为什么 Moodify 存在？

## Layer 2 - PRODUCT PRINCIPLE / 产品原则

> **LISTEN. THEN PLAY.**

回答：Moodify 与普通播放行为的不同是什么？

Moodify 不把 Play 当作未经思考的输出。系统可以先理解、准备、验证，再把复杂度隐藏在播放之前。

## Layer 3 - ACTION / 用户动作

> **Play.**

回答：用户最终需要做什么？

Moodify 的终点不是阅读技术报告，而是听。

## Layer 4 - INTERNAL CAPABILITY / 内部能力

Listen / Represent / Judge / Intervene / Verify / Learn 等能力可以继续存在，但默认不占据公共首屏。

它们只在以下场景出现：

- Research
- Evidence
- Technical Notes
- Developer / Engineering 内部文档
- 必须解释可验证性的时候

## Layer 5 - RESEARCH ORIGIN / 研究原点

> **Can machines learn to hear?**

这是长期研究问题，不再等同于面向公众的产品介绍。

---

# 4. 产品承诺

Moodify 的公开承诺应该满足三个条件：

1. **可被耳朵验证。**
2. **不需要理解 AI 才能理解。**
3. **不依赖宏大叙事才能成立。**

因此，公共产品证明应优先采用：

`Original -> Listen`

与

`Moodify -> Listen`

用户先听，再决定 Moodify 是否有价值。

## 4.1 核心证明原则

> **If only the sound remains, Moodify must still be worth using.**

如果去掉品牌故事、界面、参数、技术报告和功能列表，只剩声音本身，Moodify 仍然应该值得使用。

这条原则可以保留，并成为 Public Form 的产品验收规则。

---

# 5. 商业意图边界

品牌宪法需要消除商业身份混乱，但不替代未来商业模型决策。

当前冻结以下内容：

### 已冻结

- Moodify 面向最终聆听体验，而不是以企业 API 服务作为第一公共身份。
- 第一公共产品是 Moodify 的播放/聆听体验。
- 技术能力服务于 Play，而不是反过来要求用户理解技术。
- 未来可存在硬件、社区、创作者、数据、订阅、单曲处理或其他商业层，但它们不得在尚未成熟前抢占主品牌定义。
- 公司与产品必须分层：荣景文川是公司，Moodify 是主要公开产品。

### 暂不冻结

- 最终收费方式。
- 是否免费听歌。
- 皮肤经济的最终形态。
- 硬件发布时间。
- Creator 功能是否恢复。
- API 是否未来重新开放。
- 面向 B 端的具体商业模式。

“还没有决定”优于为了显得完整而制造错误确定性。

# 6. 品牌语气

Moodify 的语气应当：

- 安静
- 克制
- 精确
- 有立场
- 少解释
- 不炫技
- 不制造 AI 神话
- 不滥用“革命性”“颠覆”“行业领先”
- 让体验承担证明责任

## 6.1 文案规则

优先：

> Listen. Then Play.

而不是：

> 采用先进人工智能、多模态感知、云原生音频处理技术，为用户提供革命性的智能音频体验。

优先：

> Every voice deserves to be heard.

而不是：

> 我们致力于赋能全球声音内容生态，构建下一代听觉智能基础设施。

# 7. 三站权威分工

## 7.1 `rongjingmusic.com`

**身份：Moodify 主官网 / Product Home**

它是外部世界理解 Moodify 的第一入口。

只需优先回答：

1. Moodify 为什么存在？
2. Moodify 带来了什么听觉体验？
3. 我现在如何听 / 下载 / 进入 Play？

允许出现少量 Evidence，但不得让 Evidence 变成首要产品定义。

## 7.2 `rongjingwenchuan.com`

**身份：荣景文川公司官网 / Company Home**

回答：

- 荣景文川是谁？
- 我们相信什么？
- 我们创造了什么？
- Moodify 与公司是什么关系？
- 我们研究什么？
- 如何联系？

这里不再以 API / ACU / Developer infrastructure 作为公司第一身份。

## 7.3 `rongjinwenchuan.xyz`

**身份：过渡期 Web Player / 历史入口**

短期：

- 只承担进入实际体验的职责。
- 减少品牌解释。
- 必须明显返回 `rongjingmusic.com`。

中期建议：

- 将长期 Web Player 迁移到 `play.rongjingmusic.com`。
- `.xyz` 变为兼容跳转或历史入口。
- 是否最终退役，在 Package 04 执行前由仓库与 DNS 实况决定。

# 10. 视觉原则

本宪法不规定具体 UI，但冻结以下视觉方向：

1. **Sound first.** 页面不是产品功能目录。
2. **Large whitespace.** 留白高于信息密度。
3. **One focal action.** 一屏只允许一个真正的主动作。
4. **No dashboard aesthetics on brand home.** 主官网避免后台、控制台、开发者面板视觉。
5. **Motion must serve listening.** 动效应强化声音与 Play，不作为装饰性炫技。
6. **Same family across all sites.** 三站必须共享 Logo、字体层级、按钮语法、页脚语法、链接语义与黑白关系。

1. **Belief**
2. **Sound**

1. Technology
2. Architecture

4. Features
5. Business story

# 12. 对投资人与外部合作方的最短解释

Moodify 不需要用一整套技术栈才能被解释。

建议第一层表达：

> **Moodify 是一个围绕“听”重新设计的音乐产品。它把复杂的声音理解和处理留在系统内部，把用户体验压缩成一件事：Play。**

如果对方继续问“为什么”，回答：

> **因为我们相信，每一种声音，都值得被世界听见。**

如果继续问“你们怎么做到”，才进入：

> 机器听觉、每曲判断、云端处理、验证、数据与未来硬件链路。

信息应按问题逐层打开，而不是一次倾倒。

# 13. Public Form 决策测试

未来任何公开功能、文案或页面，在上线前回答：

### Test A - Identity

它是否让 Moodify 更像一个明确的聆听产品，还是再次把 Moodify 分裂成多个身份？

### Test B - Comprehension

第一次接触的人能否在 10 秒内知道这里是什么？

### Test C - Audibility

这项价值能否最终通过听觉体验得到证明？

### Test D - Complexity

这是用户必须知道的复杂度，还是我们应该替用户承担的复杂度？

### Test E - Brand

它是否服务：

> Every voice deserves to be heard.

若四项以上无法通过，默认不进入当前公共表面。

---

# 14. 当前阶段唯一目标

Public Form 阶段不是让 Moodify 看起来更大。

目标是：

> **让 Moodify 第一次变得可被准确记住。**

当一个没有见过创始人、没有读过内部文档、没有听过融资路演的人，仅凭产品和网站就能形成近似以下判断时，本阶段才算成功：

> “Moodify 是那个会先理解声音、再让你听的产品。”

或者更简单：

> “同一个声音，我想用 Moodify 听一次。”

这就是品牌开始形成的时刻。
