## 三、分阶段落地路径

### 阶段 0：代理指标 + 暴力搜索（不需要 LLM，1-2 小时）

这是最核心的一步。先让系统能「自己找最优参数」，不依赖 LLM。

```
新增: optimizer/params_to_strengths.py    (~50行)  15参数 → 5个transfer强度
新增: optimizer/proxy_metric.py           (~80行)  EDSR_proxy 计算
新增: optimizer/search.py                 (~150行) 空间定义 + 候选生成 + 评估 + top-K
改动: orchestration/workflow_engine.py    (~50行)  Phase1 后插入搜索步骤
废弃: knowledge/craft_chain_match.py      (标记废弃, 保留文件)
```

验证标准：
```
给定一首 AI 音乐 + 情绪目标
  → 诊断 18 参数
  → 暴力搜索 6500 个候选 (3^8, <1s 代理评估)
  → 选出 top-3
  → 真实 DSP 处理
  → 测量 WHS/EDS
  → 选最优输出

比较: 搜索最优 vs 工艺卡预设的 WHS/EDS
      如果搜索的结果 ≥ 预设的结果 → 阶段 0 成功
```

为什么阶段 0 不需要 LLM：
- 搜索空间可以用规则定义（根据哪些参数偏离正常范围）
- 代理指标是数学公式（不需要推理）
- 候选排序是数值比较（不需要理解）

**LLM 在阶段 1 才介入，增强搜索空间的定义质量。阶段 0 证明「搜索 > 预设」这个核心假设。**

### 阶段 1：LLM 增强搜索（需要 API key，2-3 小时）

```
新增: llm/client.py        (~80行)   LLM API 调用
新增: llm/prompts.py       (~120行)  System Prompt 模板
新增: llm/schemas.py       (~50行)   结构化 I/O
改动: optimizer/search.py  (~30行)   搜索空间定义从规则 → LLM推理
```

LLM 替代的不是参数生成（上一版的错误方向），而是**搜索空间的智能定义**。

```
规则版本: "S1_SubPresence < -3dB → P05 活跃, 范围 [1.0, 3.5]"
LLM 版本: 读完 18 个参数后推理 "哪些参数需要调, 范围多少, 为什么"
```

规则版本先跑通。LLM 版本替换规则版本时，接口不变。

### 阶段 2：记忆闭环（2-3 小时）

```
新增: memory/history.py      (~80行)   处理记录存储
新增: memory/retrieval.py    (~40行)   相似案例检索
新增: memory/calibration.py  (~30行)   代理指标自动校准
```

处理记录结构：

## 四、阶段 0 的伪代码

```python
# optimizer/proxy_metric.py
def compute_edsr_proxy(
    diagnosis: WaveStateDiagnosis,
    params: dict,
    emotion_target: str,
) -> float:
    """预估处理后的 EDSR, 不需要跑真实 DSP。"""
    
    # 1. 诊断 → 5D 向量
    ws_raw = StateTransferEngine.diagnostic_to_process(diagnosis)
    
    # 2. 参数 → transfer 强度 (新增的映射函数)
    strengths = params_to_strengths(params)
    
    # 3. 用 T_EFFECTS 预估处理后的 5D 向量
    chain_types = ["spectrum", "dynamic", "space", "layer", "master"]
    chain_strengths = [strengths[t] for t in chain_types]
    ws_proxy, _ = engine.apply_chain_transfer(
        ws_raw, chain_types, chain_strengths, emotion_target
    )
    
    # 4. 计算到目标情绪理想向量的距离变化
    target = get_ideal_vector(emotion_target)
    dist_before = np.linalg.norm(ws_raw.to_array() - target)
    dist_after = np.linalg.norm(ws_proxy.to_array() - target)
    
    eds_proxy = 100 * (1 - dist_after / max(dist_before, 0.001))
    
    # 5. 加入缺陷消除预估和安全惩罚
    defect_score = estimate_defect_resolution(diagnosis, params)
    safety_penalty = check_safety(ws_proxy, emotion_target)
    
    return eds_proxy * 0.7 + defect_score * 0.3 - safety_penalty


# optimizer/search.py
def search_optimal_params(
    diagnosis: WaveStateDiagnosis,
    emotion_target: str,
    top_k: int = 3,
) -> list[tuple[dict, float]]:
    """在参数空间中搜索最优方案。"""
    
    # 1. 定义搜索空间 (阶段0用手写规则, 阶段1用LLM)
    space = define_search_space(diagnosis, emotion_target)
    
    # 2. 生成候选 (离散化网格)
    candidates = generate_candidates(space)  # ~3000-6500个
    
    # 3. 代理指标快速评估
    scored = []
    for params in candidates:
        score = compute_edsr_proxy(diagnosis, params, emotion_target)
        scored.append((params, score))
    
    # 4. 排序 + top-K
    scored.sort(key=lambda x: x[1], reverse=True)
    return scored[:top_k]
```

关键设计：
- `define_search_space()` 的接口是固定的 (诊断 → 活跃维度 + 范围)
- 阶段 0 用手写规则实现这个函数
- 阶段 1 用 LLM 实现同样的接口
- **接口不变, 实现可替换。这就是元器件思维。**

## 五、最关键的认知

「真理级软件」和「预设管理器」之间的差距，不是 10000 行代码。

**是三个模块：搜索（150行）、LLM集成（250行）、记忆（150行）。**

而且这三个模块可以**渐进式上线**：

```
阶段 0: 搜索 + 代理指标 (不需要 LLM, 但已经比预设强)
阶段 1: + LLM 增强 (搜索空间定义更智能)
阶段 2: + 记忆闭环 (越用越准)
阶段 3: + 联邦进化 (所有用户共同训练)
```

每个阶段的代码量都不大，因为核心引擎（诊断 + DSP + 状态转移）已经在那里了——它们是高质量的传统元器件，不需要重写。

**软件工程师在这里的工作不是「写功能」，而是「连接元器件」：把诊断引擎的输出接到搜索模块的输入，把搜索模块的输出接到 DSP 引擎的输入，把 DSP 引擎的输出接到记忆模块的输入。**
