## 0. 前置思考：什么是「面向 AI 原生文明的软件」

### 0.1 三代软件范式

| 代际 | 用户 | 交互模式 | 软件形态 | 核心关注 |
|------|------|---------|---------|---------|
| 第一代 | 人 | GUI / 命令行 | 桌面应用 | 满足用户需求 |
| 第二代 | 人 + 人 | Web + 移动 | 云服务 | 用户留存、增长 |
| 第三代 | 人 + AI | API + GUI 并行 | **能力单元** | 可组合、可发现、可验证 |

Moodify 定位在第三代：**既有人用的 GUI，也有 AI 可调用的 API，两者共享同一个引擎内核。**

### 0.2 第三代软件的设计原则

**原则 1：能力优先于界面。**
GUI 是 API 的消费者，不是 API 的所有者。任何功能必须先有 API，GUI 只是 API 的一个视图。

**原则 2：自我描述。**
AI 调用一个能力时，不需要读人类文档。OpenAPI spec、类型标注、参数约束全部机器可读。

**原则 3：确定性。**
给定相同输入，产生相同输出。AI 调用方需要能预测行为，不能依赖隐藏状态。

**原则 4：可组合。**
一个能力的输出格式是下一个能力能直接消费的输入格式。标准格式（WAV、JSON）优先于专有格式。

**原则 5：反馈闭环。**
处理结果可被同一系统再次诊断，形成「处理→诊断→比较」的控制论环路。这正是 Moodify 的 WHS/EDS 评分体系已经在做的。

### 0.3 这些原则如何映射到 Moodify

```
AI 音乐生成工具 (Suno/Udio)
        │
        │ 原始音频 (.wav)
        ▼
┌───────────────────────────────┐
│        Moodify 引擎            │
│                               │
│  诊断 (18参数)                  │
│    → 缺陷分类                  │
│    → 工艺匹配                  │
│    → DSP 处理                  │
│    → 质量验证                  │
│                               │
│  输出: 处理音频 + 指标 JSON     │
└──────────┬────────────────────┘
           │
           │ 处理后的音频 + WHS/EDS/风险报告
           ▼
    ┌──────┴──────┐
    │             │
    ▼             ▼
  人类           AI Agent
  (GUI 试听)     (自动判断是否达标，
                 未达标则换工艺卡重试，
                 或反馈给 AI 生成工具
                 调整生成参数)
```

这不再是一个「上传→处理→下载」的单向工具，而是一个**控制论回路中的信号处理节点**。

## 1. 双轨方案

### 1.1 轨道划分逻辑

两条轨道按**关注点**划分，不按技术栈划分：

| | 轨道 A：引擎合并与校准 | 轨道 B：接口层与交付壳 |
|---|---|---|
| **核心问题** | 两个 Python 栈合并，生产参数回灌 | API 协议统一，Electron 壳打通 |
| **输入** | `python/` 栈 + `07Music/tools` + 核心包 | 核心包当前 API + 前端当前代码 |
| **输出** | 统一的 Python 包，模块化诊断，校准后的工艺卡 | 可工作的桌面应用 + 自描述的 API |
| **技术栈** | Python | TypeScript + Python API 层 |
| **对轨道 B 的依赖** | 无。独立运行，CLI 验证 | API 协议定义（共享文档），不依赖轨道 A 代码 |
| **可并行性** | 从第 0 分钟开始并行 | 从第 0 分钟开始并行 |

两条轨道的**唯一交汇点**是一份共享的 API 协议文档（OpenAPI 3.0 spec）。轨道 A 实现协议，轨道 B 消费协议。这份协议两边的 AI 各自读取，不需要等待对方。

### 1.2 轨道 A：引擎合并与校准

**目标**：一个干净的 Python 包，CLI 跑通端到端处理，所有模块化提取器就位。

**A1. 模块化重构 diagnosis/（吸收 EWE 栈）**

当前核心包的 `engine.py` 是 682 行的单体类。EWE 栈的 `diagnosis/` 有 5 个独立提取器文件。

```python
# 当前（单体）
class DiagnosisEngine:
    def diagnose(self, path):
        # 682行，所有计算内联
        ...

# 目标（模块化）
class DiagnosisEngine:
    def __init__(self):
        self.spectrum = SpectrumExtractor()    # S1-S5
        self.dynamics = DynamicsExtractor()    # D1-D4
        self.space = SpaceExtractor()          # SP1-SP4
        self.layers = LayersExtractor()        # L1-L4
        self.emotion = EmotionExtractor()      # E1-E4

    def diagnose(self, path):
        # 编排5个提取器，组装结果
        ...
```

每个提取器是纯函数：`audio → Dict[str, float]`。无副作用、无全局状态。

**为什么模块化更好（系统论视角）**：
- 每个提取器是独立子系统，可单独测试、单独替换
- 新增诊断参数只改对应提取器，不影响其他四个维度
- 耦合度从 O(n²) 降到 O(n)

**A2. 吸收 EWE 独特评分器**

EWE 栈有四个核心包没有的评分器：

| 评分器 | 缩写 | 测量什么 | 合并位置 |
|--------|------|---------|---------|
| 塑料语音指数 | PVI | AI 人声的不自然程度 | `health_scorer.py` 新增方法 |
| 身体感知评分 | BPS | 低频对身体的物理冲击感 | `health_scorer.py` 新增方法 |
| 空间真实感 | SRA | 声场是否像真实空间 | `health_scorer.py` 新增方法 |
| 听力疲劳风险 | LFR | 长时间聆听的疲劳程度 | 合并到现有 `risk_model.py` |

这些评分器不改变核心架构，只是给 WHS 总分增加了子维度。如同体检报告：血常规 5 项变成 9 项，报告格式不变。

**A3. 07Music 生产参数回灌校准**

生产脚本 `wavefield_enrichment_v1.py` 的 `derive_settings()` 函数包含真实数据校准的阈值断点。例如：

```python
# 诊断到处理的映射（来自真实专辑处理经验）
if mud_250_500 > -5.2:    mud_cut = -2.2 dB   # 泥声很重
elif mud_250_500 > -7.5:  mud_cut = -1.7 dB   # 泥声中等
elif mud_250_500 > -8.8:  mud_cut = -1.35 dB  # 泥声较轻
else:                      mud_cut = -1.0 dB   # 泥声正常
```

这些阈值直接校准 `craft_chain_match.py` 的匹配算法，让工艺卡推荐的参数更贴近真实听觉判断。

**这不是改代码逻辑，是改数据校准值。** 生产参数是「听觉ground truth」。

**A4. 端到端验证**

用 `07Music/albums/` 里的真实 Suno 曲目跑 `moodify process <file> <emotion>`，验证：
1. 六阶段流水线不报错
2. 处理后的 WHS > 处理前的 WHS
3. EDS > 0（情绪距离缩短）
4. 输出文件可正常播放

这是整个轨道 A 的验收标准。不通过，轨道 A 不算完成。

### 1.3 轨道 B：接口层与交付壳

**目标**：一个双击就能启动的桌面应用，完整的 GUI 工作流，API 自描述。

**B1. API 协议统一**

两份代码各自读到同一份 OpenAPI spec（`docs/engineering/api-v1.yaml`），作为唯一的真相来源：

```yaml
# 协议定义（共享，不依赖任何代码）
paths:
  /api/v1/sessions:
    post:
      summary: 创建会话并上传音频
      requestBody:
        content:
          multipart/form-data:
            schema:
              type: object
              properties:
                file:
                  type: string
                  format: binary
      responses:
        '201':
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Session'

  /api/v1/sessions/{session_id}/diagnose:
    post:
      summary: 运行18参数诊断
      responses:
        '200':
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/DiagnosisResult'
```

- 轨道 A 的 AI 读取这份 spec，实现对应的 FastAPI 路由
- 轨道 B 的 AI 读取这份 spec，实现对应的 TypeScript API client
- 两边读到的是同一份文档，不会出现「前端期望 `/sessions`，后端实现 `/analyze`」的对不齐

**这份 spec 文件是两条轨道的唯一协调点。** 两个 AI 读同一份，各自工作，不需要互相等待。

**B2. TypeScript API 客户端重新生成**

当前 `api/client.ts` 手动编写，约 100 行。改为从 OpenAPI spec 自动生成：

```bash
npx openapi-typescript ./docs/engineering/api-v1.yaml -o ./src/api/schema.d.ts
```

生成的类型文件让 TypeScript 编译器在编译期就能检查 API 调用是否正确——这就是 **TypeScript 更适配 AI 的具体机制**：AI 生成的 TypeScript 代码有编译期类型检查作为安全网，Python 的动态类型没有这个保护。

**B3. 前端状态机精简**

当前 `App.tsx` 的状态机 6 个阶段与核心引擎的六阶段不对齐。对齐后：

| 前端阶段 | 用户看到 | API 调用 | 后端做什么 |
|---------|---------|---------|-----------|
| `upload` | 拖拽区 | POST /sessions | 存文件，返回 session_id |
| `diagnosing` | 加载动画 | POST /sessions/{id}/diagnose | 18参数+缺陷+WHS+工艺卡匹配 |
| `diagnosed` | 五维雷达图 + 工艺卡列表 | — | — |
| `processing` | 进度条 | POST /sessions/{id}/process | 六阶段流水线 |
| `completed` | 前后对比 + 下载 | GET /sessions/{id}/result | 返回处理后的音频+指标 |

**B4. Electron 编译与打包**

```bash
cd moodify-pulse
npm run build:electron    # 编译 Electron main.ts → dist-electron/
npm run electron:pack     # 打包 NSIS 安装器
```

这是轨道 B 的验收标准：产生一个 `.exe` 安装包，安装后双击启动，完整走通「上传→诊断→处理→下载」流程。

### 1.4 两条轨道的独立性验证

| 场景 | 轨道 A 是否受影响 | 轨道 B 是否受影响 |
|------|------------------|------------------|
| A 重构 engine.py | — | 不影响。API 协议不变，B 只依赖协议 |
| B 修改前端组件 | 不影响。前端是 API 消费者 | — |
| A 新增评分器 PVI | — | 前端需要展示新指标（协议新增字段） |
| B 修改 Electron 打包配置 | 不影响 | — |
| API 协议新增端点 | 需要实现 | 需要消费 |

**关键约束**：API 协议的修改需要双方同步。但只要协议文件先行，两个 AI 各自读取新协议即可，不需要互相等待。

## 2. 控制论视角：Moodify 作为反馈控制系统

### 2.1 现有的控制回路

```
设定点 (Emotion Target)
    │
    ▼
┌──────────────┐    音频     ┌──────────────┐
│  诊断器       │ ◄──────── │  原始音频     │
│  (传感器)     │            │  (被控对象)   │
└──────┬───────┘            └──────────────┘
       │
       │ 18参数 + 缺陷
       ▼
┌──────────────┐
│  比较器       │ ← 情绪目标 (设定点)
│  CraftMatch  │
└──────┬───────┘
       │
       │ 工艺卡 + 15参数
       ▼
┌──────────────┐
│  执行器       │
│  DSP Chain   │
└──────┬───────┘
       │
       │ 处理后音频
       ▼
┌──────────────┐            ┌──────────────┐
│  诊断器       │ ────────► │  比较器       │
│  (再诊断)     │  新18参数  │  (EDS计算)    │
└──────────────┘            └──────┬───────┘
                                   │
                                   │ EDS < 阈值?
                                   ▼
                            ┌──────────────┐
                            │  反馈决策     │
                            │  换工艺卡/    │
                            │  调整参数/    │
                            │  接受输出     │
                            └──────────────┘
```

这就是一个标准的 **PID 控制器**（比例-积分-微分控制器），只不过执行器不是电机而是 DSP 效果链：

- **P（比例）**：缺陷严重度 → 参数调整幅度
- **I（积分）**：WHS 总分 → 整体处理强度
- **D（微分）**：处理前后变化量 → 过度处理风险

### 2.2 未来可以强化控制论特性

当前系统只有**一次处理**，没有自动迭代。但架构已经支持：

```python
# 伪代码：未来的自动迭代
def auto_process(audio, target_emotion, max_iterations=3):
    for i in range(max_iterations):
        diagnosis = engine.diagnose(audio)
        craft = matcher.match(diagnosis, target_emotion)
        processed = chain.process(audio, craft.params)
        eds = scorer.compute_eds(diagnosis, diagnose(processed), target_emotion)

        if eds >= 65:  # 达标
            return processed
        elif eds_improvement < 5:  # 边际收益递减，停止
            return processed
        audio = processed  # 反馈循环
    return processed
```

这不需要架构改动——诊断器和处理器的纯函数设计天然支持迭代调用。

## 3. 系统论视角：模块边界与熵

### 3.1 当前系统的熵

软件系统的「熵」体现在：
- **代码重复**：`python/` 和核心包实现同一规范，两份代码独立演进，修改一处另一处不知道
- **接口不对齐**：前端期望 session API，后端提供 stateless API
- **硬编码值散落**：EQ 参数同时出现在核心包工艺卡和 07Music 脚本中，哪份是真相？

**低熵系统 = 每个概念只有一种表达。**

### 3.2 降熵措施

| 当前高熵状态 | 降熵操作 | 轨道 |
|-------------|---------|------|
| 两套诊断引擎 | 合并到模块化提取器 | A |
| 两套 API 协议 | 一份 OpenAPI spec | B |
| 两份 DSP 参数 | 生产参数回灌，工艺卡数据为单一真相源 | A |
| 两套评分器 | PVI/BPS/SRA/LFR 吸收到核心包 | A |
| 前端手动写 API client | 从 spec 自动生成类型 | B |

### 3.3 模块间耦合度

目标耦合度：

```
API 层 ──依赖──► 编排层 ──依赖──► 诊断层
  │                │                 │
  │                │                 ├── 频谱提取器（无依赖）
  │                │                 ├── 动态提取器（无依赖）
  │                │                 ├── 空间提取器（无依赖）
  │                │                 ├── 层级提取器（无依赖）
  │                │                 └── 情绪提取器（无依赖）
  │                │
  │                ├── 处理层
  │                │   ├── pedalboard_chain（依赖 pedalboard）
  │                │   └── operators（依赖 numpy/scipy）
  │                │
  │                └── 知识层（纯数据，无代码依赖）
  │                    ├── emotion_targets
  │                    ├── craft_chains
  │                    └── risk_model
  │
  └── 前端（仅依赖 API 协议，不依赖 Python 代码）
```

箭头方向 = 依赖方向。**没有循环依赖。** 这是健康架构的标志。

## 4. 可执行的双轨计划

### 4.1 共享第一步（两条轨道开始前必须完成）

**P0：编写 API 协议文档**

创建 `docs/engineering/api-v1.yaml`（OpenAPI 3.0 格式），定义所有端点、请求体、响应体、数据模型。

这份文档大约 200 行 YAML，两个 AI 在开始工作前各自读取一次。后续改动通过更新这份文档同步。

### 4.2 轨道 A 执行序列

| 步骤 | 内容 | 验收方式 |
|------|------|---------|
| A-1 | 读 API 协议文档 | — |
| A-2 | 将 `python/ewe/diagnosis/` 的 5 个提取器整合到核心包 | 每个提取器单独测试通过 |
| A-3 | 重构 `engine.py`：用提取器替换内联计算 | 诊断结果与重构前一致（误差 < 1%） |
| A-4 | 吸收 PVI/BPS/SRA 评分器到 `health_scorer.py` | 新增字段在 WHS 计算中生效 |
| A-5 | 07Music 生产参数回灌到 `craft_chains.py` | 每种情绪的 rec 值对比生产脚本偏差 < 0.5dB |
| A-6 | 用 enrich 阈值校准 `craft_chain_match.py` | 匹配结果与 enrich 推荐偏差 < 1 个工艺卡 rank |
| A-7 | 按 API 协议实现 session 端点 | curl 测试全部 7 个端点通过 |
| A-8 | 端到端：真实音频 `moodify process` 跑通 | WHS_after > WHS_before, 输出可播放 |

### 4.3 轨道 B 执行序列

| 步骤 | 内容 | 验收方式 |
|------|------|---------|
| B-1 | 读 API 协议文档 | — |
| B-2 | 从 spec 生成 TypeScript 类型 | 编译无错误 |
| B-3 | 重写 `api/client.ts`，匹配 session API | 所有端点类型正确 |
| B-4 | 精简 `App.tsx` 状态机为 5 阶段 | 每个阶段 UI 可渲染 |
| B-5 | 重构 `DiagnosisDashboard`，展示模块化诊断结果 | 五维雷达图 + 缺陷表格 + 工艺卡列表 |
| B-6 | 编译 Electron 主进程 | `dist-electron/` 目录生成 |
| B-7 | 完整打包 NSIS 安装器 | 安装后可启动，Python sidecar 正常运行 |
| B-8 | 端到端：GUI 走通上传→诊断→处理→下载 | 与轨道 A-8 一致的结果，但通过 GUI 操作 |

### 4.4 为什么可以并行

两条轨道的唯一交汇是 API 协议文档。轨道 A 实现它（Python），轨道 B 消费它（TypeScript）。除此之外：

- 轨道 A 的引擎重构不需要 GUI
- 轨道 B 的 GUI 可以用 mock 数据开发（mock 的 JSON 结构来自 API 协议）
- 两条轨道都完成后，联调只需要让前端指向真实的 Python 后端

这跟硬件开发中「PCB 设计和机壳设计并行，中间靠接口定义书协调」是同一个逻辑。


## 6. 关键原则总结

1. **先写协议，再写代码。** API 协议文档是两条轨道的唯一协调点。200 行 YAML 节省 2000 行返工。

2. **引擎是纯函数。** 音频输入 → 诊断 → 工艺匹配 → DSP 处理 → 音频输出 + 指标。无副作用，无全局状态。这既是控制论要求（可重复测量），也是 AI 可调用性的基础（确定性）。

3. **GUI 是 API 的一个视图。** 前端不包含任何音频处理逻辑，只是 API 的视觉呈现。这保证人类操作和 AI 调用走的是同一条代码路径。

4. **生产参数是 ground truth。** 07Music 的实测值优先级高于理论推导值。工艺卡数据从生产脚本校准，而不是从公式推导。

5. **两个 Python 栈合并为一个是降熵动作。** 每个概念只应该有一种代码表达。

6. **TypeScript 的类型系统是 AI 代码生成的安全网。** 从 OpenAPI spec 生成的类型定义让编译器在 AI 写出不对齐的代码时立即报错。
