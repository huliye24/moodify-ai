# RAG + API 工程化推理：学习不训练的架构实现

**时间**: 2026-05-28
**触发**: 云景台的 DeepSeek API + RAG 方案文档
**问题**: SPEC-002 已经覆盖了搜索+代理+记忆, 但云景台的方案揭示了一个更根本的架构模式——RAG 不是记忆模块的附加功能, 而是整个推理流程的前置步骤。需要重新推理工程实现。

---

## 零、SPEC-002 与云景台方案的差异

### 0.1 SPEC-002 的流程

```
Phase 1: 诊断
Phase 1.5: [LLM 定义搜索空间] → [网格搜索 + 代理评估] → top-3
Phase 3-6: DSP → 选最优
(事后) → 写入 history.jsonl
```

记忆是**事后记录**。历史数据用于代理指标的偏差校准, 是辅助角色。

### 0.2 云景台方案的流程

```
Phase 1: 诊断
Phase 1.3: [检索相似案例] → top-5 历史案例
Phase 1.5: [Prompt 组装: 系统 + 诊断 + 案例 + 意图] → [LLM 推理] → 参数
Phase 3-6: DSP → 输出
(事后) → 写入知识库
```

记忆是**事前检索**。历史数据进入 LLM 的上下文窗口, 直接参与推理。这是根本性的架构差异。

### 0.3 差异的本质

| | SPEC-002 | 云景台方案 |
|---|---|---|
| 记忆的时机 | 事后 (post-hoc calibration) | 事前 (pre-prompt retrieval) |
| 记忆的作用 | 修正代理指标的数值偏差 | 直接进入 LLM 推理上下文 |
| LLM 知道历史吗 | 不知道 (零样本推理) | 知道 (few-shot with real cases) |
| 离线降级 | 回退到手写规则 | 回退到加权平均案例参数 |
| 越用越好吗 | 代理指标校准变好 | LLM 推理 + 检索都变好 |

**SPEC-002 的架构是"LLM 猜参数 + 搜索验证"。云景台的架构是"检索告诉 LLM 历史上怎么做, LLM 结合当前情况推理"。后者更接近人类专家的工作方式——参考类似案例, 做出判断。**

## 一、修正后的架构

### 1.1 完整流程

```
用户输入: 音频文件 + 意图描述
    │
    ▼
Phase 1: 诊断引擎 (本地, 确定, < 3s)
    → WaveStateDiagnosis (18参数)
    → defects (缺陷列表)
    → diagnosis_vector (18D 归一化, 用于检索)
    │
    ▼
Phase 1.3: 案例检索 (本地, < 100ms)
    → ProcessingHistory.find_similar(diagnosis_vector, top_k=5)
    → 返回 5 个最相似案例 (诊断+参数+结果+反馈)
    │
    ▼
Phase 1.5: 推理 (分支)
    │
    ├─ [在线] DeepSeek API
    │    prompt = assemble_prompt(
    │        system=EWE_PROMPT,
    │        diagnosis=当前诊断,
    │        cases=top_5_相似案例,    ← 记忆进入上下文
    │        intent=用户意图,
    │    )
    │    → LLM 推理 → 15 参数 + 解释 + 风险
    │
    ├─ [离线] 统计聚合
    │    params = weighted_average(
    │        cases=top_5_相似案例,
    │        weights=相似度,
    │        default=工艺卡 rec 值,
    │    )
    │    → 15 参数
    │
    └─ [无案例] 预设回退
         params = get_recommended_params(emotion_code)
         → 15 参数
    │
    ▼
Phase 3: DSP 执行 (本地, 确定, < 3s)
    → 处理后的音频
    │
    ▼
Phase 4-6: 空间 + 再合成 + 母带
    → 最终输出
    │
    ▼
后处理: 测量 + 记录
    → WHS_before/after, EDS
    → ProcessingRecord 写入 knowledge_base.jsonl
```

### 1.2 和 SPEC-002 的关键区别

SPEC-002 中, LLM 只做一件事: 定义搜索空间。参数本身由网格搜索 + 代理指标决定。

云景台方案中, **LLM 直接输出参数**。但不是零样本猜测——它看到了 5 个高度相似的案例, 每个案例都有真实的诊断数据、使用的参数、用户反馈。

这引入了一个问题: **LLM 直接输出参数可靠吗?**

SPEC-002 的"参数搜索"机制仍然有价值——它可以作为 LLM 输出的**验证层**:

```
LLM 输出参数 → [可选] 代理指标验证 → 如果 EDSR_proxy < 阈值, 启动网格搜索微调
```

但如果 LLM 看到的 5 个案例足够相似 (相似度 > 0.85), 它的输出应该已经非常可靠, 不需要搜索验证。只有当案例稀缺或相似度低时, 才需要搜索作为补充。

### 1.3 三层决策架构

```
Layer 1: 案例充足 (top-1 相似度 > 0.85)
    → LLM 直接输出参数 (有高度相似的先例)
    → 不启动搜索
    → 延迟: LLM 推理 ~3s

Layer 2: 案例一般 (top-1 相似度 0.5-0.85)
    → LLM 输出参数 + 代理指标验证
    → 如 EDSR_proxy < 预设值, 启动搜索微调
    → 延迟: LLM ~3s + 搜索 ~1s

Layer 3: 无案例 (相似度 < 0.5, 或知识库为空)
    → 启动完整搜索 (阶段A的网格搜索)
    → 不使用 LLM (零样本推理准确性不如搜索)
    → 延迟: 搜索 ~1s
```

这个分层策略的核心逻辑: **案例越丰富, LLM 的推理越可信, 需要的搜索越少。案例越少, 越依赖搜索。**

## 二、Prompt 工程: 让案例进入 LLM 上下文

### 2.1 Prompt 组装函数

```python
def assemble_processing_prompt(
    diagnosis: WaveStateDiagnosis,
    defects: list[Defect],
    emotion_code: str,
    emotion_name: str,
    user_intent: str,
    similar_cases: list[tuple[ProcessingRecord, float]],
) -> str:
    """组装发给 DeepSeek 的完整 prompt。
    
    结构:
      1. 当前诊断 (18参数 + 缺陷)
      2. 目标情绪
      3. 用户意图
      4. 相似案例 (最多5个, 包含诊断+参数+结果+反馈)
      5. 输出格式要求
    """
```

### 2.2 案例在 prompt 中的呈现

每个案例应该包含足够信息让 LLM 做出推理, 但不应该包含冗余信息:

```
### 案例 N (相似度: 0.92, 用户满意度: ✓)

诊断关键指标:
  SubPresence=-5.8dB, BassWarmth=-3.5dB, MidClarity=0.68
  AirBand=-15.2dB, LRA=8.1LU, Correlation=0.70
  VocalSNR=13.1dB, BassClarity=0.20, FatigueRisk=0.25

使用的参数:
  P02_vocal_presence_gain=+2.8dB
  P05_proximity_low_gain=+2.5dB
  P06_compression_ratio=2.0:1
  P11_reverb_dry_wet=0.20
  P15_high_shelf_gain=+1.5dB

处理结果:
  WHS: 72 → 81 (+9)
  用户反馈: 满意 — "人声很贴耳, 温暖但不闷"
```

关键设计:
- **不展示全部 18 参数** — 只展示与当前缺陷相关的关键指标
- **不展示全部 15 参数** — 只展示实际调整了的参数
- **包含用户反馈原文** — LLM 能从自然语言反馈中提取比数值更多的信息

### 2.3 离线 prompt vs 在线 prompt

在线模式的 prompt 目标: **让 LLM 生成精确参数。**

离线模式没有 LLM。替代方案不是"简化 prompt", 而是**完全不同的算法**:

```python
def offline_param_aggregation(
    similar_cases: list[tuple[ProcessingRecord, float]],
    emotion_code: str,
) -> dict[str, float]:
    """加权平均: 越相似的案例权重越高。"""
    if not similar_cases:
        return get_recommended_params(emotion_code)
    
    total_weight = sum(sim for _, sim in similar_cases)
    result = {}
    
    for param_key in PARAM_KEYS_15:
        weighted_sum = 0.0
        for case, sim in similar_cases:
            if case.edsr_real is not None and case.edsr_real < 0:
                continue  # 跳过用户不满意的案例
            weighted_sum += case.params.get(param_key, 0.0) * sim
        result[param_key] = weighted_sum / max(total_weight, 1e-8)
    
    return result
```

这个函数不依赖任何外部 API。复杂度 O(K × 15), K ≤ 5。延迟 < 1ms。

## 三、隐私模型

### 3.1 什么数据离开用户机器

```
离开机器的:
  - 18 个诊断参数值 (浮点数, 如 -6.2, 0.72, 8.3)
  - 缺陷列表 (参数名 + 严重度)
  - 用户意图文本 (如 "像深夜的温暖拥抱")
  - 5 个相似案例的诊断摘要 + 参数 (匿名化的历史数据)

不离开机器的:
  - 音频文件 (原始和处理后)
  - 用户身份信息
  - 完整的历史记录 (只有摘要进入 prompt)
```

18 个诊断数字无法重构音频。从 -6.2dB SubPresence 和 0.72 MidClarity 不能重建声音波形。这是单向的、不可逆的特征提取。

### 3.2 API Key 模型

两种部署模式:

**模式 A: Moodify 自带 Key**
```
优点: 用户零配置
缺点: Moodify 承担 API 费用; Key 在客户端有泄露风险
适用: 付费产品 (API 费用包含在产品价格中)
```

**模式 B: 用户自带 Key (BYOK)**
```
优点: Moodify 零成本; 用户对自己的 API 使用有完全控制
缺点: 用户需要注册 DeepSeek 账号并获取 Key
适用: 免费/开源产品
```

推荐模式: **B (BYOK) 作为默认, A 作为付费选项。** 在设置界面提供一个输入框让用户填入 API Key, 并给出注册链接。Moodify 也可以提供内置 Key 的 Pro 版本。

## 四、检索质量与案例生命周期

### 4.1 冷启动: 没有案例时

```
知识库为空:
  - 在线: LLM 零样本推理 (没有案例上下文, 只有诊断数据)
  - 离线: 回退到 8 个工艺卡预设
```

零样本推理的质量已经在之前的推理中确认——DeepSeek 读取 18 参数 + 用户意图, 能够生成合理的参数。冷启动不是问题。

### 4.2 案例的时效性

```
问题: 3 个月前的案例还有参考价值吗?

答案: 取决于诊断向量的分布是否发生了变化。
      诊断引擎是确定性的, 不会变。
      但如果用户群体的音乐类型发生了变化
      (比如从钢琴曲转向电子乐), 旧案例的参考价值下降。

解决: 检索时加时间衰减权重。
      similarity_final = similarity_cosine * exp(-age_days / 180)
      即: 半衰期 180 天。6 个月前的案例权重减半。
```

### 4.3 案例质量过滤

并非所有案例都值得参考:

```
过滤条件:
  1. edsr_real is not None 且 < 0 → 排除 (用户明确不满意)
  2. eds < 40 → 降低权重 (处理效果差)
  3. 参数异常 (超出安全边界) → 排除
  4. 时间超过 365 天 → 排除
```

## 六、更新后的 System Prompt 设计

核心变化: LLM 不再输出"搜索空间", 而是**看到相似案例后, 直接输出推荐参数**。

```
你是 Moodify 情绪波场显影引擎的推理核心。

输入:
  - 当前歌曲的 18 参数诊断数据 + 缺陷列表
  - 目标情绪
  - 用户意图 (自然语言)
  - 历史上 5 个相似案例 (诊断 + 使用的参数 + 处理结果 + 用户反馈)

输出: JSON
{
  "reasoning": "基于诊断和相似案例的推理过程",
  "parameters": { 15 个参数的推荐值 },
  "risk_assessment": { level, warnings, mitigations },
  "confidence": 0.0-1.0,
  "reference_cases": [引用哪些案例影响了推荐]
}

规则:
  - 相似度高 (>0.85) 的案例参数应作为主要参考
  - 用户不满意的案例 (反馈中包含"太亮""太闷""太远"等) 应反向参考
  - 如果案例中的参数与当前诊断有显著差异, 需要调整而非照搬
  - 所有参数必须在安全范围内
```

## 七、重新审视: 搜索还有必要吗

如果 LLM + RAG 能直接输出高质量参数, 还需要网格搜索吗?

### 7.1 搜索的价值在退化

```
案例充足 (相似度 > 0.85):
  LLM 直接输出的参数已经非常好
  搜索 5000 个候选 → 找到的和 LLM 输出的差异 < 5%
  → 搜索的边际价值很低

案例一般 (相似度 0.5-0.85):
  LLM 输出参数需要验证
  代理指标验证 → 如果不达标, 在 LLM 参数附近做局部搜索
  → 搜索缩小为局部微调, 不需要全局搜索

无案例:
  LLM 零样本推理质量不确定
  → 搜索仍然是必要的 (阶段A的逻辑)
```

### 7.2 结论: 搜索从主决策者降级为安全网

```
SPEC-002: 搜索是主决策者, LLM 辅助定义搜索空间

云景台方案: LLM 是主决策者, 搜索在不确定时才启动

修改: search.py 保留, 但 workflow_engine 改为:
  if confidence > 0.8:
      params = llm_params  # 直接使用 LLM 输出
  elif confidence > 0.5:
      params = local_search(llm_params, radius=0.2)  # LLM 参数附近微调
  else:
      params = global_search()  # 完整搜索
```

## 八、一句话总结

**云景台方案修正了 SPEC-002 的一个根本错误: 记忆应该进入 LLM 的上下文, 而不是只做事后校准。RAG + API = 学习不训练——模型权重不变, 但每次请求的 prompt 越来越好。工程上只需要新增 prompt_assembler.py (~80行) + offline_fallback.py (~40行), 其余 SPEC-002 的模块全部保留, 角色重新分配。**
