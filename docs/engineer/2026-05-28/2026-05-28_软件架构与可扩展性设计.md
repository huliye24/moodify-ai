### 2.2 为什么是两层而不是三层

删掉 Go 后端（backend/）的理由：

1. **Go 没有实际功能**：`main.go` 是 50 行占位符，不提供任何核心包没有的能力
2. **多余的网络跳**：Python API → Go 桥接 → 前端，增加延迟和故障点
3. **两种语言够了**：Python（引擎）+ TypeScript（UI）已覆盖所有需求

### 2.3 两层之间的协议

前端与后端通过 HTTP JSON 通信，所有接口定义在 TypeScript `api/client.ts` 和 Python `api/main.py` 两侧各一份。

**当前问题**：前端期望 session 模式（upload → diagnose → process 分步），后端是 stateless 模式（analyze 和 process 各自独立接受文件上传）。需要统一。

## 3. 可扩展性设计

### 3.1 新增情绪

当前 8 种情绪：GA / SE / UD / LW / HL / DR / WL / CN。

新增一种情绪的代价：**3 个文件，约 80 行数据，不需要写任何算法代码。**

| 文件 | 新增内容 | 行数 |
|------|---------|------|
| `knowledge/emotion_targets.py` | 情绪目标向量、安全区间、理想向量、混响风格 | ~40 |
| `knowledge/craft_chains.py` | 15参数 min/rec/max 三元组 + 风险警告 + 处理步骤 | ~30 |
| `knowledge/craft_chain_match.py` | 只需确认别名表中有对应映射 | ~2 |

**这就是可扩展性好的标志：加数据 ≠ 改代码。**

### 3.2 新增诊断参数

当前 18 个诊断参数：频谱5 + 动态4 + 空间4 + 层级4 + 情绪4。

新增一个参数的代价：

| 层面 | 改动 |
|------|------|
| `data_types.py` | 在对应 DimensionDiagnosis 类中加一个字段 |
| `diagnosis/engine.py` | 在对应维度方法中加计算逻辑 |
| `diagnosis/defect_classifier.py` | 加 4 个阈值（lo_low/lo_high/hi_low/hi_high）|
| `knowledge/craft_chain_match.py` | 在 DiagnosticMarkers 中注册 |

**代价约 30-50 行。** 如果采用 EWE 栈的模块化提取器架构（每个维度一个独立文件），代价可降至 15-25 行。

### 3.3 新增 DSP 参数

当前 15 个工艺参数：人声临场感3 + 低频温暖感2 + 压缩4 + 混响3 + 谐波1 + 高频2。

新增一个参数需要改：

| 文件 | 改动 |
|------|------|
| `data_types.py` | CraftCardV2 的参数字典加键 |
| `knowledge/craft_chains.py` | 8 种情绪各加一组 min/rec/max |
| `processing/pedalboard_chain.py` | `build_chain()` 中加对应的 pedalboard 效果器 |

**代价约 30-50 行。** 注意：8 种情绪的数据需要专业知识来填，不是纯工程问题。

### 3.4 新增处理阶段

当前六阶段流水线：诊断 → 分离 → 增强 → 空间 → 再合成 → 母带。

新增一个阶段（比如"去齿音"独立为单独阶段）：

| 文件 | 改动 |
|------|------|
| `orchestration/workflow_engine.py` | `process()` 方法中插入新 Phase |
| `processing/` | 新阶段的 DSP 实现 |

**代价：编排层约 30 行 + 处理层约 50-100 行。** 设计上六阶段是合理上限——超过六个阶段，编排代码的可读性会显著下降。

### 3.5 插件化（远期架构）

当前的工艺卡系统已经天然支撑了插件化概念：

```
CraftCardV2 {
    id: str              # 唯一标识
    target_emotion: str  # 目标情绪
    params: dict         # 15参数 min/rec/max 字典
    processing_steps: [] # 处理步骤描述
    risk_warnings: []    # 风险警告
}
```

未来如果需要支持用户自定义工艺卡，只需：

1. 把 `CRAFT_CHAINS_15PARAMS` 从 Python 字典改为 JSON/YAML 文件
2. 加一个 `POST /api/v1/craft_cards` 端点接受自定义卡片
3. 前端加一个工艺卡编辑器

**核心引擎不需要任何改动。** 工艺卡和引擎之间通过 15 参数字典解耦。

## 5. API 协议统一方案

### 5.1 最终 API 设计

```
POST   /api/v1/sessions                    # 创建会话，上传音频
GET    /api/v1/sessions/{id}               # 获取会话状态
POST   /api/v1/sessions/{id}/diagnose      # 运行诊断（18参数+缺陷+WHS）
GET    /api/v1/sessions/{id}/crafts        # 获取工艺卡匹配结果
POST   /api/v1/sessions/{id}/process       # 用指定工艺卡处理
GET    /api/v1/sessions/{id}/result        # 获取处理结果（WAV+指标）
GET    /api/v1/emotions                    # 列出所有情绪
GET    /health                             # 健康检查
```

会话保存在内存字典中（`dict[session_id, Session]`），不依赖数据库。音频用临时文件存储，会话关闭时清理。

### 5.2 TypeScript 侧类型定义

```typescript
interface SessionState {
  id: string;
  status: 'uploaded' | 'diagnosing' | 'diagnosed' | 'processing' | 'completed';
  waveState?: WaveStateDiagnosis;   // 18参数诊断结果
  defects?: Defect[];               // 缺陷列表
  whs?: number;                     // 波场健康评分
  craftMatches?: CraftMatch[];      // 工艺卡匹配
  result?: ProcessResult;           // 处理结果
}
```

TypeScript 的类型系统可以让 AI 在生成前端代码时，在编译期就发现与 Python API 的不对齐——这就是"TS 更适配 AI"的具体体现。

## 6. 关键原则

1. **Python 管音频，TypeScript 管界面。** 不存在全栈语言之争。
2. **工艺卡数据驱动。** 加情绪不改算法，改参数不改架构。
3. **生产参数是校准源。** 07Music 的实测值比理论推导值更可信。
4. **会话模式优于无状态模式。** 匹配用户心智模型（上传→诊断→选择→处理），匹配前端已有的状态机。
5. **代码去重优先于功能新增。** python/ 和核心包必须合并，否则维护成本翻倍。
