# Moodify 高性能处理方案：HPSS 频谱架构替代 Demucs 深度学习分离

**时间**: 2026-05-28
**状态**: 技术推理，待验证后实施
**核心论点**: Demucs 对 AI 音乐后处理是错误的技术选择。HPSS + M/S 频谱架构在速度上快 30-60 倍，在质量上可能更好。

---

## 0. 问题的重新定义

### 0.1 不是「源分离」，而是「差异化处理」

Demucs 的设计目标是把混合音频分离成独立声部（人声/鼓/贝斯/其他），然后用户可以分别处理每个声部再混音。

但 Moodify 的真实需求不是「分离声部」，而是「对音频的不同成分施加不同的处理参数」。

这两个问题看似相同，实际差异巨大：

```
Demucs 路径:
  立体声 → [30-60s DL推理] → 4个独立声部 → 分别处理 → 混合
  问题: 分离过程本身就是最慢的环节，且分离质量不可控

HPSS 路径:
  立体声 → [<1s FFT运算] → 谐波/打击乐成分 → 分别处理 → 混合
  优势: 分离是 FFT 的副产品，几乎零成本
```

### 0.2 为什么 AI 音乐不需要 Demucs

Demucs 训练在人类录制的音乐上。人类录制的音乐中，人声、鼓、贝斯是独立录音后混音的——信号之间有明确的物理边界。

AI 生成的音乐（Suno/Udio）是端到端生成的——没有物理边界。所谓的「人声」和「伴奏」在频谱上是一体的，Demucs 对它们做分离时：
1. 分离质量差于人类混音（因为 AI 音乐没有真正的声部边界）
2. 分离过程引入可闻伪影（相位扭曲、残留、过度分离）
3. 处理后的再合成进一步叠加伪影

**所以 Demucs 在最需要它的场景（AI 音乐）中表现最差。**

## 1. HPSS + M/S 频谱架构

### 1.1 核心原理

HPSS（Harmonic-Percussive Source Separation）是 librosa 内置的经典算法。它利用一个简单的事实：

- **谐波成分**（人声旋律、和弦、贝斯延音、合成器铺底）在时间上平滑、在频率上集中
- **打击乐成分**（鼓点、拨弦瞬态、钢琴敲击）在频率上平滑、在时间上集中

HPSS 通过中值滤波将两者分离：时间方向的中值滤波提取谐波，频率方向的中值滤波提取打击乐。

结合 M/S（中/侧）分解，产生 **4 个处理通道**：

```
                    立体声输入
                        │
                ┌───────┴───────┐
                │   M/S 分解     │
                │  Mid = L+R     │
                │  Side = L-R    │
                └───┬───────┬───┘
                    │       │
              ┌─────┴─┐ ┌───┴─────┐
              │  HPSS  │ │  HPSS   │
              └──┬──┬──┘ └──┬──┬──┘
                 │  │       │  │
         ┌───────┘  └──┐ ┌──┘  └───────┐
         ▼             ▼ ▼             ▼
    Harmonic-Mid  Perc-Mid  Harmonic-Side  Perc-Side
    (人声旋律、   (鼓点瞬态、 (侧向延音、   (侧向瞬态、
     贝斯延音、   拨弦攻击、  宽广铺底、    镲片、打击
     和弦铺底)    钢琴敲击)   空间混响)    乐宽度感)
         │             │       │             │
         ▼             ▼       ▼             ▼
    各自DSP处理  各自DSP处理 各自DSP处理  各自DSP处理
         │             │       │             │
         └─────────────┴───────┴─────────────┘
                        │
                        ▼
                   M/S 逆变换
                        │
                        ▼
                    立体声输出
```

### 1.2 处理时间对比

| 方案 | 分离耗时 | 处理耗时 | 总耗时 | 伪影风险 |
|------|---------|---------|--------|---------|
| Demucs 4-stem (CPU) | 30-60s | < 2s | 35-65s | 中-高 |
| Demucs 4-stem (GPU) | 5-10s | < 2s | 8-15s | 中-高 |
| **HPSS + M/S** | **< 0.5s** | **< 2s** | **< 3s** | **极低** |
| 全频段处理 (full_mix) | 0s | < 1s | < 1s | 无 |

### 1.3 四个通道对应的处理策略

| 通道 | 包含什么 | 典型处理 |
|------|---------|---------|
| **Harmonic-Mid** | 人声旋律、贝斯延音、中央和弦铺底 | 人声临场 EQ (P01-P03)、低频温暖感 (P04-P05) |
| **Percussive-Mid** | 鼓点瞬态、拨弦攻击、中央打击乐 | 压缩器 (P06-P09)、谐波驱动 (P13) |
| **Harmonic-Side** | 侧向延音、空间铺底、宽度氛围 | 混响 (P10-P12)、高频搁架 (P14-P15) |
| **Percussive-Side** | 侧向瞬态、镲片、打击乐宽度感 | 轻度压缩、宽度控制 |

这样的分配比 Demucs 的「人声/鼓/贝斯/其他」更符合音乐声学原理。

### 1.4 HPSS 增强模式：三组分分解

librosa HPSS 支持 `margin > 1.0` 的 H+P+R 三组分分解：

```python
H, P, R = librosa.decompose.hpss(S, margin=3.0)
# H = 严格谐波（延音、旋律）
# P = 严格打击乐（鼓、瞬态）
# R = 残余（噪态、空间信息、过渡区域）
```

残余成分可以分配到 Side 通道（因为它包含大量空间信息），进一步增强立体声宽度控制。

## 2. 多频段处理补充

### 2.1 频段划分

HPSS 解决了「谐波 vs 打击乐」的维度，但没有解决频率维度。例如：

- 低频谐波（贝斯延音）和高频谐波（人声旋律）需要不同的 EQ
- 低频打击乐（底鼓）和高频打击乐（镲片）需要不同的压缩

解决方案：在 HPSS 之后，对每个通道做简单的 3 频段分割：

```
Harmonic-Mid
    ├── 低频 (20-250Hz)   → 贝斯清晰度处理
    ├── 中频 (250-4kHz)   → 人声临场感处理
    └── 高频 (4k-20kHz)   → 空气感处理
```

这不需要额外的分离算法，只需要 3 个分频滤波器（Butterworth crossover），计算成本 < 0.01s。

### 2.2 完整的三维处理模型

最终的差异处理变成三维：

```
维度 1 (频率):  低频 / 中频 / 高频
维度 2 (性质):  谐波 / 打击乐
维度 3 (空间):  中 / 侧

总共: 3 × 2 × 2 = 12 个独立处理区域
```

每个 15 参数工艺卡可以映射到这 12 个区域的不同强度：

| 参数 | 主要作用区域 |
|------|------------|
| P01-P03 人声临场感 EQ | 中频 × 谐波 × 中 |
| P04-P05 低频温暖感 | 低频 × 谐波 × 中+侧 |
| P06-P09 压缩器 | 中频+高频 × 打击乐 × 中 |
| P10-P12 混响 | 高频 × 谐波 × 侧 |
| P13 谐波驱动 | 中频 × 谐波 × 中 |
| P14-P15 高频搁架 | 高频 × 谐波+打击乐 × 中+侧 |

## 3. 三级性能模式

### 3.1 模式定义

| 模式 | 耗时 | 技术 | 质量 | 适用场景 |
|------|------|------|------|---------|
| **Instant** | < 1s | 全频段处理（16 频段动态 EQ） | 良好 | 快速预览、批量筛选 |
| **Standard** | < 3s | HPSS (H+P) + M/S + 3 频段 | 优秀 | **默认模式，90% 用户选择** |
| **Precision** | 30-60s | Demucs 4-stem + 全参数独立处理 | 可能更差 | 特殊需求，人工混音素材 |

关键设计：**Standard 模式是默认，不是退而求其次的选择。** 对 AI 音乐而言，Standard 模式的质量可能高于 Precision 模式——因为跳过了 Demucs 伪影。

### 3.2 默认推荐逻辑

```
if input 是 AI 生成的（Suno/Udio）:
    默认 Standard 模式
    推荐理由: "AI 音乐使用频谱架构处理效果最优，3 秒完成"
elif input 是人类混音/录音室素材:
    可选 Precision 模式
    推荐理由: "人工混音可能受益于声部分离处理"
```

## 4. 竞争优势分析

### 4.1 时间 = 迭代次数 = 更好的成品

音乐后期处理不是「按一个按钮就完成」的任务。用户的工作流是：

1. 上传 → 诊断 → 处理 → 试听
2. 不满意 → 换情绪 → 再处理 → 再试听
3. 再不满意 → 换工艺卡 → 再处理 → 再试听
4. 满意 → 下载

**Demucs 路径**：每次迭代 35-65s。3 次迭代 = 2-3 分钟。用户在第 2 次迭代时就放弃了。

**HPSS 路径**：每次迭代 3s。3 次迭代 = 9 秒。用户可以快速试 5 种情绪，找到最合适的。

**更快的处理速度直接转化为更好的用户体验和更高的 EDSR。**

### 4.2 技术势能高地

| 维度 | 同类工具（如果有） | Moodify |
|------|-------------------|---------|
| 处理速度 | 30-120s（基于 DL 分离） | **< 3s**（HPSS 频谱架构） |
| 处理质量 | 不可控（DL 伪影） | **可控**（FFT 确定性） |
| 情绪匹配 | 无（通用母带） | **8 种情绪 × 15 参数** |
| 诊断反馈 | 无 | **18 参数 + WHS + EDS** |

速度是最容易被用户感知的差异。质量需要训练过的耳朵才能分辨。速度 = 竞争力。

### 4.3 技术壁垒

HPSS + M/S + 3 频段组合本身不是壁垒（librosa 是开源的）。真正的壁垒在于：

1. **18 参数诊断 → 12 区域处理映射**：把诊断结果转化为哪个区域加多少增益的规则引擎
2. **8 种情绪 × 15 参数的校准数据**：不是公式推导的，是真实专辑处理经验积累的
3. **闭环反馈体系**：WHS/EDS 评分让每次处理可量化比较

## 6. 总结

**核心结论**：

1. **Demucs 是为人类混音设计的工具，套在 AI 生成的音乐上既慢又可能引入伪影。**

2. **HPSS + M/S + 多频段是 AI 音乐后处理的正确技术栈。** 它快 30-60 倍，质量可能更好，且是确定性的（无 DL 随机性）。

3. **速度是产品竞争力。** < 3s 的处理让用户可以快速迭代试错，这比单次处理质量微幅提升更重要。

4. **真正的壁垒不在算法。** 在诊断→处理映射的领域知识，在 8 种情绪的数据校准，在闭环反馈的量化体系。这些我们已经有了。

5. **保留 Demucs 作为可选模式，但默认关闭。** 只在用户明确需要声部分离且接受等待时间时才启用。
