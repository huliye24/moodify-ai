# NEM-MT-003｜MRS 性能优化与批量生产瓶颈突破

## 给人看的说明版

创建日期：2026-06-02  
计划周期：2026.06-2026.07  
优先级：P0  
前置依赖：MT-001 Runtime 可稳定产生数据；MT-002 MRS 初步可用

---

## 1. 这个节点解决什么问题？

MT-003 解决的不是“MRS 有没有意义”，而是“MRS 能不能批量生产”。

如果 MRS 每首歌都要 1-6 分钟，那么它可以做研究，但很难进入 Daily Run、Night Worker 和批量生产。  
如果 MRS 支持 quick/full 两档、特征缓存、并行评分和 Runtime 可选列，它才真正具备成为 Moodify 工程基础设施的条件。

---

## 2. 与 MT-001、MT-002 的关系

| 节点 | 作用 |
|---|---|
| MT-001 Runtime | 让 Moodify 在云端稳定自动运行，持续产生数据 |
| MT-002 MRS | 建立 AI 音乐真实度的量化跑分单位 |
| MT-003 Performance | 让 MRS 可以大规模、低成本、可生产化运行 |

一句话：

```text
MT-001 让系统跑起来；
MT-002 让系统知道声音是否更真实；
MT-003 让这个判断可以批量跑。
```

---

## 3. 核心瓶颈

当前 MRS 可能面临的瓶颈包括：

1. 每个文件评分耗时较长；
2. 文件越大，WAV 中间文件越重；
3. 特征可能重复提取；
4. full_mrs 不适合所有任务都执行；
5. 并行能力未验证；
6. MRS 不能阻塞 Runtime 主流程；
7. 批量评分的吞吐量还没有标准。

---

## 4. 核心设计

MT-003 建议将 MRS 分成三种运行状态：

| 模式 | 用途 |
|---|---|
| off | 不评分，只跑主流程 |
| quick_mrs | 快速批量排序，用于日常生产 |
| full_mrs | 深度评分，用于实验、版本对比和正式报告 |

这种设计可以避免“所有任务都用最重评分模式”。

---

## 6. 最重要的判断标准

MT-003 不是看“优化了多少代码”，而是看：

- MRS 是否有 before / after 性能数据；
- quick_mrs 是否显著更快；
- full_mrs 是否保留完整判断力；
- 缓存是否减少重复计算；
- 并行是否提升吞吐；
- Runtime 是否可以选择评分模式；
- 失败评分是否不会拖垮主流程；
- 30 首真实 AI 音乐是否能稳定完成批量评分。

---

## 7. ADOPT 标准

MT-003 可以进入 ADOPT 的条件：

1. 完成 MRS 性能基线；
2. 完成 quick_mrs / full_mrs 双档；
3. 完成特征缓存机制；
4. 完成并行或替代吞吐优化；
5. MRS 成为 Runtime 可选列；
6. 至少完成 30 首真实/准真实 AI 音乐批量评分；
7. 自动输出批量报告；
8. 有清晰的生产建议。

---

## 8. 结论

MT-003 是 Moodify 从研究系统走向生产系统的瓶颈节点。  
它完成后，MRS 不再只是一个理论跑分，而是可以进入 Moodify 日常运行、夜间生产、批量实验和数据沉淀系统的核心工程能力。
