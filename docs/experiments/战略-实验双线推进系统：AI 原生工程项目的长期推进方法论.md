# 摘要

Moodify 当前已经从单点代码开发进入云端运行、批量实验、MRS 评分、工艺库沉淀并行推进的阶段。这个阶段最容易出现的问题是：今天修几个 bug，明天跑几个实验，后天根据某次结果临时改变方向，最终项目被局部反馈牵引，失去长期结构。

**战略-实验双线推进系统**的目的，是把项目推进分成两条互相配合、但不能互相替代的线：

- **战略主线**：负责长期方向、产品定位、系统结构、路线图和阶段目标。它不依赖短期数据反馈来决定是否存在，而是由长期判断、行业趋势和创始人意志驱动。
- **实验支线**：负责消除关键不确定性，包括工程稳定性、性能瓶颈、指标有效性、算法效果、用户反馈和商业验证。它必须依赖数据反馈，并通过推理闸门逐步放大。

一句话定义：

> 战略主线决定项目为什么必须前进，实验支线决定项目怎样更少浪费地前进。

Moodify 的长期主线是：从 AI 音乐原声出发，建立面向 AI 音乐时代的声音真实度提升系统，形成二次处理工艺库、MRS 真实度跑分体系、云端批处理能力、报告系统和最终产品化入口。实验支线则用于验证 Runtime 稳定性、MRS 性能、preset 效果、样本库覆盖、用户需求和商业路径。

这套方法论既适用于 Moodify，也适用于 AI 原生软件、量化交易系统、科研实验平台、品牌内容系统、B 端工具产品和长期创业项目。

# 1. 背景：为什么需要双线系统

复杂项目进入真实运行阶段后，会自然产生大量局部问题：文件名传参 bug、MRS 耗时过长、队列调度不稳定、服务器资源估算不准确、报告系统不完整、样本质量不一致、preset 效果不稳定等。这些问题都真实存在，也都需要解决。

但如果项目完全被这些问题牵引，就会陷入一种低层循环：

```text
今天修 bug
明天跑实验
后天看日志
大后天又发现新问题
然后继续修 bug
```

这种推进方式短期看很勤奋，长期看却容易失去方向。项目会不断移动，但不一定在向上生长。

Moodify 需要的不是更多随机任务，而是一个能够同时容纳战略推进和实验反馈的组织方式：

```text
战略主线：确定方向、阶段目标、产品结构和长期路线
实验支线：验证风险、寻找瓶颈、校准路径和沉淀工艺
```

二者的关系不是互相替代，而是互相约束：

- 没有战略主线，实验会变成随机试错。
- 没有实验支线，战略会变成空洞口号。
- 没有工艺库，失败不会形成复利。
- 没有路线图，日常任务无法汇入长期结构。

# 2. 核心定义

## 2.1 战略主线

战略主线是项目的长期确定性方向。它回答以下问题：

```text
我们为什么做这个项目？
这个项目最终要成为何种系统？
哪些方向不会因为短期实验结果而轻易改变？
下个月、下季度、一年后分别要到达什么位置？
```

对 Moodify 来说，战略主线包括：

- AI 音乐的真正机会不只在生成，而在后期工艺。
- Moodify 的使命是让虚拟声波不断接近真实声波。
- MRS 要发展为 AI 音乐真实度的跑分单位。
- Moodify 要从脚本、工具走向 AI 音乐后处理工业软件。
- 工艺库、样本库、评分体系和云端运行系统是长期护城河。

战略主线的特点：

| 特征 | 说明 |
|---|---|
| 长周期 | 以月、季度、年为单位推进 |
| 不被短期波动轻易推翻 | 某次实验失败只说明路径问题，不等于方向错误 |
| 需要阶段性拆解 | 战略必须落成月目标、周目标和交付物 |
| 由判断驱动 | 来自行业趋势、技术逻辑、产品哲学和创始人意志 |

## 2.2 实验支线

实验支线是项目的验证系统。它回答以下问题：

```text
当前最大不确定性是什么？
最小成本如何验证？
结果是否支持进入下一阶段？
失败属于哪一类？
这次实验沉淀了什么规则？
```

对 Moodify 来说，实验支线包括：

- Runtime 文件名鲁棒性实验。
- 90-task full test。
- 6h endurance run。
- 24h day run。
- MRS Performance Profiling Experiment。
- preset 效果对比实验。
- 样本库覆盖实验。
- quick_mrs / full_mrs 对比实验。
- B 端用户价值验证。

实验支线的特点：

| 特征 | 说明 |
|---|---|
| 短周期 | 以小时、天、周为单位推进 |
| 强依赖数据反馈 | 日志、指标、耗时、失败率、输出质量是判断依据 |
| 通过闸门放大 | 小验证未通过，不进入大规模运行 |
| 结果必须归档 | 每次实验都要形成 summary 和工艺规则 |

## 2.3 工艺库

工艺库不是文件夹，而是一种长期积累机制。它把实验中的失败、修复、参数、判断和规则沉淀为可复用资产。

工艺库至少包含五类内容：

| 类型 | 内容 |
|---|---|
| 运行工艺库 | 云端调度、队列、日志、异常处理、自动停止 |
| 音频处理工艺库 | 滤波、压缩、空间、动态、母带、响度处理 |
| MRS 评分工艺库 | 子指标、权重、快慢评分、性能优化、稳定性验证 |
| 实验工艺库 | 实验卡、闸门、失败分类、样本设计、报告模板 |
| 审美工艺库 | 真实感、塑料感、空间感、生命感、听感判断 |

工艺库的核心规则：

```text
一次失败只有被分类、记录、复用，才算项目资产。
```

# 3. 双线推进的系统结构

战略-实验双线推进系统可以表示为：

```text
长期战略判断
    v
战略主线 Roadmap
    v
阶段主战役
    v                     \
工程主线推进              实验支线验证
    v                     /
阶段交付物 <- 工艺库沉淀 <- 实验报告 / 日志 / 指标
    v
下一阶段战略校准
```

这个结构包含五个层级：

1. **战略判断层**：确定项目存在的理由和长期方向。
2. **路线图层**：把方向拆成年度、季度、月度目标。
3. **工程推进层**：持续建设主系统、产品结构和基础设施。
4. **实验验证层**：用数据消除关键不确定性。
5. **工艺沉淀层**：把实验经验变成可复用规则。

## 3.1 主线不等于不看现实

“主线不需要数据反馈”容易被误解。更准确的说法是：

> 战略主线不被短期实验结果牵引，但需要长期现实反馈校准。

例如，Moodify 继续做 AI 音乐后处理，不会因为某一次 MRS 性能慢就放弃；但 MRS 慢会改变近期工程优先级，促使系统设计 quick_mrs / full_mrs 双模式。

也就是说：

```text
实验反馈不决定项目是否存在，实验反馈决定项目如何推进。
```

## 3.2 支线不等于随机试错

实验支线也不能变成随机试错。每个实验必须服务于战略主线中的某个关键不确定性。

一个合格的实验支线必须回答：

```text
它验证哪条主线？
它消除哪个不确定性？
它通过后会放大什么？
它失败后会修正什么？
它最终进入哪一类工艺库？
```

# 4. 决策层级：从一年到今天

双线系统要求把决策分层，避免用日任务替代战略判断。

| 层级 | 时间尺度 | 作用 | 示例 |
|---|---:|---|---|
| 愿景层 | 3-5 年 | 定义项目终局 | AI 音乐真实度工程系统 |
| 年度层 | 1 年 | 定义系统成熟度 | 形成稳定产品雏形和早期用户 |
| 季度层 | 3 个月 | 定义阶段主战役 | Runtime / MRS / MVP 成型 |
| 月度层 | 1 个月 | 定义核心交付物 | 24h run 稳定、MRS 性能画像 |
| 周度层 | 1 周 | 定义具体战役 | Runtime v0.3 熔断机制 |
| 日度层 | 1 天 | 执行任务 | 修 bug、跑测试、写报告 |

关键原则：

```text
日任务必须服务周目标。
周目标必须服务月主战役。
月主战役必须服务季度路线。
季度路线必须服务年度系统成熟度。
```

如果某个任务无法说明它属于哪条主线，就应该暂停，重新判断。

# 5. Moodify 五条战略主线

## 5.1 主线一：Runtime 云端运行系统

**长期目标**：让 Moodify 可以稳定、自动、可复盘地在云端处理 AI 音乐。

阶段规划：

| 版本 | 目标 |
|---|---|
| v0.2 | 文件名鲁棒性，subprocess list argv，基础 full test |
| v0.3 | 失败熔断、任务恢复、确定性错误不重试 |
| v0.4 | 并行队列、资源调度、CPU / 内存 / 磁盘监控 |
| v0.5 | 自动日报、实验归档、summary 标准化 |
| v1.0 | 生产级批处理系统 |

战略意义：Runtime 是 Moodify 的发动机。没有稳定运行系统，后续 MRS、preset、样本库和产品化都无法沉淀。

## 5.2 主线二：MRS 跑分系统

**长期目标**：让 MRS 成为 AI 音乐真实度的跑分单位。

阶段规划：

| 版本 | 目标 |
|---|---|
| v0.3.1 | 当前 ADOPT，完成基础跑分框架 |
| v0.4 | MRS 性能画像，识别耗时瓶颈 |
| v0.5 | quick_mrs / full_mrs 双模式 |
| v0.6 | 真实 AI 音乐样本校准 |
| v1.0 | 公开 benchmark 雏形 |

战略意义：MRS 是 Moodify 的标准化语言。没有 MRS，Moodify 只能说“听起来更好”；有 MRS，Moodify 可以说“真实度提升了多少”。

## 5.3 主线三：音频处理工艺库

**长期目标**：从单个处理脚本发展为可复用声音工艺系统。

工艺库方向：

| 工艺方向 | 作用 |
|---|---|
| warm_vocal | 提升人声温度与亲密感 |
| clean_master | 清理频谱、控制响度、提升发布感 |
| wide_space | 改善空间宽度与声场层次 |
| deplastic | 降低 AI 音乐塑料感 |
| transient_repair | 修复瞬态发软问题 |
| air_band_restore | 恢复空气感和高频通透度 |
| dynamic_recovery | 恢复动态起伏和生命感 |
| vocal_texture | 增强人声纹理和颗粒度 |

战略意义：工艺库是 Moodify 的长期护城河。代码可以被模仿，但长期实验形成的参数、流程和判断不容易复制。

## 5.4 主线四：产品 MVP

**长期目标**：让非技术用户也能使用 Moodify。

MVP 最小闭环：

```text
上传音频
    v
选择处理模式
    v
生成处理后音频
    v
生成 MRS 报告
    v
下载结果
    v
保存案例
```

战略意义：工程系统必须走向产品形态。否则 Moodify 只能在服务器上运行，不能被创作者、团队和 B 端客户理解。

## 5.5 主线五：品牌与理论

**长期目标**：让 Moodify 不只是工具，而是 AI 音乐后处理领域的思想入口。

核心叙事：

```text
AI 音乐的真正机会，不在生成，而在后期工艺。
Moodify 的使命，是让虚拟声波接近真实声波。
MRS 是 AI 音乐真实度的跑分单位。
```

战略意义：技术系统需要外部语言。品牌与理论把内部工程转译成别人能理解、相信、传播和合作的叙事。

# 6. 实验支线组合

实验支线不是越多越好，而是要围绕主线建立实验组合。

## 6.1 Runtime 稳定性实验

目标：验证系统是否能稳定运行真实任务。

实验清单：

- 特殊文件名 smoke test。
- 90-task full test。
- 6h endurance run。
- 24h day run。
- 失败熔断实验。
- 任务恢复实验。
- 日志完整性实验。
- summary 自动生成实验。

关键指标：

```text
成功率
exit code 分布
unrecognized arguments 次数
连续失败次数
平均单任务耗时
卡住任务数量
summary 是否生成
```

## 6.2 MRS 性能画像实验

目标：解释 MRS 为什么慢，并设计可优化路径。

实验问题：

- MRS 为什么 1-6 分钟/文件？
- 不同文件大小对耗时有什么影响？
- WAV 中间文件大小对耗时有什么影响？
- 是否可以缓存特征？
- 是否可以并行评分？
- 是否可以把 MRS 设置为可选列？
- 是否需要 quick_mrs / full_mrs 两档？

战略意义：MRS 是标准系统，但如果性能过慢，会阻碍 Runtime 吞吐量和产品体验。

## 6.3 Preset 效果验证实验

目标：验证处理工艺是否真正提升真实度，而不是制造响度假象。

实验问题：

- 哪个 preset 能稳定提升 MRS？
- 哪个 preset 可能破坏动态？
- 哪个 preset 对人声有效？
- 哪个 preset 对电子乐有效？
- 哪个 preset 只是响度作弊？
- 是否需要按风格分 preset？

关键指标：

```text
MRS_before
MRS_after
Delta_MRS
LoudnessPenalty
OPR
动态变化
空间变化
频谱变化
```

## 6.4 样本库覆盖实验

目标：建立能代表真实 AI 音乐生态的样本集。

样本维度：

- Suno / Udio / 其他生成平台。
- 人声 / 器乐 / 电子 / 民谣 / 摇滚 / 电影感。
- 中文 / 英文 / 法语 / 其他语言。
- 高质量样本 / 普通样本 / 明显塑料感样本。
- 短音频 / 中等音频 / 完整歌曲。

战略意义：样本库决定 Moodify 的工艺库性格。不同样本分布会训练出不同的声音判断。

## 6.5 用户价值验证实验

目标：验证 Moodify 是否真的解决创作者和 B 端团队的问题。

实验问题：

- 创作者最在意音质、真实度、响度、空间感还是效率？
- 他们是否理解 MRS 报告？
- 他们愿意用 preset 还是自动推荐？
- B 端是否需要批量处理？
- 他们是否愿意为处理结果和报告付费？

战略意义：技术价值必须最终进入用户价值，否则系统只能内部循环。

# 7. 12 个月路线图

## 7.1 2026 年 6 月：云端运行系统成型期

主战役：Runtime 稳定。

目标：让 Moodify 可以在云服务器上稳定自动运行。

关键交付物：

- Runtime v0.2 通过 full test。
- 6h endurance run 通过。
- 24h day run 通过。
- MRS Performance Profiling Experiment 完成。
- quick_mrs / full_mrs 设计方案。
- 真实 AI 音乐样本库 v0.1。
- 实验报告与工艺库目录成型。

成功标志：Moodify 不再依赖人工盯屏，可以独立完成一轮云端处理并输出 summary。

## 7.2 2026 年 7-8 月：工艺库与 MVP 成型期

主战役：形成最小产品闭环。

目标：完成“导入音频 - 分析 - 处理 - MRS 评分 - 导出结果”的 MVP。

关键交付物：

- 3-5 个稳定 preset。
- MRS Open Benchmark v0.4 / v0.5。
- quick_mrs / full_mrs 双模式。
- 处理前后对比报告。
- 批量处理报告。
- 最小界面原型。
- 100-300 首 AI 音乐测试样本库。
- 10-30 组 A/B 案例。
- 第一批 Moodify 技术白皮书和公众号文章。

成功标志：Moodify 具备可展示的完整处理闭环。

## 7.3 2026 年 9-12 月：产品化与品牌成型期

主战役：从内部工程系统走向外部可理解产品。

目标：发布 Moodify Alpha / Internal Preview。

关键交付物：

- 用户上传音频。
- 处理后版本输出。
- MRS 报告输出。
- preset 选择。
- 原始音频 vs Moodify 处理后案例库。
- 品牌叙事矩阵。
- 技术叙事矩阵。
- 小规模 AI 音乐创作者或 B 端团队接触。

成功标志：外部用户能够理解 Moodify 是什么、解决什么问题、为什么 AI 音乐时代需要它。

## 7.4 2027 年：工业软件雏形与商业验证期

主战役：形成 AI 音乐后处理工业软件雏形。

目标：让 Moodify 进入早期商业化验证。

关键交付物：

- 稳定版本。
- 真实用户或合作方。
- MRS 跑分体系。
- 一批处理工艺 preset。
- 云端批处理能力。
- 自动报告系统。
- 技术白皮书。
- 品牌内容矩阵。
- 初步收费路径。
- 小团队协作机制。
- 专利 / 软著 / 技术壁垒布局。

成功标志：Moodify 不再是一个人用 AI 写代码，而是围绕 AI 音乐真实度提升而生长的工程系统。

# 8. 月度主战役制度

Moodify 不应该每个月同时打一堆方向。每个月只设一个主战役，其他内容作为支援线。

| 月份 | 主战役 | 核心交付 |
|---|---|---|
| 2026-06 | 云端 Runtime 稳定 | 24h run、MRS 性能画像、工艺库目录 |
| 2026-07 | MRS 与工艺库成型 | quick/full MRS、稳定 preset、样本库 |
| 2026-08 | MVP 闭环 | 上传、处理、评分、报告、导出 |
| 2026-09 | 外部展示版本 | Alpha 演示、案例库、品牌说明 |
| 2026-10 | 用户验证 | 创作者测试、B 端访谈、反馈收集 |
| 2026-11 | 产品打磨 | 流程优化、界面优化、批量能力 |
| 2026-12 | 年度封装 | 白皮书、案例集、技术路线、商业计划 |

原则：

```text
每月一个主战役。
每周一个主目标。
每天服务本周主目标。
```

# 9. 每周运行节奏

## 周一：战略计划日

任务：确定本周只做一个主线目标。

输出：

```text
weekly_plan.md
```

包含：

- 本周主线。
- 本周支线实验。
- 本周不做什么。
- 预计交付物。
- 风险清单。

## 周二到周四：工程推进日

任务：集中修代码、跑实验、生成日志和报告。

原则：

- 不随意新增方向。
- 不在长跑期间频繁改代码。
- 实验必须有 summary。
- 失败必须分类。

## 周五：实验复盘日

任务：总结本周实验。

输出：

```text
weekly_review.md
```

包含：

- 成功了什么。
- 失败了什么。
- 哪些失败属于确定性错误。
- 哪些规则进入工艺库。
- 下周是否放大。

## 周末：品牌与文档日

任务：把工程经验转译成文档、白皮书、公众号、路线图和外部叙事。

原则：

```text
工程不写出来，就无法变成品牌资产。
实验不归档，就无法变成工艺库。
```

# 10. 每次任务的归属判断

任何新任务出现时，先判断它属于哪一类：

| 类型 | 例子 | 处理方式 |
|---|---|---|
| 战略主线任务 | Runtime v0.3、MRS v0.5、MVP 闭环 | 优先进入路线图 |
| 实验支线任务 | MRS 性能画像、preset A/B | 进入实验卡 |
| 维护任务 | 清理日志、修路径、补报告 | 批量处理，不打断主线 |
| 临时灵感 | 新功能、新视觉、新叙事 | 先进入 backlog，不立即执行 |
| 风险任务 | 系统崩溃、数据丢失、重大 bug | 立即处理 |

任务判断句式：

```text
这个任务属于哪条主线？
它服务哪个月度主战役？
如果今天不做，会不会阻断主线？
它是战略推进，还是实验验证？
它是否值得打断当前实验？
```

# 11. To-do 体系：战略待办与实验待办分离

## 11.1 战略待办

战略待办不需要每天改动，它用于保持项目长期方向。

示例：

```text
[战略] Runtime v1.0 生产级批处理系统
[战略] MRS v1.0 AI 音乐真实度 Benchmark
[战略] Moodify MVP 产品闭环
[战略] AI 音乐后处理品牌叙事矩阵
[战略] B 端批量处理商业验证
```

## 11.2 实验待办

实验待办必须有假设、输入、指标和停止条件。

示例：

```text
[实验] MRS Performance Profiling Experiment
假设：MRS 耗时主要来自 full_mrs 特征计算。
输入：10 首不同大小音频。
指标：总耗时、特征耗时、WAV 大小、CPU 占用。
判定：是否需要 quick_mrs / full_mrs 双模式。
```

## 11.3 工艺库待办

工艺库待办用于把经验变成规则。

示例：

```text
[工艺库] 所有文件路径必须使用 subprocess list argv。
[工艺库] 确定性错误不重试。
[工艺库] 24h run 前必须通过 90-task full test。
[工艺库] MRS 评分应支持 quick/full 双模式。
```

# 12. Claude / AI 执行规范

为了避免反复点 yes 和无序执行，所有 Claude 任务都必须遵守以下规则：

```text
1. 执行前先说明任务属于战略主线还是实验支线。
2. 执行前给出预计耗时和检查时间点。
3. 不使用交互式命令。
4. 不使用 rm -rf；删除改为 mv 到 backups 或 ABORTED。
5. 长任务使用 nohup 后台运行。
6. 每个后台任务必须输出 PID、日志路径、summary 路径。
7. 每个实验必须有通过标准和停止条件。
8. 不通过上一阶段，不允许进入下一阶段。
9. 长跑阶段不随意改代码。
10. 每次结束必须生成报告并写入工艺库条目。
```

Claude 不只是执行者，而是：

```text
任务编排者
实验记录员
失败分类器
代码修复者
工艺库整理员
```

人类不应该一直盯屏幕，而应该负责：

```text
战略判断
阶段批准
路线选择
价值判断
最终决策
```

# 13. 指标体系

双线系统需要两类指标：战略指标和实验指标。

## 13.1 战略指标

战略指标用于判断项目是否在向长期目标靠近。

| 指标 | 含义 |
|---|---|
| 主线完成度 | Runtime、MRS、工艺库、MVP 是否按月推进 |
| 工艺库增长 | 新增多少可复用规则、preset、报告模板 |
| 系统成熟度 | 从脚本到批处理、从批处理到产品的进度 |
| 外部可理解度 | 是否能向外部解释 Moodify 的价值 |
| 产品闭环程度 | 是否完成上传、处理、评分、报告、导出 |

## 13.2 实验指标

实验指标用于判断某个具体不确定性是否被消除。

| 指标 | 含义 |
|---|---|
| 成功率 | 任务是否正常完成 |
| 失败类型 | 确定性、数据型、性能型、随机型、设计型 |
| 耗时分布 | 平均值、P50、P80、P95 |
| 资源占用 | CPU、内存、磁盘、I/O |
| 输出完整性 | 音频、报告、summary 是否生成 |
| 指标稳定性 | MRS 是否稳定、是否被异常样本扰动 |

# 14. 风险管理

## 14.1 战略风险

| 风险 | 表现 | 应对 |
|---|---|---|
| 方向漂移 | 每天被新问题带走 | 月度主战役制度 |
| 功能膨胀 | 还没闭环就加很多功能 | MVP 闭环优先 |
| 只做工程不做品牌 | 外部无法理解 | 周末文档与内容日 |
| 只做理论不做产品 | 无真实系统 | 工程主线必须持续推进 |

## 14.2 实验风险

| 风险 | 表现 | 应对 |
|---|---|---|
| 直接长跑 | 24h 后才发现配置错 | 推理闸门，小样本先行 |
| 重复确定性失败 | CPU 空转 | 熔断机制 |
| 数据污染 | 失败 run 混入有效结果 | ABORTED 标记和目录隔离 |
| 指标误判 | 响度提升被误认为真实度提升 | MRS 子指标拆解 |
| 性能瓶颈 | MRS 过慢 | 性能画像实验 |

# 15. 反模式清单

以下行为应被视为反模式：

```text
没有实验卡就跑长任务。
没有成功标准就判断通过。
没有停止条件就让服务器空转。
小测试没过就开 24h run。
实验运行中频繁改代码。
失败不分类，只说“跑失败了”。
报告不归档，经验留在聊天记录里。
看到新想法就立即打断主线。
没有月度主战役，天天临时决策。
```

反模式的共同问题是：它们会消耗时间，但不产生系统复利。

# 16. 标准工作流

一个完整的 Moodify 推进周期如下：

```text
战略主线确认
    v
月度主战役设定
    v
周目标拆解
    v
实验卡生成
    v
AI 推理预检
    v
最小决定性实验
    v
中规模验证
    v
长时间运行
    v
summary 生成
    v
工艺库沉淀
    v
路线图更新
```

标准决策句：

```text
这个结果是否支持进入下一阶段？
这个失败是否改变战略主线？
这个经验是否应该进入工艺库？
下一个月度主战役是否需要调整？
```

# 17. 结论

战略-实验双线推进系统的核心，不是把项目变得复杂，而是把复杂项目的推进方式变得清晰。

Moodify 接下来不能只靠日常任务推动，也不能只靠灵感和短期实验推动。它需要一条稳定的战略主线，同时用实验支线不断消除真实世界中的不确定性。

最终目标是：

```text
战略主线让项目不迷路。
实验支线让项目少浪费。
工艺库让项目有复利。
路线图让项目知道下一月、下一年要到哪里。
```

一句话总结：

> 用战略决定方向，用实验减少不确定性，用工艺库积累复利，用路线图把今天的任务汇入一年的系统生长。
