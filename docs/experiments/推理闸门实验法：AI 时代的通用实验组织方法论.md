# 摘要

**推理闸门实验法**（Reasoning-Gated Experiment Protocol, RGEP）是一套面向 AI 时代的通用实验组织方法论。它适用于软件工程、AI 项目、音频工程、量化交易、产品验证、内容实验、商业模型验证等需要持续试错、持续运行、持续沉淀的复杂项目。

这套方法的核心不是“先小样本、再大样本”这么简单，而是：

> **先用 AI 推理拆解未知与失败模式，再用最小决定性实验获得现实反馈，通过闸门机制逐步放大实验规模，最后将数据、判断与规则沉淀为可复用工艺库。**

它解决的是传统实验中的几个长期问题：目标不清、盲目大跑、失败难解释、确定性错误反复重试、长时间运行浪费资源、实验结果无法沉淀。

一句话概括：

> **先推理，后做功；先证伪，后放大；先过闸门，后长跑；失败分类，规则入库。**

---

# 1. 方法论定位

## 1.1 为什么需要新的实验方法

传统实验常常遵循一种朴素逻辑：

> “我不知道结果，所以先跑一下。”

这种方式在资源便宜、系统简单、变量较少时可以接受。但在 AI 辅助工程、云端批处理、复杂软件系统、音频后处理、量化策略、产品验证等场景中，盲目运行会带来明显问题：

- 大量时间浪费在确定性错误上，例如路径错误、配置错误、参数拆分错误、依赖缺失。
- 机器长时间满载，但实际没有产生有效数据。
- 实验目标混杂，跑完后无法判断到底验证了什么。
- 小错误在大规模运行中被放大，造成日志污染、数据污染和判断污染。
- 失败没有被分类，也没有转化为下一次实验的规则。

AI 的出现改变了实验组织方式。AI 不只是执行者，也可以成为实验前的推理者、失败模式分析者、实验设计者、日志分析员和工艺库整理者。

因此，实验不应该再从“直接运行”开始，而应该从“推理闸门”开始。

## 1.2 实验的真正目的

实验的本质不是运行代码，也不是消耗算力，而是：

> **用现实反馈减少关键不确定性。**

一个实验是否值得做，取决于它能否改变下一步决策。

每次实验开始前，必须回答三个问题：

1. 当前最大的未知是什么？
2. 用什么最低成本方式可以验证这个未知？
3. 实验结果出来后，下一步决策会如何改变？

如果一个实验无法改变决策，它只是消耗资源。

# 2. 核心定义

## 2.1 推理闸门

**推理闸门**指在现实做功之前，由 AI 和人共同完成的实验审查机制。

它要回答：

- 这个实验有没有清晰目标？
- 最可能失败的地方在哪里？
- 哪些失败是确定性的？
- 是否存在更便宜的证伪方式？
- 成功标准和停止条件是否明确？
- 是否值得进入真实运行阶段？

推理闸门的作用是减少盲目性，防止未经审查的实验直接进入昂贵运行。

## 2.2 最小决定性实验

**最小决定性实验**（Minimum Decisive Test）不是普通意义上的“小样本实验”。它强调的是“能否决定下一步”。

一个实验如果满足以下三个条件，就可以称为最小决定性实验：

1. 成本足够低。
2. 能暴露当前最关键风险。
3. 结果能决定是否进入下一阶段。

例如，验证文件名传参是否稳定，不需要先跑 90 个任务。只需要选一个带空格、括号或中文的文件名，跑一个任务，就可能直接证伪修复方案。

## 2.3 闸门

**闸门**是一种阶段性放大机制。

每个阶段都必须定义：

- 输入条件
- 执行动作
- 成功标准
- 失败标准
- 停止条件
- 输出文件
- 是否允许进入下一阶段

没有通过上一道闸门，不允许进入下一阶段。

## 2.4 工艺库

**工艺库**不是简单的实验结果集合，而是可复用规则的集合。

实验结束后，应该留下三类产物：

- 数据：日志、指标、耗时、输出、错误码。
- 判断：通过、失败、暂停、扩大、回滚。
- 规则：以后遇到同类问题时应该如何处理。

真正进入工艺库的是规则，而不仅是结果。

# 3. 总体框架

推理闸门实验法包括七个层级：

1. 问题定义
2. 不确定性拆解
3. AI 推理预检
4. 最小决定性实验
5. 扩大验证
6. 长时间做功
7. 工艺库沉淀

整体流程如下：

```text
问题定义
  ↓
不确定性拆解
  ↓
AI 推理预检
  ↓
最小决定性实验
  ↓
扩大验证
  ↓
长时间做功
  ↓
工艺库沉淀
```

这套方法的关键不是按照样本大小推进，而是按照“不确定性是否被消除”推进。

如果某个问题在推理阶段就能发现明显错误，就不应该进入真实运行。

如果一个问题用一个样本就能证伪，就不应该先跑一百个样本。

如果中规模测试没有通过，就不应该进入长时间运行。

---

# 4. 第 0 层：问题定义

## 4.1 定义实验目标

每次实验开始前，必须先写清楚：

```text
本实验要验证：__________
本实验不验证：__________
实验结果将决定：__________
```

这三句话写不清楚，不允许启动实验。

例如：

```text
本实验要验证：云端 runtime 是否能稳定处理真实文件名。
本实验不验证：音频处理后的主观听感、MRS 评分、商业价值。
实验结果将决定：是否允许进入 90-task full test 和 24h run。
```

## 4.2 防止目标混杂

复杂项目中最常见的问题是一个实验同时验证太多东西。

例如，一个 AI 音频系统可能同时包含：

- 文件路径传参
- 队列调度
- 音频解码
- preset 参数
- 频谱分析
- 母带处理
- MRS 评分
- 报告生成
- 云端吞吐量

如果一次实验同时改动多个层，一旦失败，就无法判断是哪里出错。

原则：

> **一次实验尽量只验证一个关键层。**

---

# 5. 第 1 层：不确定性拆解

## 5.1 七类不确定性

任何复杂实验都可以拆成七类不确定性：

1. 理论未知：这个想法在逻辑上是否成立？
2. 工程未知：代码、系统、流程是否能跑？
3. 数据未知：输入数据是否干净、完整、代表真实情况？
4. 性能未知：时间、CPU、内存、磁盘是否承受得住？
5. 指标未知：用什么标准判断好坏？
6. 稳定性未知：长时间运行是否可靠？
7. 价值未知：这个结果是否真的有用？

实验设计的第一步，是识别当前最危险的不确定性。

## 5.2 不确定性优先级

不是所有未知都需要同时解决。

优先处理满足以下条件的未知：

- 一旦出错，会污染后续所有实验。
- 可以用较低成本快速验证。
- 会决定是否值得扩大规模。
- 属于系统性风险，而不是个别样本风险。

例如，在云端批处理系统中，如果 runtime 传参层不稳定，那么后续音频质量、评分公式、吞吐量统计都可能被污染。因此，runtime 稳定性优先于音质验证。

---

# 6. 第 2 层：AI 推理预检

## 6.1 AI 推理预检的任务

AI 推理预检必须完成五件事：

1. 找出最可能失败的地方。
2. 判断哪些失败是确定性错误。
3. 设计最低成本验证方式。
4. 提前定义停止条件。
5. 估算时间与资源成本。

它的核心问题是：

> **有没有一种不用大规模运行，就能提前发现问题的方法？**

## 6.2 预检问题清单

每次实验前，AI 必须回答以下问题：

1. 当前实验的目标是否单一清晰？
2. 最大不确定性是什么？
3. 最可能失败的 3 个点是什么？
4. 哪些错误一旦出现就不应重试？
5. 最小决定性实验是什么？
6. 成功标准是什么？
7. 失败标准是什么？
8. 何时自动停止？
9. 预计耗时是多少？
10. 输出路径、日志路径、summary 路径是什么？

## 6.3 AI 的角色

在这套方法中，AI 不只是执行命令的助手，而是六种角色的组合：

- 推理者：拆解问题，识别最大未知。
- 怀疑者：提前寻找失败模式。
- 实验设计师：设计最小决定性实验。
- 工程执行者：写脚本、跑任务、收集日志。
- 分析员：阅读结果、分类失败、判断下一步。
- 档案员：将经验整理成工艺库。

人的角色则是设定方向、判断价值、批准放大、选择路线、维护工艺库。

---

# 7. 第 3 层：最小决定性实验

## 7.1 设计原则

最小决定性实验不是为了获得完整结论，而是为了用最低成本决定是否继续。

它的设计原则是：

- 输入尽量少。
- 变量尽量少。
- 风险样本优先。
- 成功标准提前定义。
- 失败后能明确归因。

## 7.2 风险样本优先

最小实验不一定选择“最普通样本”，而应优先选择“最容易暴露问题的样本”。

例如：

- 文件系统实验：选择包含空格、括号、中文、单引号、多空格的文件名。
- 音频实验：选择人声、鼓点、低频、高频、空间感差异明显的样本。
- 量化实验：选择震荡、趋势、暴跌、暴涨等不同市场阶段。
- 产品实验：选择目标用户中最典型、最敏感、最有痛点的人群。

## 7.3 最小决定性实验的输出

每个最小决定性实验都应输出：

- 是否通过。
- 失败类型。
- 单任务耗时。
- 是否允许扩大验证。
- 下一阶段估算。

---

# 8. 第 4 层：扩大验证

## 8.1 扩大验证的目的

最小决定性实验通过后，进入扩大验证。

扩大验证的目的不是继续探索，而是确认：

> **小规模成功是否能在更真实、更复杂的场景中保持成立？**

## 8.2 三种扩大维度

扩大验证可以增加三种复杂度：

1. 样本复杂度：更多样本、更复杂输入、更真实数据。
2. 场景复杂度：更多参数组合、更多 preset、更多环境条件。
3. 时间复杂度：更长运行、更长监控、更长数据积累。

不同项目可以形成不同的扩大阶梯。

例如：

```text
软件系统：单元测试 → 集成测试 → 全流程测试 → 压力测试
音频系统：单样本 → 高风险样本 → 全样本 → 长时间批处理
量化策略：短区间 → 多行情阶段 → 多资产 → 模拟盘 → 小资金实盘
产品验证：自己使用 → 熟人使用 → 陌生用户 → 小规模付费 → 留存验证
```

## 8.3 中规模测试的意义

中规模测试是最容易被忽略的一层。

它位于小实验和长跑之间，作用是防止把小规模偶然成功直接放大到长时间运行。

中规模测试的通过标准通常包括：

- 成功率达到预设阈值。
- 没有重复性系统错误。
- 输出结构正常。
- 日志和 summary 正常生成。
- 单任务平均耗时可估算。
- 资源占用没有异常。

---

# 9. 第 5 层：长时间做功

## 9.1 长跑不是调试

长时间运行不是调试。

如果系统还在频繁报错、频繁改代码、频繁人工介入，那么它不是 endurance run，而是 debug run。

调试阶段允许频繁修改。长跑阶段主要观察稳定性。生产阶段主要收集结果。

## 9.2 进入长跑的条件

进入长时间运行之前，必须满足：

- 核心 bug 已修复。
- 最小决定性实验通过。
- 中规模测试通过。
- 日志稳定。
- 失败率可控。
- 停止条件明确。
- summary 能自动生成。
- 预计耗时和查看时间点明确。

## 9.3 长跑的目标

长时间运行的目的不是“看看会不会出事”，而是验证：

> **系统在真实时间压力下能否保持结构稳定。**

长跑主要观察：

- 是否持续运行。
- 是否能自动停止或进入下一轮。
- 是否避免无限重试。
- 是否有磁盘异常增长。
- 是否有 CPU 空转。
- 是否能输出最终报告。
- 是否能形成可复盘数据。

# 10. 第 6 层：工艺库沉淀

## 10.1 实验结束后的三类产物

实验结束后，不能只留下“成功”或“失败”。

必须沉淀三类产物：

1. 数据：日志、耗时、输出、错误码、指标值。
2. 判断：通过、失败、暂停、回滚、扩大。
3. 规则：以后遇到同类问题时应该如何处理。

## 10.2 工艺规则格式

建议每条工艺规则使用以下格式：

```text
规则名称：
适用范围：
触发条件：
原因解释：
处理动作：
验证方式：
反例或边界：
最后更新：
```

例如：

```text
规则名称：文件路径必须使用 list argv 传参
适用范围：所有批处理、子进程调用、文件队列系统
触发条件：输入文件名可能包含空格、括号、中文、单引号、多空格
原因解释：shell 字符串拼接会导致参数被拆分
处理动作：使用 subprocess.run([...], shell=False)
验证方式：特殊文件名 smoke test
反例或边界：仅在必须使用 shell 特性时才允许 shlex.quote
最后更新：2026-06-02
```

## 10.3 工艺库的复利

工艺库的价值在于复利。

每次失败如果都能转化为规则，系统会逐渐减少重复错误；每次成功如果都能转化为流程，系统会逐渐提高可复制性。

这就是复杂工程从个人经验走向组织能力的关键。

# 11. 失败分类与停止机制

## 11.1 失败分类

实验失败不能简单重试，必须先分类。

| 类型 | 典型例子 | 是否重试 | 处理方式 |
|---|---|---:|---|
| 确定性失败 | 路径错误、配置错误、参数错误、依赖缺失 | 不重试 | 停止并修复 |
| 数据型失败 | 文件损坏、编码异常、样本质量异常 | 不全局停止 | 隔离样本 |
| 性能型失败 | 超时、CPU 满载、内存不足、磁盘不足 | 谨慎重试 | 限速、拆批、扩容 |
| 随机型失败 | 临时 I/O、偶发进程中断 | 可重试 | 重试 1-2 次 |
| 设计型失败 | 指标设计错误、实验目标错误 | 不重试 | 回到实验卡 |

## 11.2 立即停止条件

出现以下情况，应立即停止或暂停实验：

- 同类确定性错误重复出现。
- 前 10 个任务失败率超过 30%。
- 连续失败 3 次。
- 同一 stderr 摘要出现 2 次以上。
- 30 分钟无新日志或无新输出。
- 磁盘空间低于安全阈值。
- CPU 满载但没有有效任务完成。

## 11.3 不应重试的错误

以下错误通常不应通过重试解决：

- 参数无法识别。
- 配置文件无法解析。
- 文件路径不存在。
- 目录无写入权限。
- 依赖包缺失。
- preset 名称不存在。
- Python 模块不存在。

这些是确定性错误。重复运行只会浪费时间。

# 12. 时间估算方法

## 12.1 为什么必须估时

实验管理不只是技术问题，也是时间管理问题。

每次启动云端任务前，都必须明确：

- 预计多久完成。
- 什么时候查看进度。
- 超过多久判定异常。
- 最终报告在哪里。

这可以减少人反复盯屏幕，也可以防止系统长时间空转。

## 12.2 基础估算公式

最小实验完成后，可计算单任务耗时：

```text
平均单任务耗时 = 实验总耗时 / 任务数量
```

中规模测试估算：

```text
中规模预计耗时 = 平均单任务耗时 × 任务数量 × 冗余系数
```

建议冗余系数取 1.15 到 1.30，用于覆盖 I/O、日志、长任务波动和样本差异。

长时间吞吐量估算：

```text
预计任务数 = 可用时间 / 平均单任务耗时 × 成功率
```

如果一个样本需要多个 preset，则：

```text
预计样本数 = 预计任务数 / preset 数量
```

## 12.3 查看时间点

每个任务都应给出明确查看节奏。

示例：

```text
smoke test 预计 45 分钟；建议 30 分钟后查看日志，60 分钟后查看 summary。
full test 预计 3 小时；建议 1 小时后查看进度，3.5 小时后查看 summary。
24h run 启动后 30 分钟做一次健康检查，6 小时做一次 endurance 检查，24 小时看最终报告。
```

# 13. 标准实验卡模板

# 15. 通用 Claude 执行规范

为了减少人工确认和反复点击，给 AI 执行者的规范应固定化。

```text
1. 启动任务前，先输出预计耗时和建议查看时间。
2. 不使用交互式命令。
3. 不使用 rm -rf；删除改为移动到 backups/ 或 ABORTED/。
4. 长任务使用 nohup 或后台运行。
5. 每个后台任务必须输出 PID。
6. 每个任务必须输出日志路径。
7. 每个任务必须输出 summary 路径。
8. 不通过上一阶段，不允许进入下一阶段。
9. 出现确定性错误，不要盲目重试。
10. 每次实验结束，必须生成工艺库条目。
```

# 16. 适用场景

推理闸门实验法适用于所有需要“推理、试错、放大、沉淀”的复杂项目。

## 16.1 软件工程

```text
问题定义 → 静态检查 → 单元测试 → 集成测试 → 全流程测试 → 压力测试 → 工程规则沉淀
```

## 16.2 音频工程

```text
处理目标定义 → 风险样本选择 → 单样本处理 → 多 preset 测试 → 全库处理 → 长时间批处理 → 声音工艺沉淀
```

## 16.3 量化交易

```text
策略假设 → 小区间回测 → 多行情阶段 → 多资产验证 → 模拟盘 → 小资金实盘 → 策略规则库
```

## 16.4 产品验证

```text
用户假设 → 原型验证 → 5-10 人试用 → 小规模真实用户 → 留存观察 → 付费验证 → 产品机制沉淀
```


# 17. 方法论公式

可以将推理闸门实验法抽象为：

```text
有效实验价值 = 信息增量 × 决策影响 × 可复用程度 / 运行成本
```

其中：

- 信息增量：实验是否减少了关键未知。
- 决策影响：实验是否改变下一步行动。
- 可复用程度：结果是否能沉淀为规则。
- 运行成本：时间、算力、人力、资金和机会成本。

因此，高价值实验不是规模最大，而是单位成本产生的信息价值最高。

# 18. 十条纪律

推理闸门实验法真正有效，依赖纪律。

1. 目标不清，不跑。
2. 成功标准不清，不跑。
3. 停止条件不清，不跑。
4. 小实验没过，不放大。
5. 中规模没过，不长跑。
6. 确定性错误，不重试。
7. 长跑阶段，不频繁改代码。
8. 每次失败，必须分类。
9. 每次实验，必须留下 summary。
10. 每次有效经验，必须进入工艺库。

# 19. 结语

推理闸门实验法的核心不是让 AI 替代实验，也不是让机器盲目多跑，而是重新组织实验顺序。

在这套方法中：

```text
AI 负责推理、预检、设计、执行、分析与归档。
机器负责真实做功。
日志负责记录现实。
人负责判断方向、批准放大和维护规则。
工艺库负责形成复利。
```

最终目标是让每一次实验都具备更高的信息价值，让每一次失败都成为系统成长的一部分。

它的长期意义在于：

> **把个人试错升级为可复用的实验系统，把零散经验升级为组织工艺，把 AI 的推理能力转化为现实世界中的时间节省和工程复利。**
