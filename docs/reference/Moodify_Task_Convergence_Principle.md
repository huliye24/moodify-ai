# 任务收敛原则：Moodify 智能体任务工程纪律

> 发散任务消耗 token，收敛任务产生结果。  
> 复杂目标不能直接交给执行智能体，必须先被压缩、拆解、边界化、验收化。

---

## 1. 核心判断

在 Moodify 的多智能体开发流程中，一个重要规律已经显现：

```text
发散任务 = 高 token 消耗 + 高跑偏概率 + 高返工成本
收敛任务 = 低 token 消耗 + 高执行稳定性 + 高验收确定性
```

AI 并不是不能完成复杂任务，而是复杂任务如果没有被拆解成清晰边界，智能体会把大量 token 消耗在：

```text
理解任务
猜测意图
补全上下文
判断优先级
选择修改范围
解释不确定性
处理跑偏结果
反复纠错
```

这些消耗并不直接产生代码成果。

真正能产生结果的任务，必须是收敛的。

---

## 2. 任务收敛原则

**任务收敛原则**可以定义为：

```text
一个任务的执行效率，取决于它的收敛程度。
任务越发散，token 越多用于理解和猜测；
任务越收敛，token 越多用于执行和验证。
```

换句话说：

```text
有效执行 = 智能体能力 × 任务收敛度 × 上下文清晰度 × 验收明确度
```

反过来：

```text
token 浪费 = 任务发散度 × 上下文缺失 × 边界不清 × 验收模糊
```

---

## 3. 什么是发散任务？

发散任务通常长这样：

```text
把项目整理一下
优化一下 API
完善 CLI
检查哪里有问题
把 Moodify 做成完整软件
让 Claude 看看有没有 bug
```

这些任务的问题是：**没有边界**。

智能体会开始猜：

```text
是不是要改 README？
是不是要改 API？
是不是要动 CLI？
是不是要重构 workflow_engine？
是不是要新增测试？
是不是要清理旧系统？
是不是要更新版本号？
```

一旦开始猜，token 就会被消耗在路径选择上，而不是执行上。

---

## 4. 什么是收敛任务？

收敛任务长这样：

```text
只修改 cli.py
把 analyze 绑定到 cmd_v01_analyze
把 process 绑定到 cmd_v01_process
新增 presets 命令
旧系统改名 legacy-analyze / legacy-process
不要修改其他文件
完成后运行 5 条测试命令
```

收敛任务的特征是：

```text
目标唯一
文件唯一
动作明确
禁止项清楚
验收标准明确
失败路径明确
```

智能体不需要再判断“我要不要做别的”，它只需要完成一个确定动作。

---

## 5. 发散任务与收敛任务对比

| 维度 | 发散任务 | 收敛任务 |
|---|---|---|
| 目标 | 模糊 | 明确 |
| 修改范围 | 不确定 | 指定文件 |
| 智能体行为 | 自由猜测 | 按步骤执行 |
| token 消耗 | 高 | 低 |
| 跑偏概率 | 高 | 低 |
| 验收方式 | 主观判断 | 命令 / 输出 / 文件 |
| 适合对象 | ChatGPT 这类架构智能体 | Claude B / Claude C 这类执行智能体 |
| 结果质量 | 不稳定 | 可复现 |

---

## 6. 发散任务不能直接交给执行智能体

不能这样派任务：

```text
Claude B，帮我把 CLI 整理一下。
```

因为这会让 Claude B 自己判断：

```text
改哪些命令？
保留旧系统吗？
参数怎么改？
需不需要更新 README？
需不需要改 API？
```

正确写法应该是：

```text
Claude B，只修改 cli.py。

目标：
1. analyze → cmd_v01_analyze
2. process → cmd_v01_process
3. presets → cmd_v01_presets
4. legacy-analyze → 旧 cmd_analyze
5. legacy-process → 旧 cmd_process

禁止：
1. 不要修改 api/main.py
2. 不要修改 v01_pipeline.py
3. 不要删除旧系统
4. 不要新增依赖

验收：
1. moodify analyze test.wav 成功
2. moodify process test.wav --preset clean_master 成功
3. moodify presets 成功
4. moodify legacy-analyze test.wav 成功
5. git status 只显示 cli.py
```

这才是智能体能稳定执行的任务。

---

## 7. 智能体能力梯度

不同智能体适合处理不同任务层级。

```text
ChatGPT：
负责发散问题的收敛化、架构判断、任务拆解、风险判断。

Claude A：
负责读取代码事实、整理目录、收集报错、生成交接单。

Claude B：
负责执行收敛任务、修改指定文件、运行命令、提交 Git。

Claude C：
负责机械验收、记录结果、粘贴报错，不做复杂判断。
```

不能把所有智能体当成同一种劳动力。

智能体之间存在真实的能力差异、理解差异、上下文差异和稳定性差异。

因此：

```text
强智能体负责判断
中智能体负责执行
弱智能体负责记录与检查
```

---

## 8. Moodify 多智能体工作流

Moodify 的正确任务流应该是：

```text
发散问题
  ↓
ChatGPT 收敛成任务单
  ↓
Claude B 执行
  ↓
Claude C 检查事实
  ↓
Claude A 汇总交接
  ↓
GitHub 沉淀
```

而不是：

```text
发散问题
  ↓
直接丢给 Claude
  ↓
大量 token 消耗
  ↓
跑偏
  ↓
返工
```

---

## 9. 执行智能体的任务格式

任何交给 Claude B / Claude C 的任务，都必须包含以下结构：

```text
【任务编号】

【任务名称】

【负责人】

【任务目标】

【允许修改】

【禁止修改】

【输入材料】

【执行步骤】

【验收标准】

【失败处理】

【输出格式】
```

如果一个任务没有：

```text
允许修改
禁止修改
验收标准
失败处理
```

那么它还没有收敛，不允许执行。

---

## 10. 禁止交给执行智能体的模糊指令

以下指令禁止直接交给 Claude B / Claude C：

```text
优化一下
整理一下
完善一下
看看哪里有问题
重构一下
把项目做好
把功能做完整
你自己判断
按你的理解改
```

必须改写为：

```text
只修改哪个文件
完成哪个函数
运行什么命令
输出什么结果
通过什么测试
失败后如何汇报
```

---

## 11. 失败处理规则

如果智能体在任务中失败，不允许继续猜测式乱改。

必须停止，并输出：

```text
【失败转交单】

【任务编号】

【失败步骤】

【执行命令】

【完整报错】

【已修改文件】

【git status】

【请求】
请 ChatGPT 判断下一步。
```

这条规则尤其适用于 Claude C。

Claude C 不应该主动修复代码，除非用户明确授权。它默认只做机械检查。

---

## 12. Moodify 当前阶段的工程纪律

Moodify 当前阶段不是追求“大而全”，而是追求：

```text
小闭环
可运行
可验证
可提交
可回滚
```

当前主线应该持续围绕：

```text
导入音频
  ↓
生成频谱图
  ↓
生成诊断报告
  ↓
选择处理预设
  ↓
导出优化音频
```

任何偏离这个闭环的任务，都必须被标记为：

```text
future
experimental
legacy
```

不能进入 v0.1.0 主线。

---

## 13. 最终原则

Moodify 的智能体任务工程纪律可以总结为：

```text
大目标不直接执行。
复杂任务先降维。
发散任务交给 ChatGPT。
执行任务必须收敛。
每个任务只给一个主负责人。
每个智能体只做自己能稳定完成的事。
每个任务必须可验证。
失败立即停止并回报。
```

一句话总结：

> 不要让智能体理解整个世界。  
> 只让它完成一个清楚的小动作。

---

## 14. 工程口号

```text
发散任务消耗 token。
收敛任务产生结果。

未收敛的任务，不允许执行。
未验收的修改，不允许进入下一步。
未提交的阶段，不允许继续扩展。
```

这就是 Moodify 从“聊天式开发”进入“智能体工程管理”的分界线。
