# DeepSeek API 方案：RAG + API = 学习不训练

**日期**：2026-05-28
**作者**：云景台
**问题**：如果用 DeepSeek API 代替自己训练模型，行不行？推理一下。

---

## 零、直接回答

**可行，而且是当前阶段更务实的选择。**

自己训练模型的上限更高，但需要数据、基础设施、持续的 ML 工程投入。DeepSeek API + RAG 用 20% 的复杂度达到 80% 的效果，而且保留了"越用越好"的能力。

关键洞察：**RAG + API = 学习不训练。** 模型权重不变，但每次请求的上下文越来越丰富。系统在变聪明，但不需要训练任何东西。

---

## 一、为什么 API-only 比训练更适合当前阶段

### 1.1 对比

| | 自己训练 | DeepSeek API + RAG |
|---|---|---|
| 初始效果 | 差（需要训练数据） | 好（API 零样本推理强） |
| 进化能力 | 强（模型权重持续更新） | 中（依赖检索质量和 prompt 工程） |
| 上限 | 高（模型可以学到音频特有的模式） | 中高（受限于 prompt 长度和检索精度） |
| 基础设施 | 需要 GPU、训练流水线、模型版本管理 | 零 |
| 工程复杂度 | 极高 | 低 |
| Day 1 可用性 | 不可用（需要先收集数据训练） | 立即可用 |
| 离线能力 | 强（模型本地部署） | 弱（核心推理依赖网络） |
| 成本 | GPU 租赁 + 工程人力 | $0.001-0.01/次 |
| 隐私 | 完全本地 | 诊断向量上传（18 个数字，不可逆） |

### 1.2 为什么训练方案在这个阶段不现实

上一轮推导出的"蒸馏模型"方案有一个隐含前提：**有足够的训练数据。**

```
蒸馏模型需要的训练数据:
  ├─ 合成数据: LLM 生成的 10000 个样本 ← 可以用 DeepSeek 生成
  ├─ 真实 A/B 数据: 至少 500-1000 个样本 ← 需要时间积累
  └─ 覆盖诊断空间: 需要多样化的输入 ← 需要用户量

在用户量为 0 的时候，蒸馏模型只能用合成数据训练。
合成数据训练的模型，本质上就是 LLM 的一个有损压缩版本。
那为什么不直接用 LLM？——至少它是无损的。
```

**训练不是免费的午餐。没有真实数据，训练只是在复制 LLM 的能力到一个更小的模型里——而且一定会损失精度。**

等到有 10000+ 真实用户反馈样本时，再考虑训练。现在训练是过早优化。

## 二、DeepSeek API + RAG 的架构

### 2.1 核心流程

```
用户拖入文件
  ↓
诊断引擎: 18 参数 + 5 缺陷 (17秒，本地)
  ↓
知识库检索: 查找历史上最相似的 K 个案例 (< 100ms，本地)
  ↓
Prompt 组装:
  ├─ 系统提示词 (固定的 EWE 理论框架)
  ├─ 当前诊断数据 (18 参数)
  ├─ 用户意图 (自然语言或自动推断)
  ├─ 相似案例 (Top-5 的 诊断+参数+结果)
  └─ 约束规则 (风险门控 + 安全区间)
  ↓
DeepSeek API: 推理 → 返回结构化 JSON (2-5秒)
  ↓
约束层验证: 参数在安全范围内？缺陷被覆盖？(确定性，本地)
  ↓
DSP 执行: pedalboard 链 (3秒，本地)
  ↓
用户试听 + 反馈
  ↓
(诊断, 参数, 反馈) → 写入本地知识库
```

**音频数据从不离开用户机器。传到 DeepSeek 的只有 18 个数字的诊断向量和用户意图文本。**

### 2.2 为什么这个架构能"越用越好"

```
第 1 次处理:
  Prompt: "诊断: SubPresence=-6.2, AirBand=-17.1, ... 目标: 温柔觉醒"
  DeepSeek: 零样本推理 → 给出参数
  质量: 基于通用音频知识，可能不错但不会特别精准

第 100 次处理:
  Prompt: "诊断: SubPresence=-6.2, AirBand=-17.1, ...
           相似案例 1: SubPresence=-5.8, 用了 P05=+2.5dB, 用户满意
           相似案例 2: SubPresence=-6.5, 用了 P05=+2.8dB, 用户满意
           ...
           目标: 温柔觉醒"
  DeepSeek: 看到相似案例的参数模式 → 给出更精准的推荐
  质量: 基于真实用户反馈，比零样本推理更准

第 10000 次处理:
  Prompt: 包含 5 个高度相似、高置信度的案例
          知识库已有 10000 条记录
          检索精度已经非常高
  DeepSeek: 结合大量先例 + 当前诊断 → 接近最优
  质量: 逼近这个架构的上限
```

**模型没变，但上下文变了。** 这是 RAG 的核心价值——用检索替代训练。

### 2.3 离线降级方案

当 DeepSeek API 不可用时（无网络、服务故障）：

```
降级策略:
  1. 纯 RAG 模式: 检索相似案例 → 加权平均参数 → 应用
     质量: 中等（没有 LLM 推理，只有统计聚合）
     
  2. 无案例时: 回退到 8 个锚点工艺卡
     质量: 基础（传统预设模式）

用户体验:
  在线: "基于 AI 分析和 100 个相似案例的经验，推荐以下处理方案..."
  离线: "当前离线，使用本地经验为你推荐处理方案..."
```

两者都能工作，差异在于推荐质量。这个降级策略保证了软件在**任何时候都可用**。

### 2.4 成本分析

DeepSeek 的定价（2026 年参考）：
- 输入: ~$0.07/百万 tokens
- 输出: ~$0.28/百万 tokens

一次典型调用：
- 输入: ~2000 tokens（系统 prompt + 诊断 + 5 个案例 + 用户意图）
- 输出: ~800 tokens（JSON 参数 + 解释）
- 成本: (2000 × 0.07 + 800 × 0.28) / 1M ≈ **$0.0004**

**每次处理约 $0.0004。** 如果用户迭代 3 次，$0.0012。1000 次处理 ≈ $0.40。

如果担心成本：**可以把 DeepSeek API Key 作为用户自己的配置，Moodify 不自带 API Key。** 用户注册 DeepSeek 账号，填入 Key，开始使用。Moodify 不承担 API 费用。

## 三、和上一版蒸馏方案的对比

### 3.1 共识点

两种方案在以下方面一致：
- 诊断引擎是确定性的、本地的
- DSP 执行是确定性的、本地的
- 知识库需要本地存储和检索
- LLM 的推理能力是核心价值
- 人类反馈是最终校准信号

### 3.2 分歧点

| | 蒸馏方案 | API + RAG 方案 |
|---|---|---|
| LLM 调用时机 | 离线，每周一次 | 在线，每次请求 |
| LLM 调用频率 | O(1) | O(N) |
| 推理延迟 | < 1ms | 2-5s |
| 推理成本 | 0 | ~$0.0004/次 |
| 模型进化 | 权重更新（强） | Prompt 更新（中等） |
| 离线能力 | 完全离线 | 降级可用 |
| 精度上限 | 理论上更高 | 受限于检索 + prompt |
| 工程复杂度 | 需要训练流水线 | 只需要 API 调用 |
| Day 1 可用性 | 不可用 | 立即可用 |

### 3.3 什么时候应该切换到训练方案

```
信号 1: API 调用量超过 10 万次/月 → 成本开始显著
信号 2: 知识库超过 5 万条记录 → 检索质量有足够数据支撑训练
信号 3: 用户反馈数据 > 5000 个 A/B 标签 → 有监督信号可以训练
信号 4: 诊断空间中出现了 API 零样本推理覆盖不好的区域 → 泛化需求

四个信号同时满足时，蒸馏方案的优势（离线、免费、低延迟）开始超过 API 方案。
在此之前，API + RAG 是更务实的选择。
```

## 四、深入分析：API 方案的上限在哪

### 4.1 什么情况下 API 方案不如训练方案

**场景 1：大规模批量处理**

用户要处理 1000 首歌。API 方案：1000 次 API 调用 + 1000 次上下文检索 = 成本 $0.40 + 每个请求都带 2000 tokens 的相似案例 = 浪费。

训练方案：一次模型推理 < 1ms，零成本。1000 首歌秒级完成。

**场景 2：高度专业化的处理需求**

用户群体稳定后，系统积累了大量同质化数据。这些数据中蕴含的模式，API 永远发现不了——因为每次 API 只看 K 个案例，看不到全局。

训练方案：模型从全部数据中学习全局模式，可以发现 API 看不见的规律。

**场景 3：完全离线环境**

录音棚常常没有网络。API 方案降级到纯 RAG，失去了 LLM 的推理能力，只剩下统计聚合。

训练方案：蒸馏模型本地运行，完全离线，推理质量和在线一样。

### 4.2 API 方案做对了什么

1. **零基础设施** — 不需要 GPU、不需要训练、不需要 ML 工程师
2. **立即可用** — Day 1 就能给出专业级的参数推荐
3. **自动进化** — RAG 让推荐质量随使用量增长
4. **成本极低** — DeepSeek 的价格使得 API 调用几乎免费
5. **隐私安全** — 音频数据从不离开用户机器，只上传 18 个诊断数字
6. **简单可解释** — 没有黑盒模型，每个推荐都可以追溯到具体的相似案例

### 4.3 最适合的起点

**API + RAG 是 Day 1 的最优架构。** 不是因为它的上限最高，而是因为它在零数据、零基础设施的条件下就能提供接近上限的体验。

等到数据积累了、用户量上来了、找到了 product-market fit，再投资训练方案。

你的工作对象是 AI 生成的音乐——它们不是成品，而是"原始情绪波场"。

你的任务：
读取诊断数据 → 理解用户意图 → 输出 DSP 参数推荐 → 解释推理

参数体系（15 个 DSP 参数）：
P01 vocal_presence_freq [2000-4000 Hz]

## 六、知识库的 RAG 设计

### 6.1 案例存储结构

```python
case = {
    "id": "case_00001",
    "diagnosis_vector": [-6.2, -3.8, 0.72, -17.1, -4.5, 8.3, 4.1, ...],  # 18D
    "diagnosis_labels": {
        "defects": ["DEF-S-001", "DEF-S-003", "DEF-S-002"],
        "emotion_direction": "gentle",
        "genre_hint": "piano_ballad"
    },
    "target_emotion": "温柔觉醒",
    "applied_params": {"P01": 3000, "P02": 2.8, ...},
    "outcome": {
        "whs_delta": 9.0,
        "user_rating": 1,  # 1=satisfied, 0=neutral, -1=unsatisfied
        "user_comment": "很好"
    },
    "timestamp": "2026-05-28T18:00:00Z"
}
```

### 6.2 检索策略

```
第一层: 向量相似度
  18D 诊断向量的余弦相似度 → Top-50

第二层: 标签过滤
  在 Top-50 中，优先选择:
    - 相同目标情绪
    - 相同情绪方向
    - 用户评分 ≥ 0

第三层: 多样性
  从筛选后的候选池中选 5 个案例
  确保 5 个案例的参数不是全相同的
  → 给 LLM 多样化的参考
```

### 6.3 知识库的进化

```
初始（0 条记录）:
  检索为空 → Prompt 中"相似案例"部分为空
  → LLM 纯零样本推理

成长（100 条记录）:
  检索质量一般，但开始出现匹配
  → LLM 参考少量先例

成熟（1000 条记录）:
  大多数新诊断能找到 3-5 个相似案例
  → LLM 明显受先例引导，精度提升

饱和（10000 条记录）:
  几乎所有常见诊断模式都被覆盖
  → LLM 在高度信息化的上下文中推理
  → 接近 API 方案的上限

突破（> 50000 条）:
  → 考虑训练蒸馏模型
```

## 七、最终判断

### API + RAG 方案的优势

1. **今天就能做** — 不需要等数据、等训练、等 GPU
2. **效果从 70 分起步** — DeepSeek 的零样本推理已经很好了
3. **越用越好** — RAG 让每次处理比上一次更准
4. **简单** — 一个 API 调用 + 一个向量数据库 + Prompt 工程
5. **成本可忽略** — 每次 $0.0004，甚至可以由用户自带 API Key

### API + RAG 方案的问题

1. **离线时降级** — 从 LLM 推理降到统计聚合，质量下降
2. **上限受限于检索精度** — 检索不到相关案例时，退化为零样本
3. **大规模批量时成本线性增长** — 1000 首歌 = 1000 次 API 调用
4. **Prompt 维护成本** — 系统提示词需要持续优化

### 和上一版蒸馏方案的关系

**不互斥。API + RAG 是第一阶段，蒸馏是第二阶段。**

```
第一阶段 (Day 1 → 10000 用户):
  API + RAG
  目标: 快速上线，验证产品价值，积累数据

第二阶段 (10000+ 用户):
  数据充足 → 启动蒸馏模型训练
  目标: 离线可用、零成本推理、极低延迟

第三阶段 (成熟期):
  蒸馏模型为主要推理引擎
  API 用于处理边缘情况和模型更新
```

### 一句话

**DeepSeek API + RAG 是"学习不训练"——用检索替代权重更新，用上下文丰富替代模型进化。这个方案今天就能做，效果从 70 分起步，越用越接近 90 分。等到数据积累到 5 万条以上，再投资训练方案。过早训练是过早优化。**
