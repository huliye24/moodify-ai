## 零、先认清一个事实

当前 Moodify 的"AI"在哪里？

```
诊断引擎：FFT + 启发式规则 → 这是信号处理，不是 AI
工艺卡匹配：缺陷 ID 查表 → 这是数据库查询，不是 AI
DSP 链：固定参数 → pedalboard → 这是效果器，不是 AI
```

**当前整个管线，AI 参与度为零。**

诊断是算法，处理是算法，匹配是查表。大模型没有出现在任何一个关键决策环节。

所谓的"8 种情绪工艺卡"，本质是 8 个预设（preset）。和吉他效果器的"Rock / Jazz / Blues"预设没有本质区别。

**这不是 AI 原生软件。这是传统 DSP 软件换了一套理论词汇。**

## 一、重新定义问题

普通软件回答的是：

> 用户选了一个预设，软件执行预设 → 完成任务

AI 原生软件应该回答的是：

> 软件理解了这个声音，理解了用户的意图，自主推理出处理方案，执行并解释 → 完成创作

这是两个完全不同的产品。

### 1.1 大模型能做什么（音频领域）

大模型**不能**听音频。但它**能**做这些事：

**能力 1：阅读和理解音频诊断数据**

18 个参数摊开在面前，大模型可以像医生读化验单一样理解它们：

```
"S1_SubPresence = -6.2dB → 次低频严重不足，身体感会很弱"
"S4_AirBand = -17.1dB → 高频几乎完全缺失，声音会闷、没有空气感"
"D1_LRA = 8.3LU → 动态适中，不算压平也不算太跳动"
"SP1_Correlation = 0.72 → 立体声宽度中等偏窄，空间感有限"
```

人类调音师读到这些指标只能凭经验模糊判断，大模型可以精确推理每个参数的物理含义和感知后果。

**能力 2：自然语言 → 声学参数的精确映射**

```
用户："像深夜爵士俱乐部里的呢喃"
  ↓ 大模型推理
深夜 → 暗色调 → 高频衰减 -2～-4dB
爵士俱乐部 → 温暖中低频 + 适度混响 → Low Shelf +3dB @ 200Hz, Reverb T60 1.5s
呢喃 → 极度亲密 → 人声 Peak EQ +3dB @ 3kHz, 压缩比 < 2:1, 混响干湿度 0.12
空间 → 小型密闭空间 → 立体声宽度 0.8-1.0, 早期反射模拟
```

这个映射不是查表能做到的——因为"深夜爵士俱乐部里的呢喃"不是一个预设选项。它需要理解场景、情绪、声学环境和人声特征，然后综合推理。

**能力 3：生成和评估假设**

```
诊断: 人声偏远(-6dB) + 高频缺失(-17dB) + 低频温暖感不足(-3.8dB)

大模型生成假设:
  H1: 先修复人声存在感(Peak EQ 3kHz +3dB)，再补高频空气感(High Shelf 10kHz +4dB)，
      最后加低频温暖(Low Shelf 200Hz +2.5dB)。预期：人声贴耳 + 通透 + 温暖。
      风险：高频+4dB 可能让原本 -17dB 的缺失变成 +4dB 的过度。

  H2: 先补低频温暖，建立基础，再修复人声，最后轻补高频。
      预期：温暖基底上的人声增强，高频不过量。
      风险：低频先加可能让人声增强后整体偏闷。

  H3: 保持高频不做大补（-17dB 是风格特征而非缺陷），只修复人声和低频，
      保留暗调风格。预期：温暖亲密的暗调质感。
      风险：用户可能期望更亮的声音。
```

然后大模型会问用户："你的原始音频高频很暗（-17dB），这可能是风格特征而非缺陷。你想要保留这种暗调质感，还是需要增加通透感？"

**这是真正的推理，不是 if-else。**

**能力 4：从失败中学习**

```
同一首歌，用户选了"温柔觉醒"工艺卡，处理完觉得人声太亮。
大模型记录：
  - 这首歌的人声原始 centroid 偏高 (3200Hz)
  - 默认的 P02_vocal_presence_gain = 2.5dB 在这首歌上过亮了
  - 对于 centroid > 3000Hz 的人声，gain 应降到 1.5-2.0dB
  - 这条规则沉淀到工艺知识库
```

每一次处理都在进化。用的越多，越准确。这是传统 DSP 软件永远做不到的。

## 二、AI 原生产品形态

### 2.1 核心交互模型

不是"上传 → 选预设 → 下载"。

是"**对话式音频工程**"。

```
用户: [拖入一首歌]

Moodify: 我已经分析了这首歌。它的人声偏远、高频偏暗、低频温暖感不足。
         整体情绪胚胎偏向温柔方向，但空间感偏宽，不太适合亲密表达。
         你想把它变成什么样的感觉？

用户: 像一个温柔的拥抱，很温暖很近

Moodify: 明白了。我会：
         1. 增强人声存在感（+2.8dB @ 3kHz），让人声贴耳
         2. 补充低频温暖感（+2.5dB @ 200Hz），增加拥抱的厚度
         3. 收窄立体声宽度（0.9→0.7），营造近距离感
         4. 加短混响（T60 0.8s, dry/wet 0.18），亲密不空旷
         5. 轻压缩（2:1, 慢启动 20ms），保留呼吸感
         6. 高频只补 +1.5dB（保留温柔暗调，不过亮）

         要不要听听看？
         [开始处理] [调整某个参数]

用户: 低频再加一点

Moodify: 低频从 +2.5dB 加到 +3.2dB @ 200Hz。
         注意：超过 +3.5dB 可能会让声音变闷，现在 +3.2dB 是安全上限。
         [重新处理]

用户: 好了，这样可以

Moodify: 处理完成。WHS 从 72 提升到 81。这个处理方案我已经记住了，
         下次遇到类似的人声偏远 + 高频偏暗的歌曲，会优先用这个参数组合。
```

### 2.2 关键区别

| | 传统方案 | AI 原生方案 |
|---|---|---|
| 工艺选择 | 8 个固定预设 | 无限种组合，实时推理生成 |
| 参数决策 | 预设的 rec 值 | 根据诊断数据动态计算 |
| 用户意图 | 从下拉菜单选情绪 | 自然语言描述，任何表达都行 |
| 处理透明度 | 黑盒 | 每一步有解释和理由 |
| 迭代方式 | 重新选预设再来一次 | 对话式微调，精准到单个参数 |
| 知识积累 | 不积累 | 每次处理都在学习 |
| 边缘情况 | 超出预设范围的无法处理 | 自主推理处理方案 |

### 2.3 大模型在系统中的角色

```
┌─────────────────────────────────────────────────────┐
│  信号处理层（确定性，快）                              │
│  ├─ 诊断引擎: 音频 → 18 参数 WaveState                 │
│  ├─ DSP 引擎: 参数 → pedalboard → 处理后的音频         │
│  └─ 分析工具: 频谱、响度、相位、瞬态                    │
├─────────────────────────────────────────────────────┤
│  推理决策层（AI，慢但聪明）                             │
│  ├─ 诊断解读: 18 参数 → 自然语言诊断报告                │
│  ├─ 意图理解: 用户描述 → 声学目标                      │
│  ├─ 工艺生成: 声学目标 + 诊断 → DSP 参数链              │
│  ├─ 风险评估: 参数链 → 风险预测 + 安全边界              │
│  ├─ 结果评估: 处理前后对比 → 效果判断 + 改进建议         │
│  └─ 知识沉淀: 成功案例 → 工艺知识库更新                  │
└─────────────────────────────────────────────────────┘
```

信号处理层不依赖 AI，确定性运行，速度快。

推理决策层由大模型驱动，每一次调用都可能产生不同的结果——不是 bug，是智能。

## 三、技术架构

### 3.1 大模型调用策略

```
轻量决策（本地，毫秒级）：
  ├─ 缺陷分类: 基于阈值的自动检测（不需要 LLM）
  ├─ 格式验证: 文件类型检查（不需要 LLM）
  └─ 响度匹配: 固定算法（不需要 LLM）

中度决策（LLM 一次调用，2-10 秒）：
  ├─ 诊断解读: 18 参数 → 自然语言报告
  ├─ 工艺生成: 用户意图 + 诊断 → DSP 参数
  └─ 风险评估: 参数链 → 风险判断

重度决策（LLM 多次调用，10-30 秒）：
  ├─ 多轮对话: 用户来回微调
  ├─ 方案对比: A/B/C 三个方案分析优劣
  └─ 知识归纳: 多次处理 → 经验总结
```

关键原则：**能本地算的不用 LLM，需要理解的才用 LLM。**

### 3.2 LLM 的 System Prompt 设计

这是整个系统的灵魂。不是简单的"你是一个音频工程师"，而是：

```
你是 Moodify 的情绪波场显影引擎的核心推理模块。

你的理论基础是情绪波工程学 (Emotional Wave Engineering)。
核心原则文档: PRINCIPLE-001。

你的工作对象是 AI 生成的音乐（Suno/Udio 等），它们不是成品，
而是"原始情绪波场"——包含情绪胚胎但未经显影的声音材料。

你有以下能力：
1. 阅读 18 参数 WaveState 诊断数据，理解其声学和感知含义
2. 将用户的自然语言意图映射为具体的声学目标
3. 生成 DSP 处理参数链（15 参数体系）
4. 评估处理方案的风险（过度处理、情绪失真、听觉疲劳）
5. 用自然语言解释你的推理过程

你必须遵守的不可牺牲原则：
- 诊断先于处理（没有诊断数据时拒绝给出处理建议）
- 情绪先于参数（你的每个决策必须服务于情绪目标）
- 风险门控不可绕过（预测到风险时必须警告用户）
- 人耳是最终仲裁者（你的推理是建议，不是判决）

你处理的是专业音频工程任务。你的推理必须精确到具体参数值。
不要说"适当增加高频"，要说"+2.5dB High Shelf @ 10000Hz"。
```

### 3.3 工艺生成的推理链

LLM 收到诊断数据 + 用户意图后，按以下链条推理：

```
Step 1: 理解现状
  "这首歌的波场状态是..."
  - 频谱: 低频存在感偏低(-6.2dB)，中频清晰度 0.72，高频严重缺失(-17.1dB)
  - 动态: LRA 8.3LU，微动态 1.1LU，动态偏平但不严重
  - 空间: 相关性 0.72，宽度健康，但前后深度只有 5.2dB
  - 层级: 人声 SNR 12.3dB，可辨识，但低频清晰度只有 0.18（浑浊）
  - 情绪: 方向偏温柔(gentle)，丰富度中等(0.6)，疲劳风险低(0.28)

Step 2: 理解目标
  "用户想要'温柔的拥抱'，这对应..."
  - 情感: 温暖、亲密、安全感
  - 声学特征: 近讲人声 + 温暖低频 + 短混响 + 窄空间 + 柔和动态
  - 目标区间: E 0.55-0.80, D 0.50-0.70, S 0.30-0.50, T 0.40-0.60, H 0.45-0.65

Step 3: 计算差距
  "现状 vs 目标..."
  - 低频存在感 -6.2dB → 需要 +2～+4dB (目标区间内)
  - 高频 -17.1dB → 风格特征，只做轻微补偿 +1.5dB
  - 人声 SNR 12.3dB → 足够，但存在感需要频率塑造
  - 空间前后深度 5.2dB → 需要增加混响来增强深度感
  - 相关性 0.72 → 偏窄，适合拥抱的亲密感，保持不变

Step 4: 生成参数
  P01 vocal_presence_freq = 3000Hz (标准存在感频率)
  P02 vocal_presence_gain = +2.8dB (补偿人声偏远，但不超过 +3.5dB)
  P03 vocal_presence_q = 0.7 (宽 Q，自然过渡)
  P04 proximity_low_freq = 200Hz (温暖感频率)
  P05 proximity_low_gain = +2.5dB (补偿低频不足，在安全范围内)
  ...
  P15 high_shelf_gain = +1.5dB (保守补偿，避免破坏暗调风格)

Step 5: 风险评估
  "这个方案的风险..."
  - 高频补偿 +1.5dB 安全（上限 +3dB）
  - 低频 +2.5dB + 存在感 +2.8dB 同时作用 → 可能需要微调中频避免过于前压
  - 总体风险：绿色（低风险）
```

## 四、具体实现路径

### 4.1 最小可行 AI 原生版本

第一版不需要完整的多轮对话。只需要一个核心能力：**LLM 读取诊断数据 → 生成自然语言解读 + 推荐参数**。

```
用户拖入文件
  ↓
诊断引擎提取 18 参数（< 20 秒）
  ↓
诊断数据发送给 LLM
  ↓
LLM 返回:
  1. 自然语言诊断报告（"这首歌的问题是什么"）
  2. 推荐的情绪方向（"最适合往哪个方向显影"）
  3. 推荐的 DSP 参数（15 个参数的精确值 + 理由）
  4. 风险警告
  ↓
用户确认或调整
  ↓
DSP 执行（< 10 秒）
  ↓
用户听到结果
```

### 4.2 关键的 Prompt 工程

LLM 需要非常精确的 prompt 来输出**结构化**的参数：

```python
SYSTEM_PROMPT = """
你是 Moodify 的情绪波场显影推理引擎。
你的输出必须是严格的 JSON 格式，包含以下字段。
每个参数值必须是对应物理量的合理数值。

{
  "diagnosis_narrative": "用自然语言描述这首歌的波场状态（100-200字）",
  "recommended_emotion": "推荐的情绪方向",
  "emotion_confidence": 0.0-1.0,
  "parameters": {
    "P01_vocal_presence_freq": {"value": 3000, "unit": "Hz", "reasoning": "..."},
    "P02_vocal_presence_gain": {"value": 2.5, "unit": "dB", "reasoning": "..."},
    // ... P01-P15
  },
  "risk_assessment": {
    "level": "green | yellow | orange | red",
    "warnings": ["具体的风险描述"],
    "mitigations": ["降低风险的具体建议"]
  },
  "alternative_approaches": [
    {"name": "备选方案名称", "description": "简要描述", "parameter_diff": {...}}
  ]
}
"""
```

### 4.3 技术选择

**LLM 选择**：

| 方案 | 延迟 | 成本 | 质量 | 离线能力 |
|------|------|------|------|----------|
| Claude API (Sonnet) | 2-5s | $0.01/次 | 极高 | 需要网络 |
| Claude API (Opus) | 5-15s | $0.05/次 | 最高 | 需要网络 |
| GPT-4o | 1-3s | $0.01/次 | 很高 | 需要网络 |
| 本地模型 (Llama 8B) | 0.5-2s | 免费 | 中等 | 完全离线 |
| 本地模型 (Qwen 32B) | 2-5s | 免费 | 高 | 完全离线 |

**推荐策略**：
- 默认使用本地模型（离线可用，不依赖网络）
- 本地模型做诊断解读 + 参数推荐
- 可选连接 Claude API 获得更高质量的推理
- 系统提示词内置参数约束，确保即使小模型也不会输出离谱值

### 4.4 知识闭环

```
每次处理:
  ├─ 诊断数据 (客观)
  ├─ LLM 推理过程 (可解释)
  ├─ 处理前后指标对比 (可量化)
  ├─ 用户反馈 (喜欢/不喜欢/调整了什么)
  └─ → 存入知识库

知识库累积后:
  ├─ 对类似诊断自动推荐历史上用户满意度高的参数
  ├─ 新歌的推荐不再是零样本推理，而是基于历史案例的检索增强
  └─ 形成"这首歌像你之前处理过的 X，那次你用了 Y 参数，效果很好"
```

这是 RAG（检索增强生成）在音频处理中的应用：
- 诊断数据 → 向量嵌入 → 检索相似历史案例 → LLM 结合历史和新数据生成推荐

## 六、极限在哪里

### 6.1 大模型能突破的人类极限

人类调音师的极限：
- 一次只能专注听 1-2 个维度
- 经验积累受限于个人职业生涯（几百到几千首歌）
- 跨风格迁移困难（擅长摇滚的不一定懂氛围音乐）
- 疲劳后判断力下降
- 难以精确量化（"高频有点多"而不是"+2.3dB @ 10kHz 过量"）

大模型的极限：
- 同时分析 18 个参数，发现人类注意不到的交叉影响
- 每次决策可以检索历史上数千次处理的模式和结果
- 任何风格、任何情绪方向，只要理论框架能覆盖
- 不会疲劳
- 天然以精确数值思考和输出

**大模型不替代人耳，它替代"从症状到方案"的推理过程。** 人耳仍然做最终的审美判断（"我喜欢这个版本吗"），但中间的参数推导、风险评估、方案对比，大模型远超人脑。

### 6.2 真正的极限软件长什么样

不是"8 个预设"，而是"无限种显影"。
不是"选情绪"，而是"描述感觉"。
不是"按按钮"，而是"对话"。
不是"用一次就那样"，而是"越用越懂你"。

```
极限软件 = 诊断引擎（信号处理，确定性）
         + 推理引擎（大模型，智能性）
         + 知识引擎（累积学习，进化性）
         + 人耳（审美判断，最终仲裁）
```

## 七、路线图：从现在到极限

### 第一步：接入大模型（1-2 天）

- 替换工艺卡匹配逻辑：诊断数据 → LLM → 推荐参数
- 先用 Claude API 验证效果
- 输出从"CC-GA-001 预设"变为"LLM 生成的精确参数链"

### 第二步：自然语言交互（2-3 天）

- 用户输入意图描述，替代下拉菜单
- LLM 将自然语言映射为声学目标
- 对话式微调参数

### 第三步：知识闭环（3-5 天）

- 记录每次处理的诊断 + 方案 + 结果 + 反馈
- 实现案例检索（RAG）
- 新处理参考历史类似案例

### 第四步：本地模型（1 周）

- 研究本地部署方案
- 离线可用，隐私保护
- 可选云端模型（更高质量）

## 八、关键风险和应对

| 风险 | 应对 |
|------|------|
| LLM 输出的参数值不合理 | 参数约束层：每个参数有 hard min/max，超界自动剪裁 |
| LLM 调用延迟 | 本地模型用于快速响应，云端模型用于深度分析 |
| 离线不可用（云端 API） | 本地模型作为默认，云端作为可选增强 |
| 每次调用成本 | 本地模型零成本；云端 $0.01-0.05/首，可接受 |
| LLM 幻觉 | 参数约束 + 结构化输出 + 必须基于诊断数据推理 |
