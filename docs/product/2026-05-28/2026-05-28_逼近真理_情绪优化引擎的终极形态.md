## 零、上一步的结论还不够

上一步推导出的 AI 原生产品形态：

> 大模型读诊断 → 理解用户意图 → 生成参数 → 解释推理 → 对话式微调

这个方案比 8 个预设好了无数倍。但它有一个根本缺陷：

**大模型在猜。它没有验证自己的猜测。**

LLM 说 "+2.8dB @ 3kHz"，为什么是 2.8 而不是 2.3 或 3.1？因为它根据诊断数据和 prompt 推理出来的。但这个推理没有经过**实验验证**。它像一个医生开了处方但从不看病人吃了药之后的效果。

上一版方案的本质是：**LLM 替代了工艺卡查表，但仍然是一个开环系统。**

```
开环：诊断 → LLM 推理 → 参数 → DSP → 输出 → 人类判断 ✓/✗
                                                    ↑
                                          到这里才闭合，而且闭合在人脑里
```

真理级别的系统应该是：

```
闭环：诊断 → 多假设生成 → 并行处理 → 自动评估 → 选最优 → 输出 → 人类判断 → 反馈回系统
       ↑                                                              ↓
       └──────────────── 知识库更新 ←────────────────────────────────┘
```

闭环不在人脑里，闭环在系统里。

## 一、重新定义：从"工具"到"优化器"

### 1.1 核心命题

**情绪显影不是一个执行过程，是一个优化问题。**

```
给定:
  - 原始波场 W_raw（18 参数诊断结果）
  - 情绪方向 d（用户指定或系统推断）

找到:
  - 处理参数链 θ*（15 维向量）

使得:
  - EDSR(W_processed(θ), W_raw, d) 最大化

满足:
  - LFR(W_processed) < 安全阈值
  - 情绪安全区间约束
  - 处理链置信度 > 最低阈值
```

这是 PRINCIPLE-001 第 3.2 节的核心极限目标函数，但上一版方案没有真的去解这个优化问题——我们让 LLM 猜了一个 θ。

**猜不是优化。推理不是搜索。一个解不是最优解。**

### 1.2 情绪显影成功率可以被自动评估吗？

传统观点：不能。情绪是主观的，必须人耳判断。

真理观点：**可以逼近。** 因为：

1. **WHS（波场健康分）** 可以在处理前后自动计算。它衡量"结构是否更健康"——这是客观的。

2. **诊断距离** 可以计算：处理后 5D 向量与目标情绪 5D 向量的欧氏距离。距离变小 = 情绪方向在朝目标移动——这是客观的。

3. **已知缺陷的消除率** 可以计算：处理前有 N 个缺陷，处理后检测到几个——这是客观的。

4. **历史 A/B 胜率模式** 可以学习：过去 100 次，参数组合 X 在诊断类型 Y 上的 A/B 胜率是多少——这是统计的。

这四个信号合并起来，形成了一个**EDSR 代理指标**。它不是完美的（永远替代不了人耳），但它是**可计算的、可优化的、可以驱动搜索的**。

有了代理指标，系统就可以：

```
生成 θ₁ → 模拟处理 → 预估 EDSR₁ = 0.72
生成 θ₂ → 模拟处理 → 预估 EDSR₂ = 0.68
生成 θ₃ → 模拟处理 → 预估 EDSR₃ = 0.81  ← 选这个
```

**不需要真的处理三次，只需在参数空间中搜索。**

## 二、真理架构：情绪优化引擎

### 2.1 三层闭环

```
┌─────────────────────────────────────────────────────────┐
│  内环：参数搜索（自动，< 5 秒）                            │
│  ├─ 基于诊断数据，在 15 维参数空间中搜索                   │
│  ├─ 使用 EDSR 代理指标作为目标函数                         │
│  ├─ 约束：风险门控 + 安全区间 + 工艺卡推荐范围              │
│  └─ 输出：最优参数 θ* + 备选方案                           │
├─────────────────────────────────────────────────────────┤
│  中环：实验验证（自动，每次处理）                            │
│  ├─ 应用 θ*，生成处理版本                                  │
│  ├─ 对比处理前后的 WHS、缺陷、5D 距离                       │
│  ├─ 记录实际 Δ 与预估 Δ 的偏差                             │
│  └─ 偏差 > 阈值 → 修正代理指标权重                         │
├─────────────────────────────────────────────────────────┤
│  外环：人类反馈（人耳，不定期）                               │
│  ├─ A/B 盲测：原始 vs 处理                                │
│  ├─ 用户偏好数据回流                                      │
│  ├─ EDSR 真实值更新（不是代理指标）                         │
│  └─ 反馈驱动代理指标修正 + 工艺卡可信度更新                  │
└─────────────────────────────────────────────────────────┘
```

关键：**内环和中环是全自动的。外环是增量的人类反馈。三个环互相校正。**

### 2.2 参数搜索怎么做

15 维参数空间太大了，暴力搜索不可能。需要智能搜索。

**阶段 1：基于诊断的初始空间缩减**

```
诊断: SubPresence=-6.2dB → 低频需要增益
      → P04 范围缩到 [150, 250] Hz
      → P05 范围缩到 [1.5, 3.5] dB
      → 其他参数同理
      
15 维 → 缩为 8 维（有 7 个参数不需要调整）
每个维度离散化到 3-5 个候选值
总候选数：3^8 ≈ 6500 → 可暴力
```

**阶段 2：代理指标快速评估**

每个候选参数组合，不需要真的跑 DSP。用简化模型预估：

```
预估_WHS = f(θ, W_raw)   # 基于历史数据的回归模型
预估_5D = W_raw + J(θ)    # J 是雅可比矩阵，从历史数据学习
预估_EDSR = g(预估_WHS, 预估_5D, target)
```

最简单的实现：**用 LLM 做批量评估**。一次性发 50 个候选参数给 LLM，让它选出 top 3。

**阶段 3：Top-K 真实处理**

对 top 3 候选，真的跑 DSP（< 10 秒 × 3 = 30 秒），测量真实的 WHS 和 5D 变化，选出最优。

### 2.3 代理指标的进化

代理指标一开始不准确。但它会进化：

```
第 1 次处理：
  代理指标 EDSR_proxy 预测 = 0.75
  用户 A/B 选择 ✓（处理更好）
  EDSR_true = 1.0
  偏差 = 0.25

第 100 次处理：
  代理指标 EDSR_proxy 预测 = 0.78
  用户 A/B 选择 ✓
  EDSR_true = 1.0
  偏差 = 0.22（没变好）

第 1000 次处理：
  代理指标 EDSR_proxy 预测 = 0.82
  用户 A/B 选择 ✓
  EDSR_true = 1.0
  偏差 = 0.18（在收敛）

代理指标在逼近真实 EDSR。
```

这不是靠调公式参数（手工调权重），而是靠**数据驱动的自动校准**。每次处理，代理指标和真实反馈的偏差被用来修正代理模型。

这是机器学习，不是启发式规则。

## 三、大模型的真正角色：不是参数生成器

上一版方案把 LLM 定位为参数生成器——读取诊断，输出 15 个参数。

这低估了 LLM 的能力。

### 3.1 LLM 应该做什么

**角色 1：搜索空间设计师**

不是"给我参数"，而是"告诉我应该在哪些维度搜索，搜索范围是什么"。

```
输入: 诊断数据
输出:
  {
    "active_dimensions": ["P02", "P05", "P09", "P11", "P15"],
    "search_ranges": {
      "P02": {"min": 1.5, "max": 3.5, "step": 0.5},
      "P05": {"min": 1.5, "max": 3.5, "step": 0.5},
      "P09": {"min": -28, "max": -20, "step": 4},
      "P11": {"min": 0.12, "max": 0.25, "step": 0.04},
      "P15": {"min": 1.0, "max": 2.5, "step": 0.5}
    },
    "frozen_dimensions": {
      "P01": 3000, "P03": 0.7, ...
    }
  }
```

LLM 的推理能力用来**缩小搜索空间**——知道哪些参数需要调、哪些保持默认。

**角色 2：候选方案评估者**

不是"选一个最好的"，而是"给我排个序，解释为什么"。

```
输入: 50 组候选参数 + 诊断数据
输出: 排序后的 top 10 + 每组的评分理由
  "#1: EDSR_proxy=0.82 — 低频补偿充足(+2.5dB)，人声存在感适度(+2.8dB)，
       高频保守(+1.5dB)适合暗调风格，风险低"
  "#2: EDSR_proxy=0.78 — 低频更激进(+3.2dB)，但存在高频过度风险"
  ...
```

**角色 3：失败分析师**

当用户拒绝了处理结果，LLM 分析为什么。

```
输入: 诊断 + 参数 + ΔWHS + Δ5D + 用户反馈"太亮了"
输出:
  "高频补偿 +1.5dB 在这个案例中过亮了。原因：这首歌的原始 centroid
   已经是 3200Hz（偏高），即使 +1.5dB 也超出了人声的适宜范围。
   建议：对于 centroid > 3000Hz 的人声，P15 上限从 +3.0dB 降到 +1.0dB。
   这条规则建议写入知识库。"
```

**角色 4：知识蒸馏者**

从多次处理中提取可泛化的模式。

```
输入: 最近 100 次处理的诊断+参数+反馈数据
输出:
  "发现模式：
   1. SubPresence < -5dB 时，P05 最优值集中在 2.5-3.0dB（n=23, 胜率 78%）
   2. centroid > 3500Hz 时，用户偏好 P02 < 2.0dB（n=15, 胜率 87%）
   3. LRA < 6LU 时，压缩比 1.5-2.0 优于 2.0-2.5（n=31, 胜率 72%）
   建议更新工艺卡 rec 值。"
```

这些角色和"生成参数"有一个本质区别：**它们让 LLM 做的事情是它真正擅长的——理解、推理、归纳——而不是生成精确数值。**

精确数值靠搜索，搜索靠代理指标，代理指标靠数据校准。

## 四、从"一次对话"到"持续进化"

### 4.1 软件的生命周期

传统软件的进化：开发者写代码 → 发布新版本 → 用户下载更新。

真理级别软件的进化：**每一次使用都在进化。**

```
用户 A 处理了一首钢琴曲 → 系统学到了钢琴曲的低频补偿模式
用户 B 处理了一首电子乐 → 系统学到了电子乐的动态塑形模式
用户 C 处理了一首民谣   → 系统学到了民谣的空间宽度模式
```

所有用户共同训练同一个代理指标模型。模型越用越准。

### 4.2 联邦知识库

隐私敏感的本地处理 + 匿名化的参数模式上传：

```
本地: 所有音频数据留在用户机器上
云端: 只上传匿名的 (诊断特征向量, 最优参数, 用户偏好) 三元组
      不带音频，不带用户身份
      诊断特征向量不可逆（无法重构原始音频）
```

这样形成一个**去中心化的工艺知识进化网络**。

每个用户的每次处理，都在让所有用户的体验变好。这不是一个功能，这是软件的生命形态。

### 4.3 自我校准闭环

```
                ┌──────────────┐
                │  诊断引擎     │ ← 永远不变（确定性测量）
                └──────┬───────┘
                       │ 18 参数
                       ▼
                ┌──────────────┐
                │  搜索空间     │ ← LLM 根据诊断缩小搜索范围
                │  设计师       │
                └──────┬───────┘
                       │ 候选参数集
                       ▼
                ┌──────────────┐
                │  代理评估     │ ← WHS + 距离 + 缺陷 + 历史模式
                │  模型         │    持续从反馈中学习
                └──────┬───────┘
                       │ top-3 参数
                       ▼
                ┌──────────────┐
                │  DSP 引擎     │ ← 真实处理（确定性执行）
                └──────┬───────┘
                       │ 处理后的音频 + 真实指标
                       ▼
                ┌──────────────┐
                │  真实测量     │ ← 计算实际的 ΔWHS, Δ5D, Δ缺陷
                └──────┬───────┘
                       │ 预估 vs 真实偏差
                       ▼
                ┌──────────────┐
                │  代理模型     │ ← 用偏差修正模型
                │  校准器       │
                └──────┬───────┘
                       │
                       ▼
                ┌──────────────┐
                │  人类反馈     │ ← A/B 结果回流
                │  (不频繁)     │
                └──────────────┘
```

这是一个**自我改进的闭环系统**。关键特征：
- 内环全自动（搜索 → 评估 → 处理 → 测量 → 校准）
- LLM 在其中做推理和归纳，不是数值计算
- 数值计算由搜索和统计模型完成
- 人类反馈是外环，不阻塞内环运行

## 五、极限在哪：真理状态的五个特征

如果 Moodify 真的逼近了真理状态，它应该具备这五个特征：

### 特征 1：不需要用户有专业知识

用户不需要知道"EQ"、"压缩比"、"混响 T60"是什么。
用户只需要说"我想要温暖的感觉"或者"保持原来的感觉但更清晰"。
系统自己把意图翻译成搜索目标。

### 特征 2：处理方案是由数据决定，不是由预设决定

同一首歌，同样的意图，今天和明天给出的参数应该是一样的（确定性）。
不同歌，同样的意图，给出的参数应该不同（个性化）。

这是为什么"8 个预设"不行的原因：不同歌的缺陷不同，需要不同的处理。这也是为什么"LLM 猜参数"不行的原因：LLM 有随机性，同一首歌问两次可能得到不同参数。

真理：**处理方案 = f(诊断数据, 目标情绪, 历史经验)。f 是确定性的。**

### 特征 3：每一次使用都在变好

第 1 次处理的准确率可能只有 60%。
第 100 次处理的准确率应该接近 80%。
第 10000 次处理的准确率应该逼近理论极限（~90%，剩下的 10% 是审美主观性）。

不是靠开发者更新代码，是靠系统自己从数据中学习。

### 特征 4：知道自己的边界

当遇到超出知识范围的情况，系统会诚实地说：
"这首歌的诊断结果我以前没见过类似的情况。我没有足够的信心自动处理。我可以尝试一个实验性方案，但你最好多听听再决定。"

而不是在所有情况下都给出一个看似自信的推荐。

### 特征 5：人耳是最终仲裁者，但这个环越来越紧

最初：每 10 次处理需要 1 次 A/B 反馈来校准。
成熟后：每 100 次处理只需要 1 次 A/B 反馈。
极限：系统自动检测到"这次处理的不确定性很高"时，主动请求人类反馈。

人耳不是被替代，而是被精准调用——只在最需要的时候。

## 六、和上一版的本质区别

| | 上一版（AI 原生） | 这一版（真理逼近） |
|---|---|---|
| LLM 角色 | 参数生成器 | 搜索空间设计师 + 评估者 + 归纳者 |
| 参数来源 | LLM 一次推理 | 搜索 + 代理指标 + LLM 辅助评估 |
| 确定性 | 低（LLM 有随机性） | 高（搜索是确定性的） |
| 进化能力 | 不进化 | 每次使用都在进化 |
| 代理指标 | 无 | 有，且持续校准 |
| 知识闭环 | 无 | RAG + 联邦学习 |
| 人类反馈 | 必要（每次都要判断） | 渐进式减少（只在关键时请求） |

## 七、实现路线

### 第一步：建立代理指标（核心基础）

- 实现 EDSR_proxy = f(ΔWHS, Δ5D, 缺陷消除率, 安全合规)
- 用历史 demo_output 数据做初始校准
- 验证：代理指标和真实 A/B 偏好的相关性

### 第二步：实现参数搜索

- LLM 缩空间 → 离散化 → 代理评估 → top-3 → 真实 DSP → 选最优
- 初始用暴力搜索（空间够小），后续可以加贝叶斯优化

### 第三步：接入 LLM 推理

- LLM 读取诊断 → 输出搜索空间定义（JSON）
- LLM 评估候选方案 → 排序 + 理由
- LLM 分析失败 → 生成修正规则

### 第四步：知识闭环

- 记录每次处理的完整数据
- 实现相似案例检索（诊断特征向量相似度）
- 新处理参考历史最优参数

### 第五步：联邦学习

- 匿名化参数模式上传
- 云端模型聚合
- 下载更新后的代理模型

**猜不是优化。推理不是搜索。真理级别的软件是自我改进的闭环系统，不是聪明的一次性工具。**
