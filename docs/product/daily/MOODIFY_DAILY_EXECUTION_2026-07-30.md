## 3. D1-01｜执行入口基线

### 要回答的问题

1. 当前仓库、分支和工作区状态是什么？
2. 哪个版本是当前产品基线？
3. Core、Runtime和Workspace分别从哪里进入？
4. 推荐使用哪个Python和依赖环境？
5. 哪些命令用于最小测试、完整测试和服务启动？
6. 输入、运行数据、报告、交付和临时产物分别写到哪里？
7. 哪些目录包含用户或历史资产，不允许清理和覆盖？

### 交付标准 G1

- [ ] 仓库绝对路径、当前分支和HEAD可追踪；
- [ ] 明确当前发布基线与历史文档的关系；
- [ ] 至少列出Core、Runtime、Workspace三个入口；
- [ ] 测试命令可以直接复制，且工作目录明确；
- [ ] 服务或API启动命令有来源依据；
- [ ] 输入、输出、证据和临时目录边界清楚；
- [ ] 明确不得覆盖或删除的现有资产；
- [ ] 不把“文档声称可用”写成“本机已验证可用”。

只有8项全部满足，D1-01才可以标记为完成。

## 4. D1-02｜验证资产盘点

### 盘点对象

- 可用于内部验证的真实音频；
- Treatment Records及人工反馈覆盖；
- MRS参考集、配置、评分结果和校准证据；
- Listening Test、Inspector和Before/After资产；
- Workspace v2黄金路径样本；
- 已有报告、运行日志和失败记录。

### 资产分类

每项资产必须归入以下一种状态：

- `READY`：路径有效、格式可读、用途清楚，可以直接用于下一步；
- `PARTIAL`：存在但缺元数据、授权、标签、反馈或完整性证据；
- `HISTORICAL`：只用于历史追溯，不代表当前版本；
- `BLOCKED`：缺失、损坏、不可读或权利状态不明，不能进入验证集。

### 交付标准 G2

- [ ] 主要资产类别全部覆盖；
- [ ] 每项给出绝对或仓库相对路径；
- [ ] 音频只统计，不修改、不复制、不删除；
- [ ] 区分真实音频、合成测试音频和生成产物；
- [ ] 权利状态不明确的音频标记为`BLOCKED`或`PARTIAL`；
- [ ] Treatment反馈数量以实际文件重新统计，不引用过时README数字；
- [ ] 给出周二验证集筛选的可用候选池。

## 5. D1-03｜能力—证据—缺口矩阵

### 三态定义

- `IMPLEMENTED`：代码或接口存在，但未取得本轮运行证据；
- `VERIFIED`：存在当前环境、当前版本的运行或测试证据；
- `PRODUCTION-PROVEN`：在真实生产材料上经过重复运行和专业听感验证。

任何能力不得因为测试通过就直接标记为`PRODUCTION-PROVEN`。

### 最低覆盖范围

- 音频导入与格式检查；
- 诊断与指标提取；
- Treatment Plan；
- DSP处理；
- 候选版本与血缘；
- MRS与技术质量门；
- 人工批准与Final归档；
- Runtime、Queue和失败恢复；
- Report、Delivery和Craft写回；
- 真实听感验证。

### 交付标准 G3

- [ ] 每项能力只有一个当前状态；
- [ ] 每项状态都有代码、测试、运行产物或报告证据；
- [ ] 每项至少写出一个当前限制；
- [ ] 明确哪些能力尚未达到`PRODUCTION-PROVEN`；
- [ ] 按阻塞真实生产验证的程度排序缺口，而不是按开发兴趣排序。

## 6. D1-04｜最小冒烟与今日封口

### 最小冒烟范围

1. Core测试或最小处理入口；
2. Runtime关键测试或CLI健康入口；
3. Workspace v2关键闭环测试；
4. 如果具备安全、只读的真实音频路径，验证一个最小读取或登记步骤；
5. 不在冒烟阶段修改音频算法或批量生成新产物。

### 交付标准 G4

- [ ] 每条命令记录工作目录、开始时间、结束状态和返回码；
- [ ] 测试数和跳过数来自当前运行输出；
- [ ] 失败完整保留，区分环境问题、历史问题和本轮回归；
- [ ] 产物位置明确且没有覆盖历史音频；
- [ ] 今日结论只能是`BASELINE READY`、`BASELINE PARTIAL`或`BASELINE BLOCKED`；
- [ ] 只给出一个明日优先问题。
