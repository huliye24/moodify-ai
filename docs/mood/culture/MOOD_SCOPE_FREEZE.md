# WHAT MOOD IS

MOOD is an open Web3 digital world and protocol network.

MOOD is not defined by a single application, a single token, or a single company-operated product. Its purpose is to create a digital world that people, AI Agents, developers, creators, node operators, researchers, and other participants can enter, contribute to, verify, and help build under shared rules.

The canonical product architecture is:

**MOOD = WORLD + PROTOCOL + PORTAL**

Everything in the current mainline must belong clearly to one of these three layers, or directly support the shared Network state behind them.

## WORLD

WORLD is the experience and cultural layer.

Its job is to answer:

**“What kind of place is this, and why is it worth entering?”**

WORLD may contain:

- visual identity and beliefs;
- manifesto and cultural language;
- music, sound, city and spatial metaphors;
- the world map;
- Library;
- Protocol Hall;
- Builder Workshop;
- Agent Lab;
- Node Station;
- Moodify Gate.

WORLD is not decoration around the protocol. It is the human-facing entrance to the network.

## PROTOCOL

PROTOCOL is the public rule layer.

Its job is to answer:

**“How does this world actually work?”**

The current protocol scope is limited to:

- Moodify Protocol;
- Proof System;
- Agent Protocol;
- Node Protocol;
- Governance Framework / MIP;
- Economic Rules;
- Treasury rules;
- Security Model;
- canonical documentation, versioning and verifiable records.

Protocol work exists to make rules inspectable, traceable and versioned.

A protocol feature is not complete because a document says it exists. It is complete only when its rule, implementation, evidence and current state can be checked.

## PORTAL

PORTAL is the participation layer.

Its job is to answer:

**“How do I enter, act, contribute and leave a history in this network?”**

The current Portal scope is limited to:

- Wallet;
- Passport;
- Assets;
- Rewards;
- Contributions;
- Reputation;
- Agents;
- Nodes;
- Governance / Rights where applicable.

The canonical resident path is:

**Visitor → Connect Wallet → Resident → Contributor → Reputation → Governance / Rights / Rewards**

Wallet connection is only the entrance. It is not the identity system.

Passport is the human-facing identity history. Contribution and reputation must be able to exist independently from token wealth.

## NETWORK

WORLD, PROTOCOL and PORTAL must point to one shared, real Network state.

The health of MOOD is measured by real network activity, not by feature count, repository size, page count, token price, or marketing claims.

The canonical network metrics are:

- Residents;
- Token Holders;
- Developers;
- Creators;
- AI Agents;
- Nodes;
- Contributions;
- Applications;
- MIPs;
- Treasury.

All metrics begin from reality.

**A real 1 is more valuable than a fabricated 10,000.**

## MOODIFY

Moodify is the first real application built on top of the protocol.

It is the **Genesis Application**.

Moodify exists to prove that the MOOD world and Moodify Protocol can produce a useful product around sound, AI, contribution and collaboration.

Moodify is not the whole MOOD world.

## MOOD TOKEN

MOOD Token is the economic medium of the network.

Its permitted roles are:

- settlement;
- incentive;
- staking where an explicit responsibility or security condition exists;
- governance input;
- Treasury-related economic coordination.

The Token serves the Network.

The Network does not exist to serve the Token.

The long-term value proposition of MOOD must come from a functioning Network, real applications, real contributions, real nodes, real participants and public rules — not from an assumption that price will rise.

# WHAT MOOD IS NOT

This section exists to prevent scope creep.

If an idea is useful but does not belong to the current definition of MOOD, it remains outside the mainline.

## MOOD IS NOT A TOKEN PROJECT WITH A WEBSITE AROUND IT

The Token is one layer of the network.

Therefore MOOD is not primarily:

- a token launch campaign;
- a price dashboard;
- a trading interface;
- a holder-growth machine;
- a yield narrative;
- a liquidity narrative;
- a speculation community.

Price, volume and holder count may be observable network facts, but they do not define product progress.

## MOOD IS NOT “WEB3 FEATURES EVERYWHERE”

We do not put data on-chain merely because we can.

We do not treat:

- minting an NFT;
- issuing an SBT;
- connecting a wallet;
- deploying another contract;
- adding another chain;
- creating another token;
- adding staking;

as progress by themselves.

The initial identity model may remain:

**wallet signature + off-chain profile + optional on-chain anchoring.**

On-chain implementation must have a clear reason: verification, ownership, settlement, governance, security or durable public state.

## MOOD IS NOT AN EVERYTHING APP

MOOD does not need to become every possible product that AI, audio, Web3 or cloud infrastructure makes technically possible.

The mainline is not required to contain:

- a general-purpose social network;
- a general-purpose chat product;
- a general-purpose AI assistant;
- a general-purpose creator platform;
- a general-purpose cloud platform;
- a general-purpose developer marketplace;
- a general-purpose exchange;
- a general-purpose wallet;
- a general-purpose metaverse;
- a full enterprise software suite.

If a capability does not directly strengthen WORLD, PROTOCOL, PORTAL, the shared Network state, or the Moodify Genesis Application, it is outside current scope.

## MOOD IS NOT A COLLECTION OF LEGACY PRODUCTS

Past experiments do not automatically become permanent architecture.

Existing code has no right to remain in the mainline merely because time has already been spent building it.

Historical products, experiments and modules may be:

- retained if required by the frozen scope;
- frozen if potentially useful later;
- archived if they have historical or research value;
- deleted if they are duplicate, obsolete, misleading or unmaintained.

**Sunk cost is not a product requirement.**

## MOOD IS NOT A PROMISE OF FUTURE SCALE

We do not claim:

- global node networks that do not exist;
- resident counts that are not verifiable;
- Agent activity that is simulated but presented as real;
- Treasury assets that are not publicly attributable;
- contributions that have no evidence;
- partnerships or integrations that are not active;
- guaranteed rewards, returns or appreciation.

A network metric must either have a real source or remain zero / unavailable.

## MOOD IS NOT “BUY A NODE AND EARN”

A Node must ultimately represent real network service or resources.

Node identity, qualification or reward must not rely only on purchasing access.

Where node rewards exist, they must be connected to verifiable service, responsibility or contribution.

## MOOD IS NOT AN AUTONOMOUS TREASURY RUN BY AI

AI Agents may execute tasks, analyze, verify, research, coordinate and contribute.

They must not become opaque automatic money-distribution systems.

Any settlement-relevant Agent action should produce traceable evidence where practical:

**Task → Execution → Evidence → Verification → Contribution Proof → Reputation / Settlement**

High-risk keys, Treasury movement, contract deployment and permission changes remain under explicit security controls and human signing gates where required.

# WHAT WE BUILD NOW

Current work is restricted to the minimum system required to make the whitepaper true in reality.

The objective is not to complete every imagined future feature.

The objective is to make MOOD **enterable, inspectable, participatory and verifiable**.

## 1. ONE NETWORK INTERFACE

We build and converge:

**crestwavecoin.com**

as the canonical MOOD Network Interface.

It must present a coherent WORLD + PROTOCOL + PORTAL experience pointing to one network state.

We do not create parallel public websites for the same canonical function unless there is a clear infrastructure reason.

## 2. THE MINIMUM WORLD

We build only enough WORLD to make MOOD feel like a place rather than a token landing page.

Required:

- canonical visual / belief system;
- manifesto;
- world map or equivalent navigational spatial model;
- Library;
- Protocol Hall;
- Builder Workshop;
- Agent Lab;
- Node Station;
- Moodify Gate.

The WORLD layer should remain light, open and readable.

Its purpose is orientation and meaning, not endless decorative production.

## 3. THE MINIMUM PROTOCOL

We maintain one canonical, readable and versioned rule set covering:

- Moodify Protocol;
- Proof System;
- Agent rules;
- Node rules;
- Governance / MIP;
- Economic rules;
- Treasury rules;
- Security.

For each mature protocol component, prefer:

- readable web documentation;
- version;
- publication date;
- repository source;
- PDF where appropriate;
- implementation reference;
- verifiable deployment/configuration information where applicable.

We do not create multiple overlapping protocol definitions for the same concept.

## 4. THE MINIMUM PORTAL

We build the smallest resident loop that works end to end:

**Connect Wallet → Passport → Contribution → Proof → Reputation**

Then connect that identity and contribution history to:

- Agents;
- Nodes;
- Rewards where a real rule exists;
- Governance / Rights where a real rule exists.

The Portal must prioritize usable state and verifiable history over dashboards filled with empty modules.

## 5. REAL CONTRIBUTION PROOF

Contribution is a core primitive.

We support only contribution types that can produce evidence and be explained.

Initial contribution categories may include:

- development;
- creation;
- research;
- node service;
- verification;
- governance;
- community building.

A contribution record should be able to answer:

- who / what performed it;
- what was done;
- when;
- source or task;
- evidence;
- verification status;
- result;
- relevant hash / reference where applicable.

Rewards must follow contribution or explicit network rules — never precede them.

## 6. REAL AGENTS

We build only Agents that perform real tasks.

An Agent should have, where applicable:

- identity;
- role;
- capability;
- task;
- execution record;
- output;
- evidence;
- verification state;
- contribution history.

We do not multiply Agent types for presentation purposes.

One Agent doing one real, traceable job is sufficient to establish the first working loop.

## 7. REAL NODES

We build only the minimum node registry and service model necessary to represent real network resources.

Node roles may include the roles actually supported by the protocol and implementation, such as compute, storage, verification, indexing or AI-related service where defined.

A Node should have, where applicable:

- stable identity;
- operator;
- role;
- status;
- capability;
- service evidence;
- health / availability state;
- contribution history.

We begin with real nodes, even if the number is one.

## 8. MINIMUM GOVERNANCE AND TREASURY TRANSPARENCY

We build the minimum system needed to make protocol change and resource movement traceable.

Required direction:

- MIP lifecycle;
- proposal history;
- protocol-change history;
- documented authority boundaries;
- Treasury addresses where they exist;
- public asset / flow references where applicable;
- traceable authorization for major changes.

Governance may be progressive.

We do not pretend early-stage administration is already fully decentralized.

## 9. MOODIFY AS THE GENESIS APPLICATION

We keep Moodify focused on proving one proposition:

**The MOOD protocol can generate a real, useful application around sound and AI.**

Only the smallest useful Moodify path belongs in the current mainline.

Moodify must not expand into a giant audio software suite before the Network itself works.

## 10. NETWORK OBSERVABILITY

We build a Network view based only on real sources.

The first acceptable state can be:

- 1 Resident;
- 1 Developer;
- 1 Creator;
- 1 Agent;
- 1 Node;
- 1 Contribution;
- 1 Application;
- 0 or 1 MIP;
- a real Treasury state where applicable.

Zero is acceptable.

Fabrication is not.

The Network page should gradually expose:

- current network status;
- protocol version;
- contract version where relevant;
- latest contributions;
- latest MIPs;
- current epoch only if the system genuinely uses one;
- transparent metric definitions and snapshot times.

## DEFINITION OF “DONE FOR NOW”

The current build stage is complete when a stranger can:

1. enter MOOD and understand what world they entered;
2. read the protocol rules;
3. connect a wallet;
4. establish a Passport / resident identity;
5. make or inspect a real contribution;
6. inspect its evidence / Proof;
7. see reputation or contribution history;
8. inspect at least one real Agent or Node activity;
9. see real Network state;
10. enter the Moodify Genesis Application.

Until this loop works, new product categories are lower priority.

# WHAT WE REFUSE TO BUILD

This is an active refusal list.

The purpose is to protect attention, engineering time, token budget and architectural clarity.

“Not now” does not mean “never.”

It means **not part of the frozen current mainline**.

## WE REFUSE TO BUILD FEATURES WITHOUT A WHITEPAPER ROLE

Every proposed feature must answer:

**Does this directly serve WORLD, PROTOCOL, PORTAL, NETWORK, or the Moodify Genesis Application?**

If the answer is unclear, we do not build it.

## WE REFUSE TO BUILD PARALLEL PRODUCTS BEFORE THE CORE LOOP WORKS

Until the minimum MOOD loop is real, we do not expand the mainline into additional:

- desktop products;
- mobile applications;
- large standalone workspaces;
- marketplaces;
- enterprise suites;
- unrelated SaaS products;
- separate consumer applications.

Existing implementations may be frozen or archived rather than extended.

## WE REFUSE TO BUILD A FULL AUDIO EMPIRE INSIDE MOODIFY

Moodify remains the Genesis Application, not an excuse to absorb every audio product idea.

We do not currently expand it into every possible:

- DAW-like workflow;
- plugin ecosystem;
- desktop audio suite;
- mastering product;
- enterprise audio platform;
- media marketplace;
- creator social platform.

Only functionality required to demonstrate the real Moodify / MOOD protocol loop remains active.

## WE REFUSE TO ADD BLOCKCHAIN COMPLEXITY WITHOUT NECESSITY

No new chain, contract, bridge, NFT, SBT, staking mechanism, tax mechanism or token mechanism enters the mainline solely for “Web3 completeness.”

Every additional on-chain component must state:

- what problem it solves;
- why off-chain state is insufficient;
- security consequences;
- authority model;
- upgrade model;
- data source;
- failure mode.

If those answers are weak, we do not build it.

## WE REFUSE TO FINANCIALIZE IDENTITY

Passport and Reputation are not token-balance leaderboards.

We do not make wealth the sole measure of:

- identity;
- credibility;
- contribution;
- rank;
- governance legitimacy.

Contribution quality, persistence, verification and history remain first-class signals.

## WE REFUSE TO REWARD UNVERIFIED ACTIVITY

No contribution proof → no contribution claim.

No defined rule → no reward claim.

No real service → no node-service reward.

No traceable execution → no Agent settlement claim.

We do not design rewards first and search for activity later.

## WE REFUSE TO FAKE NETWORK ACTIVITY

We do not fabricate:

- residents;
- nodes;
- Agents;
- contributions;
- applications;
- governance activity;
- Treasury balances;
- service capacity.

Demo / test data must be explicitly marked as such and must never contaminate public Network Metrics.

## WE REFUSE TO TURN THE WEBSITE INTO A PRICE TERMINAL

Network health has priority over price visibility.

The primary public narrative will not be:

- price;
- chart;
- APY;
- “1000x”;
- guaranteed yield;
- countdown-to-pump;
- holder reward marketing.

If market data is shown, it must remain a factual asset view rather than the organizing principle of MOOD.

## WE REFUSE TO LET AI CREATE UNBOUNDED SCOPE

AI coding speed is not permission to create more product surface.

Codex, Cursor, Agents and other coding systems must not:

- invent new product categories;
- duplicate existing subsystems;
- expand scope because implementation is easy;
- introduce placeholder “future” modules into the mainline;
- preserve obsolete architecture only to avoid deletion.

AI must optimize for **convergence, removal, verification and simplicity**.

## WE REFUSE TO KEEP CODE BECAUSE IT WAS EXPENSIVE TO CREATE

Past effort does not override present scope.

During scope reduction, every existing module receives one status:

**KEEP / FREEZE / ARCHIVE / DELETE**

- KEEP: required by this scope.
- FREEZE: potentially valuable later; no current development.
- ARCHIVE: historical/research value; removed from active architecture.
- DELETE: obsolete, duplicate, misleading, dead, or unnecessary.

The mainline is allowed to become dramatically smaller.

## WE REFUSE TO START THE NEXT MAJOR EXPANSION BEFORE THE CURRENT NETWORK IS REAL

The next major phase does not begin because another task package number is available.

It begins only when the current phase has real, verifiable output.

The governing rule is:

**Reality before scale.  
Contribution before reward.  
Rules before narrative.  
Network before price.  
Clarity before expansion.**
