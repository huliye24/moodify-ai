# MIP-000 — MOOD Improvement Proposal (MIP) Governance Standard

> MIP-000 is itself the governance process specification. It defines how
> every other MIP is authored, reviewed, accepted, implemented, and
> superseded.

| Field | Value |
| --- | --- |
| Number | MIP-000 |
| Title | MOOD Improvement Proposal (MIP) Governance Standard |
| Status | Draft |
| Category | Governance |
| Authors | system (seeded by 020) |
| Decision Method | maintainer-consensus |

## Summary

MIP-000 defines the canonical lifecycle, format, and review process for all
MOOD Improvement Proposals. Every change to MOOD canon, policy, or
public-facing protocol must be tracked as a MIP.

## Motivation

Without a single, versioned governance process, MOOD's canonical surfaces
would drift: contributions, agents, nodes, and treasury would each grow
their own decision log and the audit story would be impossible to
reconstruct.

MIP-000 establishes the *one* authority for governance decisions. It is
deliberately conservative: maintainer-reviewed governance in v1, with
explicit hooks for future resident signaling and (eventually) token voting,
neither of which are active.

## Specification

### Lifecycle

```
draft → discussion → review → accepted → implemented
                                              ↓
                                         superseded / archived

draft → withdrawn
discussion → review → rejected → archived
```

Forbidden transitions:

- `draft → implemented`
- `discussion → implemented`
- `rejected → implemented`

### Decision Methods

- `maintainer-consensus` (default; active)
- `resident-signal` (reserved; not yet active)
- `future-token-vote` (reserved; disabled in 020)
- `emergency` (used only with a retrospective MIP)

### Required Sections

Every MIP must include:

- Number, Title, Status, Category, Authors, Created, Updated
- Summary, Motivation, Specification, Rationale
- Security Considerations, Backward Compatibility, Implementation Plan
- Open Questions, Decision Record, Implementation References

Economics / Token categories additionally require:

- Economic Risks
- Parameter Table
- Launch Gate Dependencies

### Implementation

A MIP enters `implemented` only after at least one Implementation
Reference is recorded with a verifiable artifact (commit SHA, PR URL,
deployed route, policy doc path, config change, or migration).

## Rationale

This design is intentionally narrow:

- Maintainer review keeps 020 deliverable without requiring a Token.
- Resident Signal is reserved (not active) so future versions can opt in.
- Token voting is explicitly forbidden so that 020 cannot accidentally
  ship token-gated semantics.
- Append-only audit ensures every state change is replayable.
- The Canon boundary ensures governance does not silently rewrite canon
  files.

## Security Considerations

See `020_SECURITY_MODEL.md`. Notable threats:

- proposal spam (T1) — Residents can create drafts; Maintainers archive
  obvious spam.
- self-accept by sole author (T3, T4) — `INV-020-06`.
- decision tampering (T5) — append-only.
- fake implementation reference (T8) — public verification.

## Backward Compatibility

MIP-000 introduces a new public surface (`/governance`, `/api/governance/*`)
and does not modify any existing routes. Existing Canon, Passport,
Contribution, Agent, and Node registries are unchanged.

## Implementation Plan

1. Seed MIP-000 in the registry on boot (`ensureMipZero`).
2. Expose `/governance` and `/governance/mips/[id]`.
3. Expose `/api/governance/mips` and `/api/governance/mips/[id]`.
4. Add `mips` metric and MIP activity events to `/network`.

All four steps are part of 020.
