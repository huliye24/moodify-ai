## 1. 任务意图

明城墙并没有消灭山川、街巷、人口和防务的复杂性；它通过连续围护、有限城门、分段责任和可维修结构，让复杂性不再直接压到每个使用者身上。Moodify 的目标同样不是“代码少”，而是：复杂性可以存在于墙内，但跨边界必须经过稳定门面。

数据依据：核心与运行时占已跟踪改动的 83.6%，说明变化高度压在承重区域。测试/源代码物理行比 34.2% 表明验证资产存在，但不能替代架构边界。此任务不进行大拆大建，而是先画墙、定门、测压，再选择一个高价值切口完成示范性围护。

## 2. 核心目标

1. 建立 Moodify 的系统围护图：领域、编排、能力注册、DSP、存储、API/CLI、分析与外部工具；
2. 每个区域声明公共门面、允许依赖、禁止反向依赖、数据所有权和失败语义；
3. 建立无需第三方依赖的架构边界检查器与复杂度预算；
4. 选择一个变更最集中的边界做最小示范重构，让调用方依赖门面而非内部结构；
5. 将边界违例、核心变更集中度和公共 API 扩张纳入常态分析。

## 3. 设计原则

- **墙体连续：** 每个跨域调用都有明确边界，不允许“临时穿墙”；
- **城门有限：** 公共入口少而稳定，内部实现可以演进；
- **分段责任：** 每个边界有 owner、契约测试和故障语义；
- **修旧可追：** 兼容层有期限、来源和移除条件，不永久堆积；
- **因地制宜：** 不追求机械分层，允许经过记录的例外；
- **复杂度守恒：** 隐藏复杂度不等于吞掉错误，门面必须保留诊断证据。

## 5. 执行阶段

### Stage A｜绘制系统围护图

- 用机器可读 manifest 和人类可读文档描述区域、门面和依赖方向；
- 列出当前穿墙点、循环依赖、跨层导入、共享可变状态和异常泄漏；
- 标出承重区域和高变更集中区；
- 每项判断附文件证据，不凭印象评分。

### Stage B｜建立复杂度预算

至少采集：

- 公共导出符号数及增量；
- 跨区域导入边数、反向依赖数和循环数；
- 核心/运行时改动集中度；
- 超大模块与高扇入模块清单；
- 兼容层数量、年龄和移除条件；
- 边界契约测试数量与状态。

预算首先是趋势护栏，不用未经校准的综合分数制造虚假精确。

### Stage C｜建立自动边界门禁

- 使用标准库 AST/路径规则实现确定性检查，不新增第三方依赖；
- 规则支持 allow、deny、documented exception 和 expiry；
- 新增违例失败，已有债务进入基线并要求只降不升；
- 输出机器可读 JSON 和可读报告，错误信息定位到文件、导入和规则。

### Stage D｜完成一个示范性围护

- 从高变更区选择一个边界，先写契约测试；
- 引入一个稳定门面，将内部类型、依赖选择或错误转换藏在墙内；
- 保持外部行为与声音结果不变；
- 记录调用方减少的内部知识、边界前后导入图和兼容策略；
- 只有示范通过后，才提出后续推广清单，不在本任务内扩张。

### Stage E｜纳入常态分析

- 周报展示边界新增违例、公共 API 增量和集中度趋势；
- 阶段报告评估墙体是否降低修改传播范围；
- 专项报告只在架构迁移或边界例外激增时触发。

## 6. P0 验收门槛

- 围护图覆盖所有主要区域，每个区域有门面、依赖、数据和失败语义；
- 自动检查器在同一输入上确定性输出，并能用反例证明会失败；
- 新违例为 0，已有债务不增加；
- 示范边界有契约测试，022 的全量收集门禁保持绿色；
- 外部行为与音频结果不变；
- 不使用单一综合“复杂度分数”替代原始指标；
- 报告明确复杂度被隐藏在哪里、由谁维护、如何诊断和如何回滚。
