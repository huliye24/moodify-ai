# DSK-MFY-ORDER-BEAUTY-025｜城楼：建立项目效能与秩序观测系统

**计划日期：** 2026-08-02  
**执行 Worker：** DeepSeek  
**任务所有者与最终 Judge：** Codex / 授权用户  
**依赖：** 022、023、024 ACCEPT  
**建议投入：** 6–12 小时  
**任务状态：** PLANNED

## 1. 任务意图

城墙建立秩序，城楼负责看见秩序是否仍然有效。Moodify 不能只完成一次整理；它需要持续判断：同样的时间投入是否产生更稳定的产出、一次改动是否影响更少的区域、复杂度是否被门面吸收、用户是否真正获得价值。

本任务建立轻量、只读、可复核的观测层。它不控制产品运行，不替代人的判断，也不制造一个看似精确的“项目总分”。原始指标、定义、来源与不确定性必须始终可见。

## 2. 核心问题

观测系统必须能够回答：

1. 每个任务包投入了多少人工时间、机器时间、等待时间和返工时间？
2. 一次改动传播到多少模块、公共接口、测试和任务包？
3. 测试门禁、任务冲突、工作区未知项和边界违例是否持续下降？
4. 首次验收通过率、交付周期和在制品数量是否改善？
5. 新功能是否提高任务成功率、功能使用率或音频质量，而不只是增加代码？
6. 项目是否进入“资产继续增长，但单次改动扰动范围趋于稳定或下降”的水平化阶段？

## 3. 设计原则

- **只读观测：** 采集器不得修改产品状态、任务状态或工作区文件；
- **时间可追：** 每次运行使用 Asia/Shanghai 时间戳并保存不可覆盖快照；
- **定义先行：** 指标必须有公式、单位、分母、来源、刷新频率和限制；
- **缺失诚实：** 没有数据时显示 `NOT_MEASURED`，禁止用 0 或猜测替代；
- **事实与估算分离：** 实测工时、计划工时、影响点和模型 ROI 使用不同字段；
- **不用总分遮蔽：** 不生成未经校准的单一健康分或复杂度分；
- **低维护成本：** 常态采集应快速、离线、确定性，不依赖产品运行时启动；
- **隐私最小化：** 不记录按键、屏幕、音频内容或个人活动轨迹，只记录用户主动提交的任务级汇总。

## 5. 指标框架

### A. 秩序与可信度（常态化）

- 全量测试收集错误数、收集测试数、门禁状态与耗时；
- 任务状态冲突数、UNKNOWN 数、同时在制品数；
- 已跟踪修改、未跟踪文件数及分类覆盖率；
- 新增边界违例、存量边界债务和到期例外；
- 公共 API 增量与核心/运行时改动集中度。

### B. 投入与流动效率（任务级）

- 计划人工小时、实际人工小时、机器执行小时；
- active / wait / rework 时间，禁止只记录总历时；
- 首次验收通过率、返工轮次、任务 lead time；
- 单位产出投入：人工小时 / 已验收任务包；
- 模型 ROI：影响点 / 工时中位数，必须标注为估算。

### C. 改动传播与水平化（阶段性）

- 每次任务涉及的模块数、公共接口数和测试文件数；
- 变更传播率：受影响区域数 / 系统区域总数；
- 任务完成后的新增代码、删除代码与净复杂度说明；
- 滚动中位数趋势：同等工时下的验收产出与扰动范围；
- 只有连续至少 3 个阶段窗口后，才允许判断是否进入水平化状态。

### D. 用户价值（阶段性，目前缺失）

- 核心任务成功率与失败原因；
- 功能使用次数、完成率和放弃率；
- 音频盲评、技术质量指标与人工接受结论；
- 用户节省时间或减少操作步骤；
- 在没有数据前全部显示 `NOT_MEASURED`，不得推断财务 ROI。

## 6. 执行阶段

### Stage A｜建立指标契约与输入模板

- 扩展 `metric_contracts.json`，定义公式、单位、来源、刷新频率、owner 和限制；
- 建立任务投入记录 schema：planned_hours、active_hours、wait_hours、rework_hours、machine_hours、evidence；
- 建立用户价值记录 schema，但不收集个人行为细节；
- 对旧分析提供版本兼容和迁移说明，不改写历史快照。

### Stage B｜实现只读采集器

- 复用 022 测试门禁、023 任务账本、024 边界 manifest；
- 采集失败时保留错误证据并标记 `PARTIAL`，禁止输出伪完整报告；
- 同一仓库状态与同一显式输入产生相同指标值；
- 将动态时间元数据与确定性数据主体分离。

### Stage C｜建立三种分析节奏

- **每周常态报告：** 可信度、状态冲突、工作区、边界违例和在制品；
- **阶段报告：** 投入、返工、改动传播、首次验收和水平化趋势；
- **专项报告：** 架构迁移、重大功能、质量事故或指标异常时触发；
- 每种报告都生成 JSON 数据、Markdown 摘要和运行 manifest；Excel/PDF 作为展示层，不成为唯一数据源。

### Stage D｜建立趋势与决策规则

- 采用中位数、区间和原始序列，避免小样本均值误导；
- 定义红线：测试收集错误 > 0、状态冲突 > 0、新边界违例 > 0；
- 定义观察项而非硬目标：改动集中度、任务周期、模型 ROI；
- 明确“恢复开发、继续稳定、触发专项评估”的条件；
- 不允许指标自动发布、自动关闭任务或自动阻止用户工作。

### Stage E｜回放与基线

- 以 2026-08-02 整体分析作为历史基线回放；
- 明确区分当时快照与当前状态，不让新数据覆盖旧数字；
- 生成首次阶段报告，展示哪些指标可测、哪些仍为 `NOT_MEASURED`；
- 记录下一阶段最小数据采集建议。

## 7. P0 验收门槛

- 每个指标都有可机器读取的契约和限制说明；
- 观测层对产品代码、任务状态和工作区零写入；
- 历史分析不可覆盖，registry 只能追加；
- 实测、计划、估算和缺失数据在 schema 与报告中可区分；
- 同一输入连续运行两次，数据主体一致；
- 采集失败会标记 `PARTIAL`，不会伪造完整结论；
- 三种报告节奏均有可复现入口；
- 2026-08-02 基线能够被回放，并保留 421/19、57.1%、83.6%、55/140 等历史口径；
- 无网络上传、后台监听、个人行为跟踪或新服务依赖。

## 8. 成功判定

本任务的成功不是生成更多图表，而是让项目可以长期回答：

> 我们是否用更少的返工、更小的传播范围和更稳定的边界，持续交付可验收的用户价值？

只有数据连续积累后，才能判断 Moodify 是否真正进入后期水平化阶段。首次报告必须允许结论是“证据不足”。

## 9. 停止条件

若实现需要修改产品运行时、部署遥测服务、上传内部数据、采集个人行为、引入外部数据库或自动干预任务状态，立即停止并提交 `SCOPE_CHANGE_REQUEST.md`。最终状态只能是 `READY_FOR_CODEX_REVIEW / REWORK / HOLD`。
