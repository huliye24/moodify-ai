# AI 原生架构：大模型作为核心元器件

**时间**: 2026-05-28
**前提**: 大模型不是软件的功能，是软件的元器件。如同电路板上的电容和晶体管。
**核心论点**: 我们之前所有的工程讨论——双轨并行、HPSS优化、Electron打包——都是在用互联网产品思维开发 AI 原生软件。方向偏了。

---

## 零、先承认错误

过去 48 小时我们产出了四份工程文档：

1. 软件架构与可扩展性设计
2. 双轨并行开发方案
3. 双 AI 并行实施方案（性能与重构）
4. HPSS 频谱替代 Demucs 方案

这些文档的共同特点：**讨论的都是如何优化一个传统 DSP 管线。**

没有人问过一个根本问题：**大模型在这个软件里做什么？**

答案是：什么都没做。

诊断引擎是 FFT + 启发式规则。工艺卡匹配是缺陷 ID 查表。DSP 链是固定参数 → pedalboard。8 种情绪工艺卡本质是 8 个预设。

**我们花了四份文档优化了一个预设管理器。**

而真正的机会是：**让大模型来推理"这首歌应该怎么处理"。**

## 一、重新理解「元器件」

### 1.1 传统软件的元器件

```
CPU → 执行指令
内存 → 存储运行时数据
硬盘 → 持久化存储
GPU → 并行计算
```

软件工程师不关心 CPU 内部怎么工作。CPU 是一个黑盒元器件——输入指令，输出结果。

### 1.2 AI 原生软件的元器件

```
大模型 → 理解和推理
诊断引擎 → 信号提取（传统元器件）
DSP 引擎 → 信号处理（传统元器件）
向量数据库 → 记忆和检索
```

**大模型是新的元器件类型。** 它的接口不是「寄存器」和「指令集」，而是「自然语言输入」和「结构化输出」。但它本质上和 CPU 一样——输入信息，处理信息，输出信息。

### 1.3 元器件思维改变架构方式

传统思维：
```
我要做一个音频处理软件 → 需要什么功能？→ 诊断、匹配、处理 → 写代码实现每个功能
```

元器件思维：
```
我有一块大模型（推理能力）→ 我有一组诊断工具（感知能力）→ 我有一组 DSP 工具（执行能力）
→ 我用大模型来协调感知和执行 → 软件 = 元器件之间的连接逻辑
```

**软件从「功能的集合」变成了「元器件的电路板」。**

## 二、Moodify 的真正元器件

### 2.1 元器件清单

| 元器件 | 类型 | 输入 | 输出 | 速度 | 确定性 |
|--------|------|------|------|------|--------|
| 诊断引擎 | 传感器 | 音频文件 | 18 参数 JSON | < 3s | 100% |
| HPSS 分解器 | 预处理器 | 音频波形 | H + P 波形 | < 0.5s | 100% |
| DSP 执行器 | 执行器 | 音频 + 参数 | 处理后的音频 | < 2s | 100% |
| 大模型（推理） | 推理器 | 诊断 + 意图 | 参数方案 + 解释 | 2-10s | 非确定 |
| 大模型（嵌入） | 记忆器 | 处理记录 | 向量 | < 1s | 确定 |
| 向量数据库 | 存储器 | 向量 + 元数据 | 相似案例 | < 100ms | 确定 |

**前三个是传统元器件（我们已经有）。后三个是 AI 元器件（我们完全没有）。**

### 2.2 元器件之间的连接逻辑

```
┌─────────────────────────────────────────────────────────┐
│                    Moodify 电路板                         │
│                                                         │
│   [音频输入]                                             │
│       │                                                 │

│   │ 诊断引擎  │────────────►│ 大模型     │◄── 用户意图    │
│   │ (传感器)  │              │ (推理器)   │     (自然语言)  │
│   └─────────┘              └────┬─────┘                │
│                                 │                       │
│                                 │ 15参数 + 解释           │
│                                 ▼                       │
│   ┌─────────┐              ┌──────────┐                │
│   │ HPSS    │─────────────►│ DSP 引擎  │                │
│   │ (预处理器)│   H+P 波形   │ (执行器)  │                │
│   └─────────┘              └────┬─────┘                │
│                                 │                       │
│                                 │ 处理后音频              │

│                                 ▼                       │
│   ┌──────────┐   嵌入    ┌──────────┐                   │
│   │ 向量数据库 │◄─────────│ 嵌入模型  │                   │
│   │ (存储器)  │           │ (记忆器)  │                   │
│   └────┬─────┘           └──────────┘                   │
│        │                                                │
│        │ 相似历史案例                                     │
│        ▼                                                │
│   ┌──────────┐                                          │

└─────────────────────────────────────────────────────────┘
```

**软件代码 = 这些箭头（连接逻辑）。每个框是元器件，由外部提供。**

### 2.3 对比：四种架构的代际差异

| | 传统架构 | 我们现在的架构 | AI 原生架构 |
|---|---|---|---|
| 决策方式 | 硬编码 if-else | 8 个预设 + 查表匹配 | **LLM 推理生成** |
| 用户交互 | 参数面板 | 下拉菜单选情绪 | **自然语言描述** |
| 可处理范围 | 预设覆盖的场景 | 8 种情绪 | **无限种可能** |
| 知识积累 | 不积累 | 不积累 | **每次处理都学习** |
| LLM 角色 | 无 | 无 | **核心推理元器件** |
| 软件角色 | 功能实现者 | 功能实现者 | **元器件连接板** |

我们现在的架构卡在中间——有了诊断（感知能力），有了 DSP（执行能力），但**没有大脑**。大脑的位置被 8 个 Excel 表替代了。

## 三、大模型的角色划分

### 3.1 一个软件可以插入多个大模型

就像电路板上可以有多个芯片，每个负责不同的事：

| 模型角色 | 做什么 | 候选模型 | 速度要求 |
|---------|--------|---------|---------|
| **推理器** | 诊断解读 + 参数生成 + 风险判断 | Claude Sonnet / GPT-4o / Qwen 32B | < 10s 可接受 |
| **嵌入器** | 处理记录 → 向量（用于相似案例检索）| text-embedding-3-small / bge-m3 | < 1s |
| **对话器** | 多轮交互，理解用户微调意图 | Claude Haiku / Llama 8B（本地）| < 2s |
| **审计器** | 检查推理器的输出是否合理（双模型校验）| 不同于推理器的另一个模型 | < 5s |

**推理器是核心。嵌入器是记忆。对话器是交互。审计器是安全网。**

### 3.2 推理器的输入输出规格

输入：
```json
{
  "diagnosis": {
    "spectrum": {"S1_SubPresence": -6.2, "S2_BassWarmth": -3.8, "S3_MidClarity": 0.72, "S4_AirBand": -17.1, "S5_SpectralTilt": -4.1},
    "dynamics": {"D1_LRA": 8.3, "D2_ChorusImpact": 3.2, "D3_MicroDynamics": 1.1, "D4_PLR": 7.8},
    "space": {"SP1_Correlation": 0.72, "SP2_ForeBackSep": 5.2, "SP3_RT60Consist": 0.15, "SP4_WidthHealth": true},
    "layers": {"L1_VocalSNR": 12.3, "L2_BassClarity": 0.18, "L3_DrumDetect": 0.72, "L4_LayerCount": 3},
    "emotion": {"E1_Direction": 0.65, "E2_Richness": 0.6, "E3_FatigueRisk": 0.28, "E4_SectionCont": 0.45}
  },
  "defects": [
    {"defect_id": "DEF-004", "parameter": "S4_AirBand", "severity": 3, "description_zh": "高频严重缺失"},
    {"defect_id": "DEF-001", "parameter": "S1_SubPresence", "severity": 3, "description_zh": "次低频严重不足"},
    {"defect_id": "DEF-009", "parameter": "SP2_ForeBackSep", "severity": 2, "description_zh": "前后深度不足"}
  ],
  "user_intent": "像一个深夜里的温暖拥抱",
  "platform": "spotify",
  "relevant_history": [...]  // 来自向量数据库的相似案例（可选）
}
```

输出：
```json
{
  "diagnosis_narrative": "这首歌的波场呈现暗调特征...",
  "recommended_emotion": "温柔觉醒 (GA)",
  "emotion_confidence": 0.78,
  "parameters": {
    "P01_vocal_presence_freq": {"value": 3000, "reasoning": "..."},
    "P02_vocal_presence_gain": {"value": 2.8, "reasoning": "..."},
    // ... P01-P15 全部
  },
  "risk_assessment": {
    "level": "green",
    "warnings": ["高频如果补超过 3dB 可能破坏暗调风格"],
    "mitigations": ["限制高频增益不超过 +2dB"]
  },
  "alternative_approaches": [
    {"name": "保留暗调", "desc": "少补高频，保留风格特征", "diff": {"P15": -1.0}},
    {"name": "明亮化", "desc": "激进补高频，朝明亮方向", "diff": {"P15": +2.5}}
  ],
  "explanation_to_user": "你的这首歌人声偏暗、低频身体感弱，但情绪基础是温柔的..."
}
```

### 3.3 为什么必须是 LLM 而不是查表

查表能回答：「缺陷 DEF-004 + 情绪 GA → 预设参数 rec 值」。

查表不能回答：
- 「高频 -17dB 是缺陷还是风格特征？」
- 「用户的'深夜拥抱'最接近哪种情绪？」
- 「+3dB 人声 EQ + +2.5dB 低频同时作用，中频会受影响吗？」
- 「如果用户不喜欢，备选方案是什么？」
- 「上次处理类似音频时，哪种参数组合用户最满意？」

**查表给出答案。LLM 给出判断。** 这是两种完全不同的软件。

## 四、最小可行的 AI 原生改造

### 4.1 不是推翻重来

我们已有的不是错的——诊断引擎（传感器）和 DSP 引擎（执行器）是高质量的传统元器件。**缺的只是把中间那个查表替换成 LLM。**

当前：
```
诊断 → DefectClassifier → CraftChainMatch (查表) → DSP 参数
```

改造后：
```
诊断 → DefectClassifier → LLM 推理（生成参数） → DSP 参数
                ↑
           用户意图（自然语言）
```

### 4.2 需要新增的代码

```
moodify-core-package/src/moodify/
├── llm/                          # 新增：LLM 元器件集成层
│   ├── __init__.py
│   ├── inference.py              # LLM 调用封装（多模型路由）
│   ├── prompts.py                # System prompt 模板
│   └── schemas.py                # LLM 输入输出结构定义
│
├── memory/                       # 新增：处理记忆系统
│   ├── __init__.py
│   └── history.py                # 处理记录存储 + 向量检索
│
├── diagnosis/                    # 不变
├── knowledge/                    # 退化：工艺卡变为 LLM 的参考数据
├── processing/                   # 不变
└── orchestration/                # 小改：Phase 1 diagnostic → LLM 调用
```

核心新增代码量估计：`llm/` ~300 行，`memory/` ~150 行。**不是重写系统，是插入一个元器件。**

### 4.3 LLM 调用策略

```python
class LLMRouter:
    """多模型路由：根据任务复杂度选择合适的模型"""

    def route(self, task: str, diagnosis: dict) -> str:
        """
        简单任务 → 本地小模型（Llama 8B, < 2s）
        复杂任务 → 云端大模型（Claude Sonnet, 5-10s）
        关键任务 → 双模型校验（推理 + 审计）
        """
        complexity = self._assess_complexity(diagnosis)
        if complexity < 0.3:
            return "local"       # 参数调整量 < 2dB, 1-2 个缺陷
        elif complexity < 0.7:
            return "cloud"       # 需要综合推理
        else:
            return "dual"        # 高风险：双模型校验
```

### 4.4 从「8 个预设」到「无限种可能」

改造后的用户交互：

```
用户: [上传音频]

Moodify: 我分析了这首歌。它的高频几乎完全缺失 (-17.1dB)，低频身体感很弱
         (-6.2dB)，但动态保持得不错 (LRA 8.3)。整体呈现暗调、内省的特质。
         
         你可以选一个方向，或者告诉我你想要的感觉：
         [温柔拥抱] [暗夜私语] [晨曦微光]
         [___________________________] (自己描述)

用户: 像清晨第一缕阳光穿过窗帘的感觉

Moodify: 理解了。清晨阳光意味着：
         - 温暖但不灼热 → 低频 +2dB, 高频 +2.5dB
         - 柔和通透 → 轻压缩 1.8:1, 保留微动态
         - 空间开阔但不空旷 → 混响 T60 1.2s, dry/wet 0.15
         - 立体声有宽度但不散 → 宽度 1.05

         另外我注意到你的歌高频极暗 (-17.1dB)，我建议 +2.5dB 而不是更多，
         避免破坏原始质感。要不要试试？

         或者你先听听原始版本？[播放原始]

用户: 试试

Moodify: [处理中... 3秒完成]
         
         处理好了。WHS 从 68 提升到 79。高频现在在合理范围内 (-14.6dB)，
         但保留了暗调风格。低频身体感从 -6.2dB 提升到 -3.7dB。
         
         你觉得怎么样？哪里需要调？
         [播放处理后]
```

**每次交互都不是「选预设」，而是「LLM 实时推理参数」。**

## 五、架构的根本改变

### 5.1 代码量分布的变化

| 层级 | 传统架构代码量 | AI 原生架构代码量 |
|------|-------------|-----------------|
| 诊断引擎 | 2000 行 | 2000 行 (不变) |
| DSP 执行器 | 700 行 | 700 行 (不变) |
| 工艺卡数据 | 1600 行 | 200 行 (退化为参考数据) |
| 匹配/决策逻辑 | 500 行 | **0 行 (被 LLM 替代)** |
| LLM 集成层 | 0 行 | **300 行** |
| 记忆系统 | 0 行 | **150 行** |
| System Prompt | 0 行 | **200 行** (最关键) |

**总代码量减少，但智能度暴涨。** System Prompt 的 200 行是整个软件的「灵魂」。

### 5.2 代码的性质变了

传统软件的代码是「操作指令」——告诉计算机每一步做什么。

AI 原生软件的代码是「元器件的连接线」——把感知、推理、执行、记忆连接起来。真正的「智能」不在代码里，在大模型的参数里。

**软件工程师从「写功能的人」变成「设计电路的人」。**

## 六、下一步

### 6.1 当前工程方案需要暂停

双轨并行方案（Python 引擎 + TS 前端）的基础假设是「8 个预设 + 查表匹配」。如果核心交互改为「LLM 推理参数」，那么：

1. 前端不需要「工艺卡列表」组件 → 改为「意图输入框 + LLM 诊断解读 + 处理选项」
2. 后端不需要 `CraftChainMatch` → 改为 `LLMInference`
3. `knowledge/craft_chains.py` 从算法数据退化为 LLM 的参考上下文
4. `knowledge/craft_chain_match.py` 可以删除（被 LLM 替代）

**这不是局部改动，是核心决策逻辑的替换。**

### 6.2 最小验证方案

在继续任何工程工作之前，先做一个最小验证：

```
1. 拿一首真实 AI 音乐 → 跑诊断引擎 → 得到 18 参数
2. 将 18 参数 + 用户意图描述 → 发给 Claude API
3. 看 LLM 能否生成合理的 15 参数 DSP 方案
4. 用生成的参数跑 DSP → 听效果
5. 对比：LLM 生成的参数 vs 工艺卡预设的参数
```

如果步骤 3 的效果明显好于工艺卡预设（或者至少相当），那整个工程方向就需要转向。

### 6.3 新工程方案预览

如果验证通过，新的工程方案是：

**单一焦点**：构建 LLM 集成层。

不需要双轨并行。不需要合并 python/ 栈。不需要 Electron 打包优化。

就一件事：**让大模型能读到诊断数据，能输出 DSP 参数，能解释自己的推理。**

前端可以是最简单的 HTML 对话框（甚至直接用 API 测试）。等核心智能验证通过后，再考虑 UI 包装。

## 七、核心认知

**互联网软件 = 代码实现功能。**

**AI 原生软件 = 代码连接元器件。大模型是其中最重要的那个元器件。**

这个认知转变意味着：
- 我们不是在「给软件加 AI 功能」
- 我们是在「用大模型替代软件的决策层」
- 剩余的传统代码只是大模型的「手」（DSP 执行）和「眼」（诊断感知）

**Moodify 的灵魂不是 DSP 管线，是「从症状到方案」的推理过程。**

这个过程，只有大模型能做。

---

*推理的下一步：用真实诊断数据 + Claude API 做最小验证。如果 LLM 生成的参数方案质量高于预设匹配，则整个工程方向确认转向。*
