## 缺口 1：Demucs 源分离是用户体验杀手

### 问题本质

3 分钟歌曲 → Demucs htdemucs 4-stem 分离 → **5 分 42 秒**。

这不是"慢"的问题，是"不可用"的问题。用户拖一个文件进去，等 6 分钟才能听到结果——这个产品没有人会用第二次。

### 根因分析

```
处理时间 = 诊断(17s) + Demucs(342s) + DSP(6s) + 母带(2s)
                                                  ↑
                                         占总时间 95%
```

Demucs 慢的原因：
1. htdemucs 是 Hybrid Transformer 模型，CPU 推理本身就慢
2. 4-stem 分离（vocals/drums/bass/other）需要跑 4 个模型
3. 48kHz 立体声输入，模型内部处理量大

### 深层问题

**Demucs 真的需要吗？**

回看 PRINCIPLE-001 的核心定义：
> Moodify = 情绪波场显影器
> 让原始波场中的情绪胚胎更准确、更清晰、更稳定

情绪显影的核心手段是：EQ、压缩、混响、谐波、空间——这些全都作用在**全混音**上就有效。源分离只是锦上添花，不是雪中送炭。

大部分 AI 音乐后期场景不需要分轨：
- 调整人声存在感 → Peak EQ 3kHz 就可以
- 增加温暖感 → Low Shelf 200Hz 就可以
- 增强空间感 → Reverb + M/S 宽度就可以
- 控制动态 → Compressor 全混音就可以

**源分离的价值场景是少数**：需要单独处理人声（去齿音、修音准）、需要重混鼓组、需要贝斯增强。这些是专家模式，不是默认模式。

### 解决方案

**方案：双模式架构**

```
快速模式（默认）：
  诊断 → 全混音增强 → 空间 → 母带
  耗时：< 60 秒
  适用：90% 的场景

完整模式（可选）：
  诊断 → 源分离 → 分层增强 → 空间 → 再合成 → 母带
  耗时：~6 分钟，有进度条
  适用：需要精细控制人声/鼓/贝斯的场景
```

实现要点：
- `WorkflowOrchestrator.process()` 增加 `skip_separation=True` 参数
- Phase 2 返回时直接透传全混音音频
- Phase 3 检测到无 stems 时走全混音路径（已有此逻辑！）
- Phase 5 无 stems 时跳过（已有此逻辑！）
- **代码改动量极小**，因为降级逻辑已存在于 workflow_engine.py

**额外优化（完整模式）**：
- 2-stem 替代 4-stem：只分离 vocals+accompaniment，速度约快 2 倍
- 更轻模型：`mdx_extra_q` 比 `htdemucs` 快约 30%
- 预处理降采样：Demucs 内部降采样到 44.1kHz，减少计算量

### 一句话

**Demucs 从默认路径改为可选路径。快速模式 < 60 秒，完整模式作为深度处理。改动量小，收益巨大。**

## 缺口 2：前端数据解析断裂

### 问题本质

后端返回了正确的诊断数据，前端展示了错误的值。雷达图 5D 全是 0.50，匹配分全是 40%。

### 根因分析

**问题 A：雷达图 5D 值全是 0.50**

原因是**两个 WaveState 模型不匹配**。

后端 API 返回的 `diagnosis.wave_state` 是 `WaveStateDiagnosis.to_dict()` 的输出，结构是：

```python
{
  "Spectrum": {
    "S1_SubPresence": -6.2,    # dB
    "S2_BassWarmth": -3.8,     # dB
    "S3_MidClarity": 0.72,     # [0,1]
    "S4_AirBand": -17.1,       # dB
    "S5_SpectralTilt": -4.5,   # dB/oct
  },
  "Dynamics": {
    "D1_LRA": 8.3,             # LU
    "D2_ChorusImpact": 4.1,    # LU
    "D3_MicroDynamics": 1.1,   # LU
    "D4_PLR": 12.5,            # dB
  },
  "Space": {
    "SP1_Correlation": 0.72,   # [-1,1]
    "SP2_ForeBackSep": 5.2,    # dB
    "SP3_RT60Consist": 0.45,   # seconds
    "SP4_WidthHealth": "healthy",
  },
  "Layers": {
    "L1_VocalSNR": 12.3,       # dB
    "L2_BassClarity": 0.18,    # [0,1]
    "L3_DrumDetect": 0.65,     # [0,1]
    "L4_LayerCount": 3,
  },
  "Emotion": {
    "E1_Direction": "gentle",
    "E2_Richness": 0.6,
    "E3_FatigueRisk": 0.28,
    "E4_SectionCont": 0.55,
  },
}
```

前端的 `extract5D()` 函数尝试从这个嵌套结构取 `S3_MidClarity`、`D1_LRA` 等字段，但**取字段的路径不对**——它在 `wave_state` 根层级找 `s?.S3_MidClarity`，但实际数据在 `wave_state.Spectrum.S3_MidClarity`（注意大写 S）。

而且，前端试图把异构参数（dB、LU、比率、标签）直接映射到 [0,1] 区间，映射逻辑过于简单（`/5000`、`/15`），没有考虑参数的物理意义和正常范围。

**正确的映射逻辑应该是**：

```
E (Energy/频谱丰富度):
  从 Spectrum 维度提取
  = f(S1_SubPresence, S2_BassWarmth, S3_MidClarity, S4_AirBand)
  归一化：低频饱满 + 中频清晰 + 高频不刺 → 高 E

D (Dynamics/动态呼吸感):
  从 Dynamics 维度提取
  = f(D1_LRA, D2_ChorusImpact, D3_MicroDynamics)
  归一化：LRA 8-12 LU → 高 D

S (Space/空间层次感):
  从 Space 维度提取
  = f(SP1_Correlation, SP2_ForeBackSep, SP4_WidthHealth)
  归一化：corr 0.5-0.85 → 自然宽度 → 高 S

T (Texture/瞬态清晰度):
  从 Layers 维度提取
  = f(L1_VocalSNR, L2_BassClarity, L3_DrumDetect)
  归一化：各声部清晰分离 → 高 T

H (Heart/情绪强度):
  从 Emotion 维度提取
  = f(E2_Richness, E4_SectionCont, E1_Direction 匹配度)
  归一化：情绪丰富 + 段落连贯 → 高 H
```

**问题 B：匹配分全是 40%**

原因是匹配逻辑用**中文文本子串匹配**。

诊断返回的缺陷：`DEF-S-001`、`DEF-S-003`（英文 ID + 中文描述）
工艺卡的 common_defects：`["人声存在感不足", "高频偏暗", ...]`（纯中文）

匹配代码：
```python
hits = sum(1 for cd in common if any(cd in dd for dd in defect_descs))
```

它在中文描述中做子串匹配，但诊断返回的中文描述（如"次低频存在感严重偏低 (-6.2)"）和工艺卡的简短描述（"人声存在感不足"）几乎没有直接子串匹配。所以 `hits` 始终为 0，`match_score = 0.40 + 0.12 × 0 = 0.40`。

### 解决方案

**修复 A：5D 值映射**

在 `DiagnosisDashboard.tsx` 的 `extract5D()` 中：

1. 正确访问嵌套对象：
```typescript
const spectrum = (wave_state as any).Spectrum || (wave_state as any).spectrum || {}
const dynamics = (wave_state as any).Dynamics || (wave_state as any).dynamics || {}
const space = (wave_state as any).Space || (wave_state as any).space || {}
const layers = (wave_state as any).Layers || (wave_state as any).layers || {}
const emotion = (wave_state as any).Emotion || (wave_state as any).emotion || {}
```

2. 每个维度实现分段线性映射函数，使用参数的物理意义：
```
E: SubPresence 正常范围 -4→+3 dB, BassWarmth -2→+4 dB, MidClarity 0.4→0.8
D: LRA 4→14 LU, ChorusImpact 1→6 LU
S: Correlation 0.3→0.9 (峰值在 0.5-0.85), ForeBackSep 2→10 dB
T: VocalSNR 6→18 dB, BassClarity 0.1→0.6, DrumDetect 0.3→0.9
H: Richness 0.2→0.9, SectionCont 0.3→0.8
```

**修复 B：工艺卡匹配**

建立 `defect_id → emotion_code` 的映射表，不依赖中文文本匹配：

```python
DEFECT_TO_EMOTION = {
    "DEF-S-001": ["HL", "GA"],  # 低频存在感不足 → 治愈温暖、温柔觉醒
    "DEF-S-002": ["HL", "GA"],  # 低频温暖感不足 → 同上
    "DEF-S-003": ["SE", "CN"],  # 高频空气感不足 → 神圣空灵、电影感
    "DEF-D-001": ["LW", "CN"],  # 微动态过高 → 孤独留白、电影感
    "DEF-L-001": ["UD", "WL"],  # 低频清晰度不足 → 都市危险、废土机械
    # ... 完整映射
}
```

匹配分 = 基础分(0.3) + 缺陷命中加权(0.4) + 情绪约束兼容性(0.3)

### 一句话

**前端拿到的数据是对的，解析方式是错的。修复数据映射逻辑 + 用缺陷 ID 映射表替代中文文本匹配，两个改动都不大。**

## 缺口 3：无持久化

### 问题本质

刷新页面 = 丢失所有会话。重启后端 = 丢失所有数据。这是产品级 bug。

### 根因分析

当前：`_store: dict[str, Session] = {}` — 纯内存，进程死了就没了。

影响：
- 用户上传了文件，刷新页面 → 文件还在磁盘上，但不知道 session_id
- 处理了一半，后端挂了 → 没有恢复机制
- 想回看之前的结果 → 不可能

### 解决方案

**方案：SQLite 轻量持久化**

为什么选 SQLite：
- 零配置、零依赖（Python 标准库自带 `sqlite3`）
- 单文件，适合桌面应用
- 不需要安装数据库服务
- 读写性能足够（本地桌面，不是高并发服务器）

数据模型（3 张表）：

```sql
CREATE TABLE sessions (
    id TEXT PRIMARY KEY,           -- session_id (UUID 前12位)
    filename TEXT NOT NULL,
    file_path TEXT NOT NULL,
    status TEXT DEFAULT 'uploaded', -- uploaded/diagnosed/processed/failed
    created_at TEXT NOT NULL,
    duration_s REAL,
    sample_rate INTEGER,
    channels INTEGER,
    diagnosis_json TEXT,           -- 诊断结果 JSON 字符串
    craft_matches_json TEXT        -- 工艺匹配结果 JSON
);

CREATE TABLE process_results (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT NOT NULL,
    craft_id TEXT NOT NULL,
    process_id TEXT,
    success INTEGER,
    output_path TEXT,
    result_json TEXT,              -- 处理结果 JSON 字符串
    created_at TEXT NOT NULL,
    FOREIGN KEY (session_id) REFERENCES sessions(id)
);

CREATE TABLE craft_usage (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    craft_id TEXT NOT NULL,
    session_id TEXT,
    used_at TEXT NOT NULL,
    eds_score REAL,               -- 效果评分
    user_rating INTEGER            -- 用户评分 (1-5)
);
```

关键设计决策：
- JSON 字段用 TEXT 存储（SQLite 没有原生 JSON 类型，但 Python json.dumps/loads 足够）
- 文件保留 7 天，超期自动清理（启动时检查，清理 sessions 和文件）
- craft_usage 表用于未来工艺卡可信度计算（对应 FORM-200）
- 数据库文件位置：`~/Moodify/data/moodify.db`（用户目录下）

`SessionManager` 改为：
```python
class SessionManager:
    def __init__(self, db_path="data/moodify.db"):
        self.db = sqlite3.connect(db_path)
        self._init_tables()
    
    def create(self, filename, raw_bytes) -> Session:
        # INSERT INTO sessions ...
        # 事务保护
    
    def get(self, session_id) -> Session | None:
        # SELECT from sessions, parse diagnosis_json
    
    # ... etc
```

改动范围：
- `session_manager.py` 重写（从 dict 改为 SQLite）
- `sessions.py` API 无需改动（SessionManager 接口保持一致）
- 启动时自动迁移（无旧数据时建表，有旧数据时兼容）

### 一句话

**从 `dict` 改为 SQLite，接口不变，数据存活。改动集中在一个文件，不影响其他模块。**

## 缺口 4：无错误恢复

### 问题本质

任何阶段失败 → HTTP 500 → 前端空白或卡住。用户不知道发生了什么，不知道该怎么办。

### 根因分析

当前错误处理的三个层次都薄弱：

```
API 层：    except Exception → raise HTTPException(500, "Internal Server Error")
处理层：    Phase 失败 → result.success=False，无降级
前端层：    catch → setState error → 显示 error banner（小字）
```

缺失的东西：
1. 错误分类（可恢复 vs 不可恢复）
2. 降级策略（这个阶段失败了，能不能跳过继续？）
3. 用户指引（"你的文件可能已损坏，请尝试用其他文件"）

### 解决方案

**三层错误处理体系**

**第一层：API 层 — 翻译错误**

```python
# 每种错误有：HTTP 状态码 + 中文消息 + 错误代码 + 建议操作

ERROR_MAP = {
    "corrupt_audio": {
        "status": 400,
        "message": "音频文件无法读取，文件可能已损坏",
        "code": "CORRUPT_AUDIO",
        "action": "请检查文件是否完整，尝试用其他播放器打开验证",
    },
    "unsupported_format": {
        "status": 400,
        "message": "不支持的音频格式",
        "code": "UNSUPPORTED_FORMAT",
        "action": "支持的格式：WAV、MP3、FLAC、AIFF、M4A",
    },
    "demucs_failed": {
        "status": 200,  # 不是错误，是降级
        "message": "源分离失败，已自动切换为全混音处理模式",
        "code": "DEGRADED_NO_SEPARATION",
        "action": None,
    },
    "dsp_failed": {
        "status": 200,
        "message": "部分音频处理未能完成，已保留原始音频",
        "code": "DEGRADED_PARTIAL",
        "action": "可以尝试其他工艺卡",
    },
    "out_of_memory": {
        "status": 507,
        "message": "内存不足，无法处理该文件",
        "code": "OUT_OF_MEMORY",
        "action": "请尝试较短的音频文件，或关闭其他应用后重试",
    },
}
```

**第二层：处理层 — 降级而不是失败**

WorkflowOrchestrator 每个 Phase 的降级策略：

```
Phase 1 诊断:
  降级: 快速诊断代替完整诊断
  不可降级场景: 文件完全无法读取 → 返回错误

Phase 2 源分离:
  降级: 跳过，使用全混音模式（默认路径就是降级路径）
  不可降级场景: 无

Phase 3 分层增强:
  降级: 全混音增强代替分轨增强
  不可降级场景: 音频数据本身损坏 → 返回原始

Phase 4 空间重构:
  降级: 单声道跳过 M/S 处理
  不可降级场景: 无

Phase 5 再合成:
  降级: 跳过
  不可降级场景: 无

Phase 6 母带:
  降级: 跳过限幅/响度标准化，输出未母带版本
  不可降级场景: 磁盘写入失败 → 返回错误

任何 Phase 失败 → 后续 Phase 检查输入是否可用 → 可用则继续 → 不可用则跳过
```

实现方式：每个 Phase 返回 `PhaseResult` 时标记 `degraded=True` + `degradation_reason`，前端可以展示。

**第三层：前端层 — 展示问题 + 引导行动**

```
错误类型 → 展示方式:

1. 可恢复错误（后端挂了）:
   → 全屏提示 "后端服务未启动，正在尝试重连..."
   → 自动重试 3 次，每次间隔 2 秒
   → 3 次后显示 "请手动启动后端：运行 moodify serve"

2. 处理降级（Demucs 失败）:
   → 黄色提示条 "源分离不可用，已使用全混音模式处理"
   → 处理继续，用户可以下载结果

3. 处理部分失败（某个 DSP 步骤失败）:
   → 黄色提示条 "高频增强未能应用（原因：XXX）"
   → 处理继续，Phase 列表显示哪个 Phase 被跳过

4. 文件问题（损坏/不支持的格式）:
   → 红色提示条 + 建议操作
   → 阻止继续

5. 超时（处理超过 10 分钟）:
   → 提示 "处理时间超过预期，是否继续等待？"
   → 按钮: [继续等待] [取消]
```

### 一句话

**不是所有失败都是 500。区分"不能用"和"降级用"，让用户知道发生了什么、可以做什么。大部分场景可以降级继续，只有真正的输入问题才阻断。**

## 缺口 5：无打包方案

### 问题本质

现在是开发环境。用户需要：安装 Python 3.10+、pip install、npm install、手动启动后端、手动启动前端。这不是产品，是开源项目。

### 根因分析

当前启动流程：
```
开发者: 
  1. pip install -e moodify-core-package
  2. python -m uvicorn moodify.api.main:app --port 8000
  3. cd moodify-pulse && npm install && npm run dev
  4. 浏览器打开 localhost:5173

用户（期望）:
  1. 双击 Moodify.exe
  2. 用
```

### 解决方案

**方案：分层打包**

核心思路：**把依赖按重量拆分，核心轻量打包，重依赖可选下载。**

```
Layer 1: 核心（必须打包）           ~150MB
  ├─ Python 3.11 嵌入式运行时        ~40MB
  ├─ moodify-core-package           ~1MB
  ├─ numpy, scipy, soundfile        ~60MB
  ├─ librosa                        ~30MB（诊断必需）
  ├─ pedalboard                     ~10MB
  ├─ fastapi, uvicorn, pydantic     ~10MB
  └─ Electron + React 前端          ~80MB（已构建）

Layer 2: 可选（首次使用下载）       ~2GB
  ├─ torch                          ~1.5GB
  └─ demucs                         ~500MB
```

**打包工具选型**：

| 工具 | PyInstaller | Nuitka | Embedded Python |
|------|------------|--------|-----------------|
| 打包方式 | 单文件 exe | 编译为 C | 便携 Python 目录 |
| 启动速度 | 慢（解压到临时目录） | 快 | 快 |
| 包大小 | 最小 | 中等 | 最大 |
| 调试难度 | 难 | 中 | 易 |
| 兼容性 | 好 | 好 | 最好 |

**推荐：Embedded Python + 启动脚本**

原因：
1. 调试最友好（文件结构可见，错误日志清晰）
2. 修改代码不需要重新打包（`pip install -e` 语义）
3. 可选依赖（Demucs）可以后续安装
4. Electron 打包时直接把 Python 目录作为 extraResource

实现：
```
Moodify Post Lab/
├── Moodify Post Lab.exe        # Electron 主程序
├── resources/
│   └── python/                  # Embedded Python 运行时
│       ├── python.exe
│       ├── Lib/
│       │   └── site-packages/
│       │       └── moodify/     # 核心引擎（预装）
│       └── ...
├── data/
│   └── moodify.db               # SQLite 数据
└── uninstall.exe
```

Electron 启动时：
```typescript
// 1. 找到 resources/python/python.exe
// 2. spawn("resources/python/python.exe", ["-m", "uvicorn", "moodify.api.main:app", ...])
// 3. 首次运行检查依赖：import moodify → 失败 → 提示运行安装脚本
// 4. 健康检查通过 → 加载前端
```

安装包生成：
```powershell
# 1. 构建 Python 环境
cd moodify-core-package
pip install -e . --target ../build/python/Lib/site-packages

# 2. 复制嵌入式 Python
# 从 python.org 下载 Windows embeddable package

# 3. 构建前端
cd moodify-pulse
npm run build

# 4. 打包 Electron
```

## 五缺口的优先级和依赖关系

```
缺口 3（无持久化）──→ 缺口 4（错误恢复）依赖持久化来保存错误状态
缺口 2（前端解析）──→ 独立修复，不依赖其他
缺口 1（Demucs 慢）──→ 缺口 5（打包）时决定 Demucs 是否预装

建议顺序：
  第一天：缺口 2（前端解析）→ 立即看到正确数据
  第一天：缺口 1（快速模式）→ 处理速度从 6 分钟降到 60 秒
  第二天：缺口 3（SQLite 持久化）→ 刷新不丢数据
  第三天：缺口 4（错误降级）→ 各种边缘情况不会白屏
  第四-五天：缺口 5（打包）→ 能给其他人安装
```

## 总结：五个缺口，五个策略

| 缺口 | 核心策略 | 改动范围 | 收益 |
|------|----------|----------|------|
| Demucs 太慢 | 默认跳过，快速模式 < 60s | workflow_engine.py 一个参数 | 从不可用到可用 |
| 数据展示错 | 修复映射逻辑 + 缺陷 ID 表 | DiagnosisDashboard.tsx + sessions.py | 从假数据到真数据 |
| 无持久化 | dict → SQLite | session_manager.py 一个文件 | 从玩具到产品 |
| 无错误恢复 | 三层降级：API/处理/前端 | 分散在各层 | 从脆弱到韧性 |
| 无打包 | 嵌入式 Python + Electron | 打包脚本 + Electron 配置 | 从开发环境到安装包 |

**核心思想**：小改动、大收益。不改架构，只补缺口。每个缺口独立可修，互不阻塞。
