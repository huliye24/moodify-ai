# Moodify 交付级版本分析：从 MVP 到稳定可交付

**日期**：2026-05-28
**作者**：Claude (分析) / 影焰实验室
**背景**：MVP 全栈管线已跑通（上传→诊断→工艺匹配→六阶段处理→下载），现在需要思考如何做到稳定交付。
**18：38**
---

## 一、当前真实状态

### 1.1 已经有了什么

| 模块 | 成熟度 | 实际表现 |
|------|--------|----------|
| 诊断引擎 | 75% | 18 参数提取正确，17s/首，WHS 计算有效 |
| 工艺库 | 80% | 8 情绪 × 15 参数完整，风险警告到位 |
| DSP 链 | 70% | pedalboard 集成正确，但参数映射有缺失（P10 reverb_t60 未使用） |
| 工作流引擎 | 60% | 六阶段跑通，但 Demucs 是唯一瓶颈（5分钟+） |
| API 服务 | 50% | 端点可用，但无认证、无持久化、无异步、无进度推送 |
| 前端 UI | 40% | 五阶段向导可用，但数据展示有问题（雷达图值固定、匹配分单一） |
| Electron 壳 | 30% | 能启动 Python 后端，但无打包、无监控、无优雅关闭 |
| CLI | 60% | 命令可用，但 analyze 输出中文乱码、无 JSON 模式默认输出 |

### 1.2 最关键的五个缺口

1. **Demucs 源分离是用户体验杀手** — 3 分钟歌曲处理需 6-8 分钟，用户不可能等
2. **前端数据解析断裂** — 雷达图 5D 值全是 0.50，匹配分全是 40%，诊断数据已正确返回但未正确展示
3. **无持久化** — 重启丢失所有会话，刷新页面丢失上传的文件
4. **无错误恢复** — 任何环节失败都是 500，用户不知道发生了什么
5. **无打包方案** — 用户需要装 Python + Node.js + pip install + npm install 才能运行

## 二、交付级架构设计

### 2.1 核心原则

```
不做完美架构，做可用的架构。
每拆一个模块，必须有明确的价值——更快、更稳、或更好维护。
```

### 2.2 目标交付形态

```
用户下载一个安装包（.exe / .dmg）
  → 双击安装
  → 打开 Moodify Post Lab 桌面应用
  → 拖入 AI 生成的音频文件
  → 看到诊断结果（< 20 秒）
  → 选择目标情绪
  → 听到处理后的版本（< 60 秒，快速模式）
  → 下载成品
```

关键数字：
- 安装时间：< 2 分钟
- 首次诊断：< 20 秒
- 快速处理（无源分离）：< 60 秒
- 完整处理（含源分离）：< 10 分钟，有进度条
- 内存占用：< 2GB（4GB 机器可运行）

### 2.3 推荐架构

```
┌─────────────────────────────────────────────┐
│  Electron 壳                                 │
│  ├─ 管理 Python 进程生命周期                 │
│  ├─ 健康检查 + 自动重启                      │
│  └─ 原生文件对话框                           │
├─────────────────────────────────────────────┤
│  React 前端                                  │
│  ├─ 状态机: idle→uploaded→diagnosing→        │
│  │          diagnosed→processing→completed    │
│  ├─ WebSocket 接收处理进度                   │
│  └─ 本地 SQLite 缓存诊断结果                 │
├─────────────────────────────────────────────┤
│  Python FastAPI 后端                          │
│  ├─ REST: 上传、诊断、工艺匹配、下载          │
│  ├─ WebSocket: 处理进度推送                  │
│  ├─ SQLite: 会话 + 工艺卡使用记录             │
│  └─ 后台任务队列: 异步处理                    │
├─────────────────────────────────────────────┤
│  EWE 核心引擎                                 │
│  ├─ 诊断: 快速模式 (< 5s) / 完整模式 (~17s)   │
│  ├─ 处理: 快速模式 (跳过 Demucs) / 完整模式   │
│  └─ 导出: WAV 24bit + MP3 320kbps            │
└─────────────────────────────────────────────┘
```

## 三、分阶段交付计划

### Phase A：可演示版（1-2 天）

目标：UI 正确展示数据，端到端流程可演示

**A1. 修复前端数据解析**
- 雷达图从 WaveState 诊断对象提取真实的 5D 值
- 工艺卡匹配分基于缺陷覆盖差异化（不是全 40%）
- 处理进度实时展示六阶段状态

**A2. 处理模式分级**
- 添加"快速模式"开关：跳过 Demucs Phase 2
- 快速模式：诊断 → 全混音增强 → 空间 → 母带（< 60 秒）
- 完整模式：全部六阶段（> 5 分钟，显示进度）

**A3. 错误处理加固**
- 每个 API 端点有明确的错误消息（中文）
- 前端显示具体错误而非空白
- 后端不可用时前端提示"后端未启动"

### Phase B：可测试版（1 周）

目标：可在其他机器上安装运行，核心流程稳定

**B1. Python 环境打包**
- 方案：PyInstaller 将 moodify-core-package 打包为单个 .exe
- Electron 的 extraResources 包含这个 .exe
- 用户不需要装 Python

**B2. 持久化**
- SQLite 替代内存字典
- 会话重启后仍可访问
- 处理结果保留 7 天自动清理

**B3. 后端进程管理**
- Electron 启动时自动寻找/启动 Python 后端
- 健康检查：每 5 秒 ping，挂了自动重启
- 应用退出时优雅关闭 Python
- 端口冲突时自动选择备用端口

**B4. 安装程序**
- electron-builder 生成 NSIS 安装包（Windows）
- 安装后桌面快捷方式
- 卸载时清理所有数据

### Phase C：可交付版（2-3 周）

目标：性能达标，可以给外部用户使用

**C1. 异步处理 + 进度推送**
- WebSocket 端点：实时推送六阶段进度
- 处理请求立即返回 process_id，前端通过 WS 订阅
- 支持取消正在进行的处理

**C2. 性能优化**
- 诊断缓存：同一文件不重复诊断
- 音频流式读取：不一次性加载整个文件到内存
- 并行处理：多文件批量时并行诊断
- Demucs 优化：使用 CPU 优化的模型配置

**C3. 音频播放改进**
- 使用 Web Audio API 替代 HTML5 `<audio>`
- 支持 A/B 无缝切换（同位置对比）
- 响度匹配播放（LUFS 对齐，避免响度偏差）

**C4. 输出格式**
- WAV 24bit/48kHz（主要输出）
- MP3 320kbps（预览/分享）
- Markdown 处理报告
- JSON 诊断数据（可导入其他工具）

## 四、性能关键路径分析

### 4.1 时间消耗拆解（3 分钟立体声 48kHz）

| 阶段 | 当前耗时 | 目标（快速） | 目标（完整） |
|------|----------|-------------|-------------|
| 文件上传 | < 2s | < 2s | < 2s |
| Phase 1: 诊断 | 17s | < 5s (轻量模式) | 17s |
| Phase 2: 源分离 | 5m42s | 跳过 | 5m (可接受) |
| Phase 3: 分层增强 | ~3s | ~2s (全混音) | ~8s (4 stems) |
| Phase 4: 空间重构 | < 1s | < 1s | < 1s |
| Phase 5: 再合成 | < 1s | 跳过 | < 2s |
| Phase 6: 母带 | ~2s | ~2s | ~2s |
| **总计** | **~6m** | **< 60s** | **~6m** |

### 4.2 最大瓶颈

**Demucs 源分离（5 分 42 秒）**占总时间的 95%。

三个选择：
1. **快速模式默认跳过** — 大多数场景不需要 stem 分离
2. **GPU 加速** — CUDA 可将 Demucs 降到 30 秒，但增加安装复杂度
3. **更换模型** — `htdemucs_ft` 更快但质量略低，`mdx_extra_q` 更快

**推荐策略**：快速模式默认跳过 Demucs，完整模式作为"深度处理"选项。

### 4.3 内存关键路径

当前处理流程一次性加载全部音频到内存：
- 3 分钟 48kHz 立体声 WAV ≈ 100MB
- Demucs 4 stems 各 100MB ≈ 400MB
- 处理中间缓冲 ≈ 200MB
- **峰值**：约 700MB

对于 10 分钟音频：峰值可能超过 2GB。

优化方向：
- 流式处理（librosa 支持分块加载）
- 及时释放不再需要的 stem 数组
- 限制并发处理数

## 五、稳定性关键路径

### 5.1 当前最容易崩溃的场景

1. **损坏的音频文件** → librosa/soundfile 加载失败 → 500
2. **超大文件（>200MB）** → 内存不足 → 进程被杀
3. **Python 进程意外退出** → 前端无限等待
4. **端口被占用** → 启动失败，无提示
5. **磁盘空间不足** → 写入失败，静默

### 5.2 必须加固的点

```
输入层:
  ├─ 文件格式白名单验证 + Magic bytes 检测（不只是扩展名）
  ├─ 文件大小预检 + 内存预估
  └─ 损坏文件友好错误提示

处理层:
  ├─ 每一步有 try/except + 降级策略
  ├─ Demucs 失败 → 自动降级为全混音模式
  ├─ DSP 失败 → 保留原始音频，标记该阶段
  └─ 母带失败 → 输出未母带版本

输出层:
  ├─ 写入前检查磁盘空间
  ├─ 写入后验证文件完整性（soundfile 回读）
  └─ 临时文件定期清理
```

## 六、前端数据展示修复

### 6.1 雷达图 5D 值

**问题**：当前展示全是 0.50，因为提取逻辑试图从 WaveState 诊断对象获取 `S3_MidClarity` 等字段，但诊断返回的是 `wave_state` 嵌套对象，结构不同。

**修复**：从 `diagnosis.wave_state` 的五个子对象（Spectrum/Dynamics/Space/Layers/Emotion）提取有意义的归一化值。

### 6.2 工艺卡匹配分

**问题**：全是 40%，因为缺陷 ID 匹配命中率 0%（诊断返回的 defect_id 格式是 DEF-S-001，工艺卡的 common_defects 是中文描述）。

**修复**：使用关键词语义匹配替代精确 ID 匹配，或直接在工艺卡中维护 defect_id 映射表。

## 七、不做的事情（明确边界）

以下功能**不在交付范围内**，避免范围蔓延：

- 用户注册/登录系统（本地软件不需要）
- 云端处理/GPU 集群
- 实时协作
- 插件市场
- 移动端
- AI 音乐生成（Moodify 只做后期处理）
- 自动混音（保留人工选择工艺卡的环节）
- 社交分享

---

## 八、一句话总结

**当前状态**：管线跑通了，但还不能交付——前端展示有 bug，Demucs 太慢，没有打包方案。

**优先做三件事**：
1. 修复前端数据展示 + 添加快速模式（跳过 Demucs）→ 可演示
2. PyInstaller 打包 + SQLite 持久化 + Electron 进程管理 → 可安装
3. WebSocket 进度推送 + 诊断缓存 + 音频流式读取 → 可交付

**时间估算**：Phase A 1-2 天 → Phase B 1 周 → Phase C 2-3 周 → 总共约 1 个月到可交付状态。
