# Moodify 工程原则与协作经验

**版本：** 0.1  
**建立日期：** 2026-08-02  
**适用范围：** Moodify 全部产品、服务、客户端、任务包、分析与发布工作  
**文档性质：** 项目级工程宪章；若任务包与本文冲突，以更严格且经授权的规则为准

## 1. 工程愿景：高级的秩序美

Moodify 是一个复杂系统。我们的目标不是假装复杂性不存在，也不是通过持续堆叠功能证明能力，而是让复杂性被稳定边界、有限入口、明确责任和可追溯证据组织起来。

南京明城墙没有消灭城内的山川、街巷、人口和防务复杂性。它通过连续围护、有限城门、分段责任和可维修结构，使复杂性不再直接压到每一个使用者身上。Moodify 的工程目标与此相同：

> 复杂性可以存在于墙内，但跨越边界必须经过稳定城门；用户看到作品、意图、进度、试听和决定，工程系统承担算法、任务、失败恢复和证据。

“隐形”不等于隐藏错误。被围护的复杂度必须有所有者、诊断入口、测试契约和回滚路径。

## 2. 十条基本原则

### 2.1 用户面对稳定门面，内部实现可以演进

- Android App、未来桌面端和云端只依赖版本化 API，不调用 Python 内部函数；
- 公共入口少而稳定，内部模块可以重构；
- 用户不需要理解 DSP、模型、能力注册或任务编排，但必须知道系统做了什么、是否完成、能否撤销；
- 错误必须翻译为可行动状态，同时保留工程诊断证据。

### 2.2 一个事实只能有一个权威来源

- API schema、任务状态、当前版本、验收结论和指标定义分别只有一个权威写入者；
- 其他文件和页面是派生视图，不得形成平行真相；
- orchestration 描述计划，handoff 描述执行方交付，acceptance 描述 Judge 的验收事实；
- 冲突必须显式暴露，禁止以文件修改时间或“最后写入”静默解决。

### 2.3 边界先于并行，契约先于实现

- 多 Worker 并行前先确定目录所有权、接口所有权和禁止范围；
- 共享接口先冻结 schema、错误语义、版本和兼容策略，再由两侧分别实现；
- 不允许客户端为了等待服务端而复制临时后端；
- 不允许服务端猜测客户端状态或绕过正式协议。

### 2.4 证据先于完成声明

- “代码写完”“能够编译”“局部测试通过”均不等于完成；
- 完成必须由可复现命令、测试日志、产物 hash、真机/真实环境证据和已知问题共同证明；
- DeepSeek 等执行 Worker 只能提交 `READY_FOR_CODEX_REVIEW / REWORK / HOLD`；
- 最终 `ACCEPT` 由 Codex 或授权用户独立验收后写入。

### 2.5 失败关闭，不制造伪成功

- 缺少数据写 `NOT_MEASURED`，不能写 0；
- 采集不完整写 `PARTIAL`，不能生成完整结论；
- 处理未知写“正在重新同步”，不能用计时器猜进度；
- 未验证、hash 不一致或来源不明的音频产物不得进入 READY/ACCEPTED；
- 禁止通过删除测试、吞异常、扩大 skip 或空实现取得绿灯。

### 2.6 历史追加，不静默改写

- 任务事件、版本决定、规则更新、分析运行和验收记录采用追加式历史；
- 修正通过新事件和 `supersedes` 关系完成；
- 原始音频、已验收记录和已发布产物不被覆盖；
- 时间戳快照不可被实时扫描覆盖。

### 2.7 先完成纵向闭环，再横向扩张功能

优先完成一条可交付主链路：

```text
输入 -> 项目 -> 任务 -> 处理 -> 验证 -> 试听 -> 决定 -> 交付
```

- 主链路尚未可靠时，不增加支付、社区、多人协作、云规模化或大量专业参数；
- 一个真实闭环比十个孤立页面更有价值；
- 每次扩张前必须确认测试、状态、回滚和观测门禁仍然成立。

### 2.8 语言按责任分工，不以重写证明进步

- Kotlin 管理 Android 体验、生命周期、存储和播放；
- Python 管理音频分析、DSP、模型、知识和快速研究；
- Go 只有在本地网关、并发接入和单文件部署出现真实需求时引入；
- 新语言必须减少的复杂度大于新增的构建、调试、部署和人才成本；
- 禁止为追求“先进”重写已经验证的音频内核。

### 2.9 本地与云端共享同一协议

- App 不假定后台一定是 USB 电脑、局域网电脑或云服务器；
- 本地服务、未来 Go Gateway 和云端实现同一 API 契约；
- 项目、上传、任务、版本和产物使用稳定 ID；
- 输入输出进入抽象存储，不把电脑绝对路径暴露给客户端；
- 任务是异步状态机，不用长 HTTP 请求等待整个处理过程。

### 2.10 优化投入回报，而不是优化活动数量

- 优先恢复测试、状态和回滚等会提高后续所有工作的基础能力；
- 记录 active / wait / rework / machine 时间，不能只记录总历时；
- 模型 ROI 与财务 ROI 明确分离；
- 没有用户价值、工时或质量数据时，拒绝做虚假精确结论；
- 判断“水平化”至少需要连续三个阶段窗口，而不是一次感觉。

## 3. 系统责任边界

### 3.1 Android App

负责：

- 项目与作品入口；
- 意图输入；
- 上传、任务和连接状态；
- 原版/处理版 A-B 试听；
- 版本决定、下载、保存与分享；
- 生命周期恢复和用户可理解的错误。

不负责：

- 完整 Python 环境；
- 大型模型和专业 DSP 渲染；
- 直接修改引擎内部状态；
- 保存唯一正式项目数据；
- 伪造处理进度或质量结论。

### 3.2 本地电脑服务

负责：

- 手机配对、鉴权和 API；
- 文件接收、hash、去重和持久化；
- 项目、任务、版本和产物的正式记录；
- 调用 Moodify Engine；
- 真实进度、失败恢复、质量验证和技术日志。

### 3.3 Moodify Engine

负责：

- 音频分析、诊断和方案；
- DSP、模型和外部工具；
- 质量验证、证据和知识反馈；
- 输入、参数、引擎版本和结果 hash 的可追溯关系。

### 3.4 未来云端

云端不是另一套产品，只是同一协议的可横向扩展实现：API Gateway、对象存储、任务队列、Worker、验证和通知。App 的主流程不得因后台从电脑迁移到云端而重写。

## 4. 双 Worker 并行规则

### 4.1 默认所有权

| Worker | 可写目录 | 默认只读目录 |
|---|---|---|
| DeepSeek-PC | `moodify-core-package/`、`project_analytics/`、经授权的 `docs/api/` | `apps/android/` |
| DeepSeek-Android | `apps/android/` | Python 引擎与服务端业务目录 |

任务包和验证产物应使用各自独立目录，不得同时编辑同一个 `HANDOFF.md`。

### 4.2 共享接口所有权

- `docs/api/` 的版本化 schema 默认由 PC Worker 单一写入；
- Android Worker 消费冻结 schema，并通过客户端契约测试反馈问题；
- schema 变更必须包含版本、兼容影响、迁移策略和双方测试；
- 同一轮中不得双方各自修改 DTO 含义。

### 4.3 合法并行方式

```text
PC Worker：恢复测试、领域导出、服务端契约
Android Worker：工程构建、设计系统、页面和真机适配
                       ↓
               API 契约汇合门
                       ↓
PC Worker：上传/任务/产物服务端
Android Worker：客户端上传/状态/试听
```

### 4.4 冲突处理

- 发现范围重叠立即停止写入，保留现场并通知 Judge；
- 不通过 checkout、reset、clean、stash 或覆盖文件解决冲突；
- 接口争议先更新决策记录，再修改实现；
- 无法判定的文件和状态保留 `UNKNOWN`，由用户决定。

## 5. 任务包与执行纪律

每个正式任务包至少包含：

```text
00_TASK_ORCHESTRATION.md
01_DEEPSEEK_EXECUTION_COMMAND.txt
02_CODEX_ACCEPTANCE_MATRIX.md
```

执行方必须交付：

```text
PROGRESS.md
VALIDATION.md
FAILURE_LEDGER.md
HANDOFF.md
```

每个任务必须声明：目标、依据、依赖、允许范围、禁止范围、阶段、P0 门槛、停止条件、时间上限和最终状态集合。

时间目标不是放弃证据的授权。到期但依赖未满足或 P0 未通过时，应当 `HOLD/REWORK`，而不是写成完成。

## 6. 测试与质量门禁

质量门禁按由浅到深排列：

```text
静态检查
  ↓
测试收集
  ↓
快速单元测试
  ↓
领域与 API 契约测试
  ↓
集成测试
  ↓
纵向端到端
  ↓
真机/真实环境验收
```

规则：

- 全量测试无法收集时，不宣称系统测试基线绿色；
- Android Preview 不能代替 APK 构建和真机安装；
- API 两侧必须通过同一契约样例；
- 音频结果要验证 hash、格式、质量证据和不覆盖原音；
- 修复必须包含防复发测试；
- 新边界违例为 0，存量债务只降不升。

## 7. 数据、隐私与安全

- 原始音频默认本地处理，未经授权不上传第三方；
- 手机只申请完成任务所需权限，优先使用系统文件选择器和 MediaStore；
- 令牌进入 Android Keystore，不写源码、日志或普通配置；
- API 不返回电脑绝对路径、Python traceback 或内部密钥；
- 日志不记录音频内容、令牌、个人文件名等不必要信息；
- 测试使用授权或合成音频；
- 发布密钥只能由用户授权创建和保管。

## 8. 工作区保护

- 默认工作区可能包含用户未提交修改；
- 修改前检查目标文件，避免覆盖并行 Worker 和用户内容；
- 禁止未经授权执行 `git reset --hard`、`git clean`、`git stash`、`git checkout --`；
- 删除、移动和批量重写前必须解析并确认精确目标；
- 生成物与源码分开，临时文件不进入正式目录；
- 未跟踪文件不能被视为可随意删除的垃圾。

## 9. 可观测性与工程分析

常态化观测：

- 测试收集错误、门禁状态和耗时；
- 任务冲突、UNKNOWN、在制品和首次验收率；
- 工作区分类覆盖率；
- 新边界违例、公共 API 增量和核心改动集中度；
- active、wait、rework 和 machine 时间。

阶段性观测：

- 改动传播范围；
- 同等投入下的验收产出；
- 用户任务成功率、节省时间和音频质量；
- 是否进入“资产增长但单次扰动稳定或下降”的水平化阶段。

所有分析运行必须带 Asia/Shanghai 时间戳、manifest、来源、限制和不可覆盖产物。Excel/PDF 是展示层，结构化数据才是复核来源。

## 10. 发布与收尾

任何版本封板至少执行：

1. 冻结功能范围；
2. 独立、可重复构建；
3. 记录版本、API、Engine 和产物 SHA-256；
4. 在目标设备全新安装或部署；
5. 连续两次跑通主链路；
6. 测试断网、进程终止、服务重启和数据恢复；
7. 检查权限、日志、密钥、许可证和已知风险；
8. P0 清零，残余 P1 获得用户明确批准；
9. 生成安装、恢复、回滚、已知问题和验收文档；
10. 由独立 Judge 写最终 acceptance，并登记项目分析。

不能以“基本完成”“应该可以”或单次成功替代封版证据。

## 11. 工程决策检查表

开始一项工作前，回答：

- 它解决的是用户问题还是内部活动？
- 权威数据源和接口所有者是谁？
- 修改范围、失败边界和回滚方式是什么？
- 是否能用现有语言和组件完成？
- 如何证明完成，而不是仅证明写过代码？
- 是否保护了用户工作区、原始音频和历史记录？
- 是否会让未来从本地迁移到云端更加困难？
- 它隐藏了什么复杂度，复杂度由谁维护和诊断？

如果这些问题无法回答，任务应先进入方案评估，而不是直接编码。

## 12. 最终准则

Moodify 的高级秩序美不来自页面更少、文件更少或技术更新，而来自：

```text
有限入口
明确边界
单一事实
失败诚实
历史可追
结果可撤销
证据可复核
复杂度有归属
```

工程的最高目标不是让系统看起来简单，而是让用户能够安全、稳定、低负担地使用一个真正复杂而强大的系统。
