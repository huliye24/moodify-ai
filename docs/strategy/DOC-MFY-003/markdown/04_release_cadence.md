# DOC-MFY-003｜研发节奏与冻结规则

> v0.4 采用"输入冻结→P0 修复→P1 补完→回归→P2 判断→封口"的六阶段节奏。
> 每个阶段有明确的进入/退出条件和冻结门禁。

---

## 1. 六阶段节奏总览

```text
Phase 0: 章程签核     Phase 1: P0 修复     Phase 2: P1 补完
[──── 0.5d ────]     [───── 2d ─────]     [───── 5d ─────]
                                                    │
Phase 3: 回归测试     Phase 4: P2 判断     Phase 5: 封口归档
[───── 1d ─────]     [───── 1d ─────]     [───── 1d ─────]
```

| 阶段 | 名称 | 预计耗时 | 关键活动 | 退出条件 |
|------|------|----------|----------|----------|
| P0 | 章程签核 | 0.5 天 | Founder/CTO 审阅并批准 DOC-MFY-003 | GATE-09 签核通过 |
| P1 | P0 修复 | 2 天 | ACU-001/002/003 的研发和验收 | 3 个 P0 AEP 的 MUST 验收项全部通过 |
| P2 | P1 补完 | 5 天 | ACU-004/005/006 的研发和验收 | 3 个 P1 AEP 的 MUST 验收项全部通过 |
| P3 | 回归测试 | 1 天 | 全量 pytest + MRS 回归 + ruff lint | GATE-03/04/05/06 全部通过 |
| P4 | P2 判断 | 1 天 | 评估 P2 任务 (ACU-007~010) 是否合入 v0.4 | P2 合入/推迟决定已记录 |
| P5 | 封口归档 | 1 天 | DOCX/PDF 生成 + 图表创建 + 最终验收 | GATE-01~09 全部通过 |

**总预计耗时：约 10.5 天**

## 2. 冻结门禁

### F-INPUT: 输入冻结

**触发时间**：P1 开始前（章程签核后立即生效）

**冻结内容**：
- DOC-MFY-003 的 In Scope / Out of Scope 边界
- AEP-ACU-001~010 任务范围
- 测试音频基线集（`tests/data/baseline/v04/`）

**冻结后变更流程**：任何变更→范围变更控制流程（见 01_scope_boundary.md §4）

### F-P0: P0 实现冻结

**触发时间**：P1 阶段完成时

**冻结内容**：
- ACU-001/002/003 的实现代码
- P0 修复的实验数据和验收证据

**冻结后变更流程**：P0 代码如需修改→必须重新通过 P0 验收 + 回归测试

### F-P1: P1 实现冻结

**触发时间**：P2 阶段完成时

**冻结内容**：
- ACU-004/005/006 的实现代码
- 7 频段定义文件（此后再改频段需大版本号递增）
- True Peak Limiter 的参数

### F-MRS: MRS 参考基线冻结

**触发时间**：P3 回归测试通过后

**冻结内容**：
- 20 首基线音频的处理后 MRS 分数（作为未来版本的回归基准）
- MRS 计算管线的版本快照

### F-RELEASE: 发布冻结

**触发时间**：P5 封口完成时

**冻结内容**：
- v0.4 全部代码、文档、测试基线、验收证据
- 创建 git tag: `v0.4.0-acu`
- DOC-MFY-003 全部交付物转为只读

## 4. 节奏控制原则

1. **P0 不可并行压缩。** 三个 P0 任务虽无代码依赖冲突，但共用一个测试基线集和同一批验收资源（ruff/pytest/MRS 回归）。
2. **P1 的节奏瓶颈是 ACU-006。** Mel/Bark/ERB 三种尺度的实现 + 验证需要 2 天——不要试图在 1 天内完成。
3. **P2 不拖延 P5。** 如果 P2 验收在 Day 9 下午 3 点前未完成，自动推迟到 v0.5。P5 封口日期不因 P2 延期。
4. **每个阶段完成后，先冻结再进入下一阶段。** 不跳跃，不回滚。
