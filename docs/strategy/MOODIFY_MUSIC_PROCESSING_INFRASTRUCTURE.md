# Moodify 音乐处理基础设施定位

**状态：现行战略定义**  
**生效日期：2026-07-30**  
**适用范围：Moodify v2.0.0-mvp 之后的产品与研发决策**

开发模式由`MOODIFY_CIVILIZATIONAL_DEVELOPMENT_MODEL.md`约束：20年时间尺度、年度稳定版本、每天4小时可持续推进、实验层与工业主线隔离。

## 1. 一句话定义

> Moodify 是供音乐公司调用的无创作者前端音乐处理基础设施：它接收结构化制作任务，将制作判断转化为可执行、可复现、可审查、可积累的专业音频生产流程。

“音乐工业基础设施”在 Moodify 中特指**声音生产基础设施**，不表示 Moodify 覆盖音乐产业的全部职能。

## 2. 组织边界

### 2.1 荣景文川负责

- 接触、沟通和理解创作者；
- 判断创作者才华、作品价值和签约可能性；
- 完成艺人定位、审美方向和制作目标判断；
- 将自然语言需求转译为结构化制作任务；
- 选择最终版本并承担艺术决策；
- 负责签约、宣发、发行、舞台、商务和长期运营。

### 2.2 Moodify 负责

- 接收原始音频、分轨、参考、目标、保护项和禁止项；
- 执行声学扫描、诊断、Treatment Plan 和音频处理；
- 生成可追踪的候选版本；
- 执行技术质量门、风险检查和合规判断；
- 保存参数、版本血缘、报告、人工决定和交付记录；
- 将项目结果写回 Craft Library，积累可复用的声音生产知识；
- 通过 API、任务队列和运行时能力被公司内部系统稳定调用。

## 3. 标准生产关系

```text
创作者 / 艺人
  -> 荣景文川沟通、判断和定义制作目标
  -> ProductionSpec（结构化制作任务）
  -> Moodify诊断、处理、候选生成和技术质检
  -> ProductionResult（候选音频、报告和证据）
  -> 荣景文川试听、选择和艺术决策
  -> Moodify归档、交付和工艺写回
```

Moodify 可以判断候选版本是否满足 `ProductionSpec`，但不得自行决定创作者应该采用何种艺术路线。

## 4. 核心输入合同

后续版本应逐步将现有 `CreativeBrief` 的外部语义收敛为公司提交的 `ProductionSpec`。v2 数据模型暂不破坏性改名，通过兼容映射演进。

`ProductionSpec` 至少表达：

- 原始音频、分轨及素材身份；
- 制作目标和目标优先级；
- 必须保留的声音特征；
- 必须避免的结果与副作用；
- 参考音频及具体参考维度；
- 目标平台、交付格式和技术标准；
- 可处理范围、处理深度和候选数量；
- 时间、算力、成本和人工复核约束；
- 可机器检查的验收条件。

## 5. 核心输出合同

`ProductionResult` 至少包含：

- 输入诊断和问题证据；
- Treatment Plan、工艺链和参数；
- 一个或多个候选音频版本；
- 版本血缘和可复现环境信息；
- 技术质量门结果；
- 风险、副作用和降级说明；
- 推荐候选及其技术理由；
- 公司人工决定；
- Final 交付包和 Craft Library 写回记录。

## 6. 产品形态

Moodify 的正式产品表面按以下优先级建设：

1. `Moodify Core`：声学分析、DSP、MRS、Craft、Judge；
2. `Moodify Runtime`：任务、队列、版本、存储、报告、恢复和成本记录；
3. `Moodify Contract/API`：供荣景文川及其他获授权音乐生产组织调用；
4. 内部 Operator Console：只用于调试、运维、验收和异常处置，不作为创作者产品。

## 7. 冷边界

Moodify 不做：

- 创作者社区、消费级应用或创作者自助前端；
- 创作者沟通、需求访谈和艺人服务；
- 才华评估、签约推荐和艺人定位；
- 词曲选题、文化叙事和最终审美决策；
- 宣发、发行、粉丝、舞台、商务和艺人运营；
- 用播放量或单一算法分数判断艺术价值；
- 无人监督的最终艺术审批。

内部控制台、API 文档和运维工具不属于创作者前端，可以为工业系统的可观测性和安全运行保留。

## 8. 发展原则

1. **纵向加深优先于横向扩张。** 优先提高音频处理深度和可靠性，不扩张为音乐产业平台。
2. **合同优先。** 人的模糊意图由公司转译，Moodify 对结构化任务负责。
3. **结果优先。** 长运行时间、复杂模型或昂贵设备本身不构成价值，必须形成可听和可验证的提升。
4. **可复现优先。** 每个结果必须能够追踪输入、代码、参数、候选、门禁、决定和交付。
5. **工艺复利。** 每个项目都应同时形成声音结果、质量证据和可复用工艺知识。
6. **人类艺术主权。** Moodify 提供技术判断和候选，不取代音乐公司的制作人与最终决策者。
7. **年度工业发布。** 每年只封存一个正式稳定版本，年度内的Alpha、Beta和RC不替代年度发布门禁。
8. **可持续节奏。** 默认每天4小时推进一个原子任务，剩余注意力用于验证、证据和继承，不以长工时制造虚假进度。

## 8.1 工程厚度与文明继承

Moodify 的长期价值不以功能数量或迭代速度定义。任何生产与研发任务都必须同时产生：

```text
Result（结果）
+ Evidence（证据）
+ Inheritance（继承）
```

代码和模型可以被替换，但经过验证的案例、失败边界、专业判断、标准历史和工艺证据必须能够跨版本继承。任务和里程碑的统一门禁由
`MOODIFY_ENGINEERING_THICKNESS_STANDARD.md`定义。

这意味着：

- 不覆盖版本，不删除失败来制造成功率；
- 不让汇总替代原始记录，不让指标替代人的最终判断；
- 每个项目都要使下一次生产获得更高起点；
- 每次升级都必须保护或明确迁移已有工程记忆。

## 9. 与既有版本的关系

- v2.0.0-mvp 已完成的项目、Brief、线程、Treatment Plan、版本、Judge、人工审批和 Final 归档继续作为基础；
- 既有 `CreativeBrief` 视为 `ProductionSpec` 的兼容前身；
- 既有 Workspace UI 和 Operator Console 视为内部验证、运维表面；
- 既有 AI 音乐后处理能力是首条生产线，不是最终能力上限；
- 后续扩展聚焦 stem 级处理、混音关系、空间、动态、母带、质量校准和工业运行，不进入创作者运营领域。
- 所有扩展必须通过工程厚度与继承门禁，禁止以新功能冲淡历史可追溯性。
